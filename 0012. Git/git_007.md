**Pull Request (PR)** và **Merge Request (MR)** về bản chất là **cùng một khái niệm**, chỉ khác tên gọi tùy nền tảng: GitHub, Bitbucket, Azure DevOps gọi là Pull Request; GitLab gọi là Merge Request. Cả hai đều là cơ chế để đề xuất hợp nhất thay đổi từ nhánh nguồn (source/compare) vào nhánh đích (target/base), kèm theo diff, thảo luận, review và kết quả CI/CD trên một giao diện duy nhất.

---

## 1. Bản chất: Tại sao cùng một thứ lại có hai tên?

Sự khác biệt nằm ở **hành động cuối cùng** mà mỗi nền tảng muốn nhấn mạnh:

- **Pull Request**: Nhấn mạnh hành động **"kéo" (pull)** thay đổi từ nhánh của bạn vào kho chứa của người khác. Cách gọi này bắt nguồn từ lệnh `git request-pull` trong Git thuần, vốn được dùng để gửi yêu cầu qua email trong cộng đồng nhân Linux.
- **Merge Request**: Nhấn mạnh hành động **"hợp nhất" (merge)** cuối cùng để đưa thay đổi vào nhánh đích. GitLab chọn tên này vì trọng tâm là kết quả cuối cùng của quá trình.

Dù tên khác nhau, **luồng làm việc cơ bản là giống hệt nhau**: bạn push một nhánh lên, mở request, nhận review, vượt qua các kiểm tra tự động, và cuối cùng là merge.

---

## 2. Cơ chế vận hành: Một PR/MR thực chất là gì?

Về mặt kỹ thuật, PR/MR **không phải là một đối tượng trong Git**. Nó là một **lớp metadata do nền tảng (GitHub/GitLab) tạo ra**, tham chiếu đến:

- **Cặp nhánh**: `source branch` (nơi chứa thay đổi) và `target branch` (nơi muốn hợp nhất vào).
- **Tập hợp commit** nằm trong `target..source` — chính là những gì sẽ được merge.
- **Diff** được tính toán động từ `merge-base` của hai nhánh, không phải dữ liệu tĩnh được lưu sẵn.

Khi bạn mở PR/MR, nền tảng thực hiện các bước logic sau:

1. **Tính toán diff** giữa nhánh nguồn và nhánh đích tại thời điểm mở.
2. **Hiển thị commit history** của nhánh nguồn (những commit chưa có ở nhánh đích).
3. **Kích hoạt các pipeline CI/CD** đã được cấu hình cho sự kiện PR/MR.
4. **Tạo không gian thảo luận** (comment theo dòng, review tổng thể, suggestion).
5. **Theo dõi trạng thái** (open, draft, approved, changes requested, merged, closed).

**Điểm mấu chốt về mặt lý thuyết**: PR/MR **không thay đổi Git history**. Nó chỉ là **cổng kiểm soát (gate)** trước khi thực hiện thao tác merge thực sự. Khi bạn nhấn nút "Merge", nền tảng mới thực thi lệnh Git tương ứng (merge commit, squash, hoặc rebase) trên server.

## 3. Luồng làm việc chuẩn (Unified Workflow)

Dù dùng GitHub hay GitLab, quy trình điển hình gồm các giai đoạn sau:

### 3.1 Tạo nhánh và phát triển

```bash
git switch -c feature/add-login    # tạo nhánh từ nhánh đích (thường là main)
# ... code ...
git add .
git commit -m "feat: add login form"
git push -u origin feature/add-login
```

### 3.2 Mở PR/MR

- **GitHub**: `gh pr create` hoặc qua web UI.
- **GitLab**: `glab mr create` hoặc qua web UI.

Ở bước này, bạn cung cấp:
- **Title**: theo Conventional Commits (ví dụ: `feat(auth): add login form`).
- **Description**: giải thích **why** (tại sao thay đổi này cần thiết), **what** (tóm tắt thay đổi), và **test plan** (cách kiểm chứng).
- **Reviewers**: người review (có thể tự động qua `CODEOWNERS`).
- **Labels, milestone, linked issue** (ví dụ: `Fixes #42` để tự động đóng issue khi merge).

### 3.3 Review và thảo luận

- **Reviewer** xem diff, để lại comment theo dòng, có thể **suggest changes** (đề xuất sửa trực tiếp).
- Trạng thái review:
  - **GitHub**: `Comment`, `Approve`, `Request changes`.
  - **GitLab**: `Approve`, có thể `Revoke approval`; reviewer cũng có thể yêu cầu thay đổi qua comment.

### 3.4 CI/CD checks

- **GitHub Actions** (hoặc CI khác) chạy test, lint, build, security scan — kết quả hiển thị dưới dạng **status checks** trên PR.
- **GitLab CI/CD** tích hợp pipeline trực tiếp vào MR; có thể đặt **"Merge when pipeline succeeds"** (auto-merge).
- Các **required status checks** phải pass trước khi nút Merge được kích hoạt (thường được enforce bởi **branch protection rules**).

### 3.5 Merge

Khi mọi thứ đã sẵn sàng (approved + checks pass + không conflict), bạn chọn **chiến lược merge** (xem phần 5) và nhấn Merge.

## 4. Điểm khác biệt thực tế giữa GitHub PR và GitLab MR

Mặc dù cùng bản chất, hai nền tảng có cách triển khai khác nhau ở các khía cạnh sau:

| Khía cạnh                   | GitHub Pull Request                                                   | GitLab Merge Request                                                                    |
| --------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **Tên nhánh**               | `head` (compare) → `base`                                             | `source` → `target`                                                                     |
| **Draft**                   | Trạng thái draft riêng, chuyển bằng 1 click hoặc `gh pr ready`        | Tiền tố `Draft:` trong title, hoặc quick action `/draft`, `/ready`                      |
| **Approval**                | Dùng **branch protection rules** + **CODEOWNERS** để yêu cầu reviewer | **Approval rules** linh hoạt trên mọi tier (Free: optional, Premium/Ultimate: bắt buộc) |
| **Approval sau commit mới** | Được giữ, trừ khi branch bật "dismiss stale approvals"                | Mặc định **bị xóa** khi có commit mới (setting trên Premium/Ultimate)                   |
| **Merge methods**           | Merge commit, Squash, Rebase                                          | Merge commit, Semi-linear, Fast-forward; Squash là setting riêng                        |
| **Auto-merge**              | **Auto-merge** (tự merge khi checks pass)                             | **"Merge when pipeline succeeds"**                                                      |
| **Merge queue**             | **Merge queue** (hàng đợi merge cho branch nhiều traffic)             | **Merge trains** (Premium/Ultimate)                                                     |
| **CLI**                     | `gh pr create`                                                        | `glab mr create`                                                                        |

## 5. Các chiến lược Merge (áp dụng cho cả PR và MR)

Khi merge, nền tảng thường cung cấp 3 lựa chọn chính, mỗi lựa chọn tạo ra hình thái lịch sử khác nhau:

### 5.1 Merge Commit (`--no-ff`)

- **Cơ chế**: Tạo một **merge commit** với hai parent (nhánh đích và nhánh nguồn), giữ nguyên toàn bộ commit của nhánh nguồn.
- **Ưu điểm**: Bảo toàn ngữ nghĩa "feature X được merge vào thời điểm Y"; dễ revert toàn bộ feature bằng một merge commit.
- **Nhược điểm**: Lịch sử có "merge bubble" (nhánh rẽ), kém tuyến tính.
- **Khi nào dùng**: PR/MR lớn, cần giữ từng commit riêng lẻ để audit hoặc bisect; nhánh có nhiều commit có ý nghĩa độc lập.

### 5.2 Squash and Merge

- **Cơ chế**: Gộp **toàn bộ commit** của nhánh nguồn thành **một commit duy nhất** trên nhánh đích.
- **Ưu điểm**: Lịch sử nhánh đích cực kỳ sạch (1 commit cho 1 feature/fix); dễ đọc, dễ revert.
- **Nhược điểm**: Mất lịch sử chi tiết bên trong feature; `git log --follow` không theo dõi được từng bước thay đổi.
- **Khi nào dùng**: **Hầu hết các PR/MR thông thường** — đây là lựa chọn phổ biến nhất cho team muốn lịch sử tuyến tính và sạch sẽ.

### 5.3 Rebase and Merge

- **Cơ chế**: **Áp lại từng commit** của nhánh nguồn lên đầu nhánh đích, **không tạo merge commit** → lịch sử tuyến tính hoàn toàn.
- **Ưu điểm**: Lịch sử phẳng, không có merge bubble; từng commit được bảo toàn (khác squash).
- **Nhược điểm**: **Viết lại SHA** của mọi commit (vì parent thay đổi); nếu có conflict, phải giải quyết từng commit.
- **Khi nào dùng**: PR/MR nhỏ, từng commit là một bước logic có thể review độc lập; team ưu tiên lịch sử tuyến tính.

### 5.4 Bảng so sánh nhanh

|                       | Merge Commit           | Squash                | Rebase                |
| --------------------- | ---------------------- | --------------------- | --------------------- |
| **Lịch sử**           | Phân nhánh (có bubble) | Tuyến tính (1 commit) | Tuyến tính (n commit) |
| **Giữ commit gốc**    | ✅                      | ❌ (gộp)               | ✅ (SHA mới)           |
| **Viết lại lịch sử**  | ❌                      | ❌ (với nhánh đích)    | ✅ (SHA mới)           |
| **Dễ revert feature** | ✅ (1 merge commit)     | ✅ (1 commit)          | ❌ (nhiều commit)      |
| **Phù hợp**           | PR lớn, audit          | Hầu hết PR            | PR nhỏ, lịch sử sạch  |

## 6. Best Practices (Lý thuyết được đúc kết từ cộng đồng)

### 6.1 Giữ PR/MR nhỏ và tập trung

- **Một feature/fix cho một PR** — không trộn nhiều mục đích khác nhau.
- **Kích thước lý tưởng**: dưới **400 dòng thay đổi** (lines changed). Lý do: reviewer có "ngân sách nhận thức" hạn chế; PR càng lớn, chất lượng review càng giảm.

### 6.2 Commit nguyên tử (Atomic Commits)

- Mỗi commit nên là **một thay đổi logic hoàn chỉnh**, không trộn lẫn refactor + feature + fix.
- Nếu cần sửa nhiều file cho một mục đích → một commit. Nếu là nhiều mục đích → nhiều commit.
- **Lý thuyết**: Atomic commit giúp `git bisect` hiệu quả và cho phép revert từng phần mà không ảnh hưởng toàn bộ PR.

### 6.3 Title và Description chất lượng

- **Title**: dùng **Conventional Commits** (`feat:`, `fix:`, `chore:`...) và **động từ mệnh lệnh** ("add", "fix" — không phải "added", "fixed"). Giới hạn **< 70 ký tự**.
- **Description**: trả lời **"why"** (tại sao cần thay đổi) quan trọng hơn **"what"** (what có thể thấy trong diff). Kèm **test plan** cụ thể.
- **Link issue**: `Fixes #N` hoặc `Closes #N` để tự động đóng issue khi merge.

### 6.4 Draft PR/MR cho công việc đang tiến hành

- Mở **Draft PR** (GitHub) hoặc **Draft MR** (GitLab) ngay từ đầu để:
  - Thông báo cho team biết bạn đang làm gì (tránh trùng lặp công việc).
  - Nhận phản hồi sớm về hướng tiếp cận (trước khi viết quá nhiều code).
  - CI có thể chạy ngay từ giai đoạn sớm.

### 6.5 Đảm bảo CI pass trước khi request review

- **Không bao giờ** request review khi CI đang đỏ — gây lãng phí thời gian reviewer.
- Chạy test local trước khi push (`npm test`, `pytest`...) để giảm vòng lặp.

### 6.6 Phản hồi review một cách xây dựng

- **Comment cụ thể**: thay vì "code này sai", hãy nói "dòng 42: biến `x` có thể null ở đây, nên thêm kiểm tra".
- **Phân biệt blocking và non-blocking**: đánh dấu rõ comment nào là "nit" (không bắt buộc) và comment nào phải sửa.
- **Suggestion**: dùng tính năng suggest changes để đề xuất code cụ thể — giảm vòng lặp qua lại.

### 6.7 Xử lý conflict trước khi merge

- **Rebase lên nhánh đích** trước khi merge để đảm bảo không conflict:
  ```bash
  git fetch origin
  git rebase origin/main
  # giải quyết conflict
  git push --force-with-lease
  ```
- **Lý thuyết**: Giải quyết conflict **trên nhánh nguồn** (trước merge) an toàn hơn nhiều so với giải quyết **trên nhánh đích** (sau merge), vì nó không ảnh hưởng đến lịch sử chung.

## 7. Tổng kết lý thuyết

| Khái niệm             | Định nghĩa cốt lõi                                                    | Lưu ý                                               |
| --------------------- | --------------------------------------------------------------------- | --------------------------------------------------- |
| **PR/MR**             | Đề xuất hợp nhất nhánh nguồn vào nhánh đích, kèm diff + review + CI   | Không phải đối tượng Git — là metadata của nền tảng |
| **Pull vs Merge**     | Pull = nhấn mạnh "kéo" thay đổi; Merge = nhấn mạnh "hợp nhất" kết quả | Cùng bản chất, khác ngữ nghĩa từ ngữ                |
| **Review states**     | GitHub: Approve/Request changes/Comment; GitLab: Approve/Revoke       | Quyết định điều kiện merge                          |
| **Branch protection** | Enforce required checks + reviews trước khi merge                     | Lớp bảo vệ nhánh chính                              |
| **Merge strategies**  | Merge commit (giữ topology), Squash (1 commit), Rebase (tuyến tính)   | Chọn theo ngữ nghĩa lịch sử mong muốn               |
| **Merge queue**       | Serialize merge của nhiều PR để tránh conflict                        | GitHub: Merge queue; GitLab: Merge trains           |
| **Best practices**    | PR nhỏ (<400 dòng), atomic commits, title chuẩn, CI xanh trước review | Giảm tải nhận thức cho reviewer, tăng tốc vòng lặp  |

**Điểm mấu chốt cần nhớ**: PR và MR là **cùng một cơ chế**, chỉ khác tên gọi và một số tính năng phụ thuộc nền tảng. Chúng đóng vai trò là **cổng kiểm soát chất lượng** trước khi thay đổi được hợp nhất vào nhánh chính — nơi hội tụ của **code review**, **kiểm tra tự động (CI/CD)**, và **quyết định merge**. Việc chọn chiến lược merge (merge commit, squash, rebase) phản ánh triết lý của team về lịch sử: **bảo toàn ngữ cảnh** (merge commit) hay **tối giản và tuyến tính** (squash/rebase).
