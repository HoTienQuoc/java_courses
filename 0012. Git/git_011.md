# Git Interactive Rebase — Giải thích lý thuyết chi tiết

---

## 1. Bản chất: Interactive Rebase là gì?

### 1.1 Định nghĩa

**Interactive rebase** (`git rebase -i`) là phiên bản **có can thiệp** của rebase — thay vì Git tự động áp lại commit, nó **mở editor** cho bạn xem danh sách commit (gọi là **todo list**) và **quyết định** làm gì với từng commit trước khi thực thi.

> **Điểm lý thuyết cốt lõi**: Interactive rebase là **công cụ viết lại lịch sử có kiểm soát** — nó cho phép bạn "biên tập" lại quá khứ: sắp xếp lại, gộp, tách, sửa message, xóa, chèn commit. Đây là công cụ mạnh nhất của Git để **dọn dẹp lịch sử trước khi chia sẻ**.

### 1.2 Mô hình tư duy: "Biên tập bản thảo"

Hãy nghĩ lịch sử commit như **bản thảo**:

- **Rebase thường** = "viết lại chương 3-5 dựa trên chương 1-2 mới nhất" (dịch chuyển vị trí).
- **Interactive rebase** = "mở bản thảo, sắp xếp lại chương, gộp chương ngắn, xóa chương nháp, sửa tiêu đề" (biên tập toàn diện).

**Lý thuyết**: Interactive rebase tách quá trình thành **hai pha**:
1. **Pha lập kế hoạch**: Bạn viết "kịch bản" (todo list) — muốn làm gì với từng commit.
2. **Pha thực thi**: Git chạy kịch bản, áp từng commit theo chỉ dẫn, dừng lại khi gặp `edit`/`break`/conflict.

Đây là điểm khác biệt căn bản với rebase thường: **bạn kiểm soát từng bước**, không phải Git.

### 1.3 Cơ chế bên trong — Điều gì thực sự xảy ra?

Khi bạn chạy `git rebase -i <base>`, Git thực hiện:

```
Bước 1: Tìm commit range = <base>..HEAD (các commit sẽ rebase)
Bước 2: Tạo thư mục trạng thái: .git/rebase-merge/
   - git-rebase-todo: kịch bản bạn sẽ sửa
   - done: các commit đã áp
   - git-rebase-todo.backup: bản gốc
   - head-name: branch đang rebase
   - onto: commit đích (base)
Bước 3: Detach HEAD tại <base>
Bước 4: Mở editor với file git-rebase-todo
Bước 5: Đọc todo list SAU KHI bạn lưu và đóng editor
Bước 6: Thực thi từng dòng trong todo:
   - pick → cherry-pick commit đó
   - squash/fixup → cherry-pick + amend commit trước
   - edit → cherry-pick + dừng lại
   - drop → bỏ qua
   - exec → chạy lệnh shell
Bước 7: Khi todo hết → di chuyển branch ref về commit cuối
Bước 8: Xóa .git/rebase-merge/, attach HEAD lại
```

**Điểm mấu chốt**: Interactive rebase **thực chất là một chuỗi cherry-pick tuần tự** có kiểm soát. Mỗi `pick` = một cherry-pick. Mỗi `squash` = cherry-pick + amend. Đây là lý do conflict xảy ra **từng commit một**.

## 2. Cú pháp và chọn range

### 2.1 Cú pháp cơ bản

```bash
git rebase -i <base>
```

`<base>` là commit **TRƯỚC** commit đầu tiên bạn muốn thao tác. Commit range là `<base>..HEAD` — **không bao gồm** `<base>`.

### 2.2 Các cách chỉ định range

| Cú pháp                     | Ý nghĩa                                        |
| --------------------------- | ---------------------------------------------- |
| `git rebase -i HEAD~5`      | 5 commit gần nhất                              |
| `git rebase -i HEAD~3`      | 3 commit gần nhất                              |
| `git rebase -i <sha>`       | Mọi commit sau `<sha>`                         |
| `git rebase -i --root`      | Từ root commit (commit đầu tiên)               |
| `git rebase -i main`        | Commit trên branch hiện tại không thuộc `main` |
| `git rebase -i origin/main` | Commit chưa push lên `origin/main`             |
| `git rebase -i @{u}`        | Commit chưa push lên upstream                  |

**`@{u}`** = `@{upstream}` — shorthand cho upstream branch. Rất tiện cho "dọn commit trước khi push".

### 2.3 Ví dụ chọn range

```
A ← B ← C ← D ← E ← F ← G   (HEAD)

git rebase -i HEAD~3
# range = D..G = {E, F, G}    ← 3 commit gần nhất
# editor hiện E, F, G

git rebase -i HEAD~5
# range = B..G = {C, D, E, F, G}

git rebase -i --root
# range = {A, B, C, D, E, F, G}  ← toàn bộ, kể cả root
```

**Lưu ý**: Nếu bạn chỉ định `HEAD~3`, editor hiện commit `E, F, G` (KHÔNG có `D`). `D` là base — không bị chạm.

## 3. Todo List — Ngôn ngữ của interactive rebase

### 3.1 Cấu trúc file

Sau khi chạy `git rebase -i HEAD~4`, editor (thường `vim`) mở:

```
pick a1b2c3d feat: add login form
pick e4f5g6h fix: typo in validation
pick i7j8k9l feat: add logout
pick m0n1o2p wip

# Rebase d5e6f7g..m0n1o2p onto d5e6f7g (4 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup <commit> = like "squash", but discard this commit's log message
# x, exec <command> = run command (the rest of the line) using shell
# b, break = stop here (continue rebase later with 'git rebase --continue')
# d, drop <commit> = remove commit
# l, label <label> = label current HEAD with a name
# t, reset <label> = reset HEAD to a label
# m, merge [-C <commit> | -c <commit>] <label> [# <oneline>]
#
# These lines can be re-ordered; they are executed from top to bottom.
#
# If you remove a line here THAT COMMIT WILL BE LOST.
#
# However, if you remove everything, the rebase will be aborted.
```

### 3.2 Cấu trúc một dòng

```
<command> <sha> <subject>
```

- **Thứ tự dòng** = thứ tự áp commit. Dòng đầu tiên được áp trước.
- **Command** = hành động với commit đó.
- **`<sha>`** = định danh commit (không được sửa).
- **`<subject>`** = message (có thể sửa cho dễ đọc — Git bỏ qua).

### 3.3 Nguyên tắc "thứ tự là vàng"

**Sắp xếp lại dòng = sắp xếp lại commit.** Đây là cách bạn **reorder** history — một trong những ứng dụng mạnh nhất của interactive rebase.

```
# Trước
pick a1b2c3d feat: add login form
pick e4f5g6h feat: add logout
pick i7j8k9l fix: typo

# Sau khi di chuyển
pick i7j8k9l fix: typo
pick a1b2c3d feat: add login form
pick e4f5g6h feat: add logout
```

Git sẽ áp `i7j8k9l` trước — **có thể conflict** nếu commit phụ thuộc lẫn nhau.

## 4. Các lệnh chi tiết — Lý thuyết từng lệnh

### 4.1 `pick` (p) — Giữ nguyên

```
pick a1b2c3d feat: add login form
```

**Hành động**: Cherry-pick commit `a1b2c3d` lên HEAD hiện tại. Giữ nguyên nội dung và message (SHA thay đổi vì parent khác).

**Lý thuyết**: Đây là "no-op" — commit được áp lại **y hệt**. Nếu commit không conflict và base không đổi → tree giống hệt, chỉ SHA khác (vì parent và committer date).

**Khi nào dùng**: Khi bạn muốn giữ commit, chỉ cần nó trong rebase để **sắp xếp lại vị trí**.

### 4.2 `reword` (r) — Sửa message

```
reword a1b2c3d feat: add login form
```

**Hành động**: Áp commit, **mở editor** để sửa message. Nội dung giữ nguyên.

**Lý thuyết**: 
- Nếu chỉ sửa message, **tree giữ nguyên** — SHA mới chỉ vì message khác.
- Author/committer date: author giữ, committer = thời điểm rebase.

**Khi nào dùng**:
- Sửa typo trong message.
- Chuẩn hóa theo Conventional Commits.
- Thêm context/mô tả cho commit cũ.

**Khác `git commit --amend`**: `--amend` chỉ sửa commit **gần nhất**. `reword` sửa **bất kỳ** commit trong range.

### 4.3 `edit` (e) — Dừng để amend

```
edit a1b2c3d feat: add login form
```

**Hành động**: Áp commit, **dừng lại** tại commit đó. Bạn có thể:

```bash
# 1. Sửa nội dung
vim file.js
git add file.js
git commit --amend        # cập nhật commit hiện tại

# 2. Tách commit thành nhiều commit
git reset HEAD^           # quay lại trước commit, giữ thay đổi trong working tree
git add -p                # stage từng phần
git commit -m "part 1"
git add .
git commit -m "part 2"

# 3. Thêm file bị bỏ sót
git add forgotten.js
git commit --amend --no-edit

# 4. Xóa hoàn toàn commit
git reset --hard HEAD^    # nguy hiểm — commit bị bỏ

# Sau khi xong:
git rebase --continue
```

**Lý thuyết**: `edit` là "cửa ngõ" cho mọi thao tác phức tạp — vì nó dừng lại, bạn có **toàn quyền** với repo state tại commit đó.

**Khi nào dùng**:
- Cần tách commit (split).
- Cần thêm file bị bỏ sót.
- Cần sửa nội dung phức tạp (nhiều file).
- Cần chạy test tại commit đó.

### 4.4 `squash` (s) — Gộp, giữ message

```
pick a1b2c3d feat: add login form
squash e4f5g6h fix: typo
squash i7j8k9l address review
```

**Hành động**: Cherry-pick `e4f5g6h`, **gộp vào `a1b2c3d`** (amend), rồi mở editor để **kết hợp message**:

```
# This is a combination of 3 commits.
# This is the 1st commit message:

feat: add login form

# This is the commit message #2:

fix: typo

# This is the commit message #3:

address review

# Please enter the commit message for your changes. Lines starting
# with '#' will be ignored, and an empty message aborts the commit.
```

Bạn **sửa** để có message cuối cùng (thường giữ message đầu, bỏ các message sau).

**Kết quả**: 1 commit duy nhất (`a1b2c3d` được thay bằng commit mới) chứa nội dung của cả 3.

**Lý thuyết**:
- `squash` **luôn mở editor** — cho bạn kiểm soát message cuối.
- Commit `squash` **phải đứng sau** một commit `pick`/`reword`/`edit` — không thể là dòng đầu tiên (vì không có gì để gộp vào).
- SHA cuối khác tất cả SHA gốc.

**Khi nào dùng**:
- Gộp "fix typo" vào feature commit.
- Gộp nhiều commit nhỏ thành một feature commit có ý nghĩa.
- Gộp "address review" vào commit gốc.

### 4.5 `fixup` (f) — Gộp, bỏ message

```
pick a1b2c3d feat: add login form
fixup e4f5g6h fix: typo
fixup i7j8k9l wip
```

**Hành động**: Cherry-pick, gộp vào commit trước, **BỎ message** của commit đang áp. **Không mở editor**.

**Kết quả**: 1 commit duy nhất với **message của commit đầu tiên** (`feat: add login form`).

**Lý thuyết**: `fixup` = "squash không cần editor". Message của commit `fixup` **bị vứt hoàn toàn**.

**Khi nào dùng**:
- Commit sau là "rác" (wip, fix typo, address review) — không cần message riêng.
- Gộp nhanh nhiều commit sửa lỗi nhỏ.
- Kết hợp với `--autosquash` (xem mục 5).

### 4.6 `drop` (d) — Xóa commit

```
drop m0n1o2p wip
```

**Hành động**: **Bỏ qua** commit — không áp. Nội dung của commit **không có trong lịch sử mới**.

**Tương đương**: Xóa dòng khỏi todo list.

**Lý thuyết**: 
- Commit vẫn tồn tại trong objects (unreachable) — cứu được qua reflog.
- Nếu commit sau phụ thuộc commit bị drop → **conflict** khi áp commit sau (vì nội dung thiếu).

**Khi nào dùng**:
- Xóa commit "wip" không cần.
- Xóa commit thử nghiệm.
- Xóa commit đã được thay thế bởi commit khác.

**Cẩn thận**: Nếu commit bị drop chứa thay đổi quan trọng → mất. Kiểm tra kỹ trước khi drop.

### 4.7 `exec` (x) — Chạy lệnh shell

```
pick a1b2c3d feat: add login form
exec npm test
pick e4f5g6h feat: add logout
exec npm test
```

**Hành động**: Chạy lệnh shell **tại điểm đó** trong quá trình rebase. Nếu lệnh fail (exit code ≠ 0) → rebase **dừng** — bạn phải sửa hoặc `--skip`/`--abort`.

**Lý thuyết**: `exec` biến interactive rebase thành **công cụ kiểm tra lịch sử** — đảm bảo mỗi commit đều "xanh" (test pass, build OK).

**Khi nào dùng**:
- **Test-driven history**: Mỗi commit phải pass test → dễ bisect.
- **Build check**: Mỗi commit phải build được.
- **Lint check**: Mỗi commit phải pass lint.
- **Migration check**: Chạy DB migration tại mỗi commit.

**Ví dụ nâng cao**:

```bash
git rebase -i HEAD~5 --exec "npm test"
# → tự động chạy "npm test" sau MỖI commit, không cần gõ exec từng dòng
```

Hoặc trong todo list:

```
pick a1b2c3d feat: add login form
x npm test && npm run lint
pick e4f5g6h feat: add logout
x npm test
```

**Lý thuyết sâu**: `exec` chạy với **shell của bạn** (thường `sh`). Có thể dùng `&&`, `||`, pipe... Nếu script dài, tốt hơn là tạo script riêng và gọi.

### 4.8 `break` (b) — Dừng có chủ đích

```
pick a1b2c3d feat: add login form
break
pick e4f5g6h feat: add logout
```

**Hành động**: Dừng rebase tại điểm đó (như `edit` nhưng **không có commit** đi kèm). Bạn có thể:

- Kiểm tra trạng thái (`git log`, `git diff`).
- Chạy lệnh (`npm test`).
- Sửa file (`vim`).
- Rồi `git rebase --continue`.

**Lý thuyết**: `break` linh hoạt hơn `exec` — vì `exec` chạy lệnh tự động, còn `break` **chờ bạn** làm gì đó thủ công.

**Khi nào dùng**:
- Debug giữa rebase.
- Chèn commit mới tại điểm cụ thể.
- Kiểm tra trạng thái trung gian.

### 4.9 `label`/`reset`/`merge` — Cho `--rebase-merges`

Chỉ dùng với `git rebase -i --rebase-merges` để tái tạo cấu trúc merge:

```
label onto
reset onto
pick a1b2c3d commit A
label branch1
reset onto
pick e4f5g6h commit B
merge -C abc1234 branch1 # Merge branch 'branch1'
```

- `label <name>`: Đặt tên cho HEAD hiện tại (để `reset` sau).
- `reset <label>`: Quay HEAD về label (như `git reset --hard`).
- `merge -C <sha> <label>`: Tạo merge commit từ label (giữ message từ `<sha>`).

**Lý thuyết**: Đây là ngôn ngữ "script" để tái tạo DAG phức tạp — dùng khi branch có merge commit và bạn muốn giữ topology.

### 4.10 Bảng tổng hợp

| Lệnh     | Viết tắt | Áp commit | Mở editor           | Tác dụng            |
| -------- | -------- | --------- | ------------------- | ------------------- |
| `pick`   | `p`      | ✅         | ❌                   | Giữ nguyên          |
| `reword` | `r`      | ✅         | ✅ (message)         | Sửa message         |
| `edit`   | `e`      | ✅ + dừng  | ❌                   | Amend thủ công      |
| `squash` | `s`      | ✅ + gộp   | ✅ (message kết hợp) | Gộp, giữ message    |
| `fixup`  | `f`      | ✅ + gộp   | ❌                   | Gộp, bỏ message     |
| `drop`   | `d`      | ❌         | ❌                   | Xóa                 |
| `exec`   | `x`      | —         | ❌                   | Chạy lệnh           |
| `break`  | `b`      | — (dừng)  | ❌                   | Dừng thủ công       |
| `label`  | `l`      | —         | ❌                   | Đặt tên HEAD        |
| `reset`  | `t`      | —         | ❌                   | Reset HEAD về label |
| `merge`  | `m`      | ✅         | ✅ (tùy)             | Tạo merge commit    |

## 5. `--autosquash` — Tự động hóa fixup/squash

### 5.1 Vấn đề

Workflow thực tế: Bạn commit feature, rồi reviewer yêu cầu sửa. Bạn tạo commit "fix", "address review". Cuối cùng phải **gộp thủ công** chúng vào commit gốc.

### 5.2 Giải pháp: `fixup!` và `squash!`

Khi commit sửa nhỏ, dùng prefix đặc biệt trong message:

```bash
# Sửa commit "feat: add login form"
git commit -m "fixup! feat: add login form"

# Hoặc sửa commit "feat: add logout"
git commit -m "squash! feat: add logout"
```

**Lý thuyết**: `fixup!`/`squash!` + subject của commit đích = "tôi là bản sửa cho commit có subject đó".

### 5.3 `--autosquash`

```bash
git rebase -i --autosquash HEAD~5
```

**Hành động**: Git **tự động**:
1. Tìm commit có subject khớp sau `fixup!`/`squash!`.
2. **Sắp xếp** commit `fixup!` ngay sau commit đích.
3. **Đổi lệnh** thành `fixup` hoặc `squash` tương ứng.

Todo list tự động:
```
pick a1b2c3d feat: add login form
fixup e4f5g6h fixup! feat: add login form
pick i7j8k9l feat: add logout
squash m0n1o2p squash! feat: add logout
```

Bạn chỉ cần **lưu và đóng editor** — Git tự làm phần còn lại.

### 5.4 Cấu hình mặc định

```bash
git config --global rebase.autoSquash true
```

→ Mọi `git rebase -i` đều tự động áp `--autosquash`.

### 5.5 `git commit --fixup=<sha>` — Tạo fixup tự động

```bash
git commit --fixup=a1b2c3d
# Tự động tạo message: "fixup! feat: add login form"
```

**Lý thuyết**: `--fixup=<sha>` lấy **subject** của commit `<sha>` và tạo message `fixup! <subject>`. Không cần nhớ subject.

**Tương tự**: `--squash=<sha>` cho `squash!`.

### 5.6 Workflow hoàn chỉnh

```bash
# 1. Code feature
git commit -m "feat: add login form"

# 2. Reviewer yêu cầu sửa
vim login.js
git commit --fixup=HEAD~1
# → "fixup! feat: add login form"

# 3. Sửa thêm
vim login.js
git commit --fixup=HEAD~2

# 4. Trước khi merge, dọn dẹp
git rebase -i --autosquash origin/main
# → Tự động gộp tất cả fixup! vào commit gốc

# 5. Force push
git push --force-with-lease
```

**Lý thuyết**: Đây là **workflow được khuyến nghị** cho team dùng PR — commit thoải mái trong lúc làm, dọn dẹp tự động trước khi merge.

## 6. Conflict trong interactive rebase

### 6.1 Đặc điểm

Conflict xảy ra **từng commit một** — khi áp commit cụ thể:

```bash
git rebase -i HEAD~4
# editor → lưu → Git bắt đầu áp

# Applying: feat: add login form
# Applying: fix: typo
# CONFLICT (content): Merge conflict in login.js
# error: could not apply e4f5g6h... fix: typo
```

**Khác merge**: Merge conflict 1 lần (tất cả cùng lúc). Rebase conflict N lần (từng commit).

### 6.2 `ours`/`theirs` đảo ngược

**Cạm bẫy lớn nhất**:

```bash
# Trong rebase conflict:
git checkout --ours <file>    # = base mới (commit đang áp lên)
git checkout --theirs <file>  # = commit đang được áp (code CỦA BẠN)
```

**Ngược hoàn toàn với merge**. Lý do: rebase "replay" commit của bạn lên base mới. Trong quá trình replay, Git coi base mới là "nền hiện tại" (ours), còn commit bạn đang áp là "thay đổi được áp vào" (theirs).

**Cách nhớ**: Trong rebase, `theirs` = "code bạn đang cố áp vào" = **code của bạn**.

### 6.3 Quy trình giải quyết

```bash
# 1. Nhận diện
git status
# both modified: login.js

# 2. Sửa file
vim login.js
# chọn/ghép, xóa marker

# 3. Đánh dấu
git add login.js

# 4. Tiếp tục
git rebase --continue

# Nếu conflict tiếp → lặp lại
```

### 6.4 Các lựa chọn khi conflict

```bash
git rebase --continue       # sau khi giải quyết
git rebase --skip           # bỏ qua commit đang áp (nguy hiểm — mất nội dung)
git rebase --abort          # hủy toàn bộ rebase (quay về trước)
git rebase --edit-todo      # mở lại todo list (thay đổi kế hoạch giữa chừng)
```

**`--skip` — Lý thuyết**: Bỏ qua commit đang conflict — commit đó **không có trong lịch sử mới**. Dùng khi commit đã được áp bằng cách khác (vd: đã cherry-pick). **Cẩn thận**: nội dung commit bị mất.

**`--edit-todo` — Ứng dụng**: Khi đang rebase giữa chừng, phát hiện kế hoạch sai → sửa todo list mà không cần abort.

### 6.5 `rerere` — Cứu tinh

```bash
git config --global rerere.enabled true
```

**Lý thuyết**: Rebase dài có thể gặp **cùng conflict** nhiều lần. `rerere` (REuse REcorded REsolution) ghi nhớ cách giải quyết và **tự động áp lại** khi gặp cùng pattern.

**Cơ chế**: `.git/rr-cache/` lưu hash của `(base, ours, theirs)` → resolution. Lần sau trùng → áp ngay.

**Ứng dụng**: Rebase branch 50 commit qua main mới → cùng conflict có thể gặp 5-10 lần. `rerere` tiết kiệm **hàng giờ**.

## 7. Kỹ thuật nâng cao

### 7.1 Tách commit (split)

**Mục tiêu**: Một commit lớn → nhiều commit nhỏ logic.

```bash
git rebase -i HEAD~3
# Đổi "pick" thành "edit" cho commit cần tách
```

Khi dừng tại commit:

```bash
# 1. Reset về trước commit, giữ thay đổi trong working tree
git reset HEAD^

# 2. Stage từng phần
git add -p file1.js              # interactive staging
git commit -m "part 1: refactor"

git add file2.js
git commit -m "part 2: add feature"

git add .
git commit -m "part 3: tests"

# 3. Tiếp tục
git rebase --continue
```

**Lý thuyết**: `git reset HEAD^` di chuyển HEAD về commit cha, giữ working tree **nguyên vẹn** (thay đổi của commit giờ là "unstaged"). Rồi bạn commit lại theo cách muốn.

### 7.2 Gộp commit không liền kề

**Vấn đề**: `squash`/`fixup` chỉ gộp vào commit **ngay trước**. Nếu muốn gộp commit cách xa:

```
pick a1b2c3d feat: A
pick e4f5g6h feat: B
pick i7j8k9l feat: C
pick m0n1o2p fix for A        ← muốn gộp vào A
```

**Giải pháp**: **Sắp xếp lại** — di chuyển `fix for A` ngay sau `A`, đổi thành `fixup`:

```
pick a1b2c3d feat: A
fixup m0n1o2p fix for A
pick e4f5g6h feat: B
pick i7j8k9l feat: C
```

**Cẩn thận**: Có thể conflict nếu `fix for A` phụ thuộc `B`/`C`. Kiểm tra kỹ.

### 7.3 Di chuyển commit giữa các branch

**Mục tiêu**: Commit `X` đang ở branch A, muốn chuyển sang branch B.

**Cách 1: Cherry-pick**

```bash
git switch branch-B
git cherry-pick <sha-X>

git switch branch-A
git rebase -i HEAD~N              # drop commit X
```

**Cách 2: Rebase --onto**

```bash
git rebase --onto branch-B <sha-truoc-X> branch-A
# Chỉ di chuyển commit X (và sau nó) sang branch-B
```

**Cách 3: Interactive rebase + reset**

```bash
git switch branch-A
git rebase -i HEAD~N              # drop X

git switch branch-B
git cherry-pick <sha-X-gốc>       # lấy từ reflog nếu cần
```

### 7.4 Sửa commit cũ mà không rebase toàn bộ

**Vấn đề**: Muốn sửa commit ở giữa lịch sử dài (100 commit).

**Giải pháp**:

```bash
# 1. Tìm commit
git log --oneline | grep "commit cần sửa"

# 2. Rebase từ commit đó
git rebase -i <sha-truoc-commit>

# 3. Đổi thành edit/reword, sửa, continue
```

**Lý thuyết**: Rebase sẽ **áp lại** tất cả commit sau commit bị sửa — có thể conflict nhiều. Đây là lý do **nên sửa sớm**, không để tích tụ.

### 7.5 `--rebase-merges` — Giữ cấu trúc merge

**Vấn đề**: Rebase mặc định **làm phẳng** merge commit. Nếu branch có merge (từ pull), cấu trúc DAG bị mất.

```bash
git rebase -i --rebase-merges main
```

**Todo list** phức tạp hơn — có `label`, `reset`, `merge`:

```
label onto

# Branch: feature-x
reset onto
pick a1b2c3d commit A
pick e4f5g6h commit B
label feature-x

# Merge feature-x vào main
reset onto
pick i7j8k9l commit C on main
merge -C abc1234 feature-x # Merge branch 'feature-x'
```

**Lý thuyết**: `--rebase-merges` dùng ngôn ngữ script để **tái tạo DAG** — giữ topology merge. Dùng khi bạn cần rebase branch có merge commit mà không muốn làm phẳng.

### 7.6 `--keep-base`

```bash
git rebase -i --keep-base main
```

**Hành động**: Giữ base cũ thay vì update lên đầu `main`. Chỉ dọn dẹp commit, không dịch chuyển.

**Lý thuyết**: Thông thường rebase dịch chuyển commit lên đầu base mới. `--keep-base` giữ nguyên base — commit chỉ bị biến đổi (squash, reword...) mà không đổi vị trí trong DAG.

**Ứng dụng**: Khi chỉ muốn dọn dẹp commit, không muốn cập nhật base (tránh conflict không cần thiết).

### 7.7 `--empty` — Xử lý commit rỗng

```bash
git rebase -i --empty=drop main      # bỏ commit rỗng (mặc định)
git rebase -i --empty=keep main      # giữ commit rỗng
git rebase -i --empty=ask main       # hỏi
```

**Lý thuyết**: Sau rebase, một commit có thể trở thành **rỗng** (nội dung đã có trong base mới — ví dụ commit fix trùng với fix đã merge). Git mặc định bỏ — có thể bất ngờ. `--empty=keep` giữ lại.

## 8. An toàn và phục hồi

### 8.1 `ORIG_HEAD` — Hủy nhanh

```bash
git reset --hard ORIG_HEAD
```

**Lý thuyết**: `ORIG_HEAD` = vị trí HEAD **trước thao tác nguy hiểm gần nhất** (rebase, merge, reset). Nó được Git tự động lưu.

**Ứng dụng**: Rebase xong, thấy sai → `git reset --hard ORIG_HEAD` = quay về trước rebase. **Nhanh hơn reflog**.

### 8.2 `reflog` — Cứu hộ toàn diện

```bash
git reflog
# f7g8h9i HEAD@{0}: rebase (finish): returning to refs/heads/main
# ...
# a1b2c3d HEAD@{5}: rebase (start): checkout main
# ...
# e5f6g7h HEAD@{10}: commit: feat: add login
```

**Ứng dụng**: Nếu `ORIG_HEAD` không đủ (đã qua nhiều thao tác), dùng reflog tìm SHA cụ thể.

```bash
git reset --hard HEAD@{5}      # quay về vị trí cụ thể trong reflog
git branch rescue <sha>        # tạo branch từ commit cũ
```

### 8.3 `--abort` — Hủy giữa chừng

```bash
git rebase --abort
```

**Hành động**: Hủy rebase, quay về trạng thái **trước khi bắt đầu**. Xóa `.git/rebase-merge/`.

**Lý thuyết**: `--abort` hoạt động **bất kỳ lúc nào** trong rebase — kể cả khi conflict, khi đang `edit`, khi đang `break`. Nó an toàn vì Git lưu trạng thái gốc trong `.git/rebase-merge/`.

### 8.4 `--quit` — Thoát không hủy

```bash
git rebase --quit
```

**Hành động**: Thoát rebase **mà không hủy** — giữ trạng thái hiện tại (HEAD detached tại commit đang áp), xóa `.git/rebase-merge/`.

**Lý thuyết**: `--quit` dùng khi bạn muốn **giữ kết quả một phần** — ví dụ: đã áp 3/5 commit, muốn dừng, giữ 3 commit đã áp, bỏ 2 commit còn lại.

**Khác `--abort`**: `--abort` = quay về trước rebase. `--quit` = giữ trạng thái hiện tại.

### 8.5 So sánh

| Lệnh          | Kết quả                    | Khi nào dùng                               |
| ------------- | -------------------------- | ------------------------------------------ |
| `--continue`  | Tiếp tục sau conflict/edit | Sau khi giải quyết                         |
| `--skip`      | Bỏ commit đang áp          | Commit không cần                           |
| `--abort`     | Quay về trước rebase       | Muốn hủy hoàn toàn                         |
| `--quit`      | Giữ trạng thái hiện tại    | Muốn dừng giữa chừng, giữ kết quả một phần |
| `--edit-todo` | Sửa todo list              | Thay đổi kế hoạch giữa chừng               |

## 9. Workflow thực tế — Các pattern phổ biến

### 9.1 Dọn dẹp trước khi mở PR

```bash
# Trước: nhiều commit lộn xộn
git log --oneline origin/main..HEAD
# m0n1o2p wip
# i7j8k9l fix typo
# e4f5g6h address review
# a1b2c3d feat: add login form

# Dọn dẹp
git rebase -i origin/main

# Editor: gộp thành 1 commit sạch
pick a1b2c3d feat: add login form
fixup e4f5g6h address review
fixup i7j8k9l fix typo
fixup m0n1o2p wip

# Kết quả: 1 commit duy nhất
git log --oneline origin/main..HEAD
# f7g8h9i feat: add login form

git push --force-with-lease
```

### 9.2 Chia feature lớn thành commit logic

```bash
# Trước: 1 commit khổng lồ
# a1b2c3d feat: add entire auth system

git rebase -i HEAD~1
# Đổi pick → edit

# Khi dừng:
git reset HEAD^
git add src/auth/login.js
git commit -m "feat(auth): add login form"
git add src/auth/logout.js
git commit -m "feat(auth): add logout"
git add src/auth/validation.js
git commit -m "feat(auth): add validation"
git add tests/
git commit -m "test(auth): add tests"

git rebase --continue
```

### 9.3 Reorder commit để logic hơn

```bash
git rebase -i HEAD~5
# Di chuyển commit theo thứ tự logic:
# 1. refactor trước
# 2. feature sau
# 3. test cuối
# 4. docs cuối cùng
```

### 9.4 Xóa commit nhạy cảm

```bash
# Lỡ commit .env có API key
git log --oneline
# m0n1o2p add .env
# i7j8k9l feat: add feature
# ...

git rebase -i HEAD~3
# Đổi pick → drop cho commit ".env"

# Kiểm tra
git log --all --oneline -- .env
# (không còn)

# Push force
git push --force-with-lease
```

**Cảnh báo lý thuyết**: Drop commit **không xóa** nội dung khỏi objects — vẫn cứu được qua reflog/`git fsck` trong ~30 ngày. Nếu đã push, người khác có thể đã clone. **Phải coi như secret đã lộ** — rotate key ngay, không chỉ drop commit.

### 9.5 Sửa commit gốc (root)

```bash
git rebase -i --root
# Editor hiện cả root commit
# pick/reword/edit/drop root
```

**Ứng dụng**: Sửa commit đầu tiên (thường là "Initial commit"). Hữu ích khi:
- Đổi message "Initial commit" thành gì đó có ý nghĩa.
- Gộp root với commit thứ hai.
- Xóa file nhạy cảm khỏi root.

**Lý thuyết**: `--root` đặc biệt vì không có `<base>` — Git áp lại **toàn bộ** lịch sử từ đầu. Có thể chậm với repo lớn.

### 9.6 Rebase tương tác qua nhiều commit với `--exec`

```bash
git rebase -i HEAD~10 --exec "npm test && npm run lint"
```

**Lý thuyết**: Sau **mỗi** commit được áp, chạy test + lint. Nếu fail → dừng. Đảm bảo **mỗi commit đều xanh** — nguyên tắc "testable history".

**Ứng dụng**: Trước khi push feature branch, đảm bảo mọi commit đều build/test được — cho `git bisect` hiệu quả.

## 10. Tổng kết lý thuyết

### Bảng tổng hợp lệnh

| Lệnh                    | Chức năng        | Đặc điểm                          |
| ----------------------- | ---------------- | --------------------------------- |
| `pick`                  | Giữ commit       | Mặc định                          |
| `reword`                | Sửa message      | Mở editor message                 |
| `edit`                  | Dừng để amend    | Toàn quyền với commit             |
| `squash`                | Gộp, giữ message | Mở editor kết hợp                 |
| `fixup`                 | Gộp, bỏ message  | Không editor                      |
| `drop`                  | Xóa              | Commit không có trong history mới |
| `exec`                  | Chạy lệnh        | Fail → dừng                       |
| `break`                 | Dừng thủ công    | Chờ bạn thao tác                  |
| `label`/`reset`/`merge` | Script hóa DAG   | Cho `--rebase-merges`             |

### Nguyên tắc vàng

1. **Interactive rebase = cherry-pick tuần tự có kiểm soát** — hiểu điều này giải thích mọi hành vi.
2. **Thứ tự dòng = thứ tự áp commit** — sắp xếp lại là công cụ mạnh.
3. **`ours`/`theirs` đảo ngược trong rebase** — `theirs` = code của bạn.
4. **`--autosquash` + `fixup!`** — workflow hiện đại, commit thoải mái, dọn tự động.
5. **`--exec` cho test-driven history** — mỗi commit đều xanh.
6. **`rerere` cho rebase dài** — tiết kiệm hàng giờ conflict.
7. **`ORIG_HEAD`/`reflog` là phao cứu sinh** — commit "mất" vẫn cứu được.
8. **Không rebase commit đã push lên shared branch** — quy tắc bất biến.
9. **Dọn dẹp trước khi mở PR** — lịch sử sạch, dễ review, dễ bisect.
10. **`--force-with-lease --force-if-includes`** — không bao giờ `--force`.

### Điểm mấu chốt cần nhớ

**Interactive rebase là công cụ "biên tập lịch sử"** — nó cho phép bạn viết lại quá khứ một cách có kiểm soát. Về bản chất, nó là **một chuỗi cherry-pick tuần tự** theo kịch bản bạn viết trong todo list. Mỗi commit được "replay" — tạo SHA mới với parent mới, giữ author nhưng đổi committer. Đây là lý do nó **viết lại lịch sử** và **không được dùng trên commit đã push**.

Sức mạnh của nó nằm ở **tính linh hoạt**: bạn có thể kết hợp `pick`/`squash`/`edit`/`drop`/`exec`/`break` để tạo ra bất kỳ lịch sử nào mong muốn. Nhưng đi kèm là **trách nhiệm**: mỗi thao tác đều có thể mất commit nếu sai. Vì vậy, **luôn hiểu rõ todo list trước khi lưu**, **luôn kiểm tra sau khi rebase**, và **luôn nhớ `ORIG_HEAD`/`reflog`** — phao cứu sinh khi mọi thứ sai.
