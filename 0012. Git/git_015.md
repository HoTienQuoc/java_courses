# Git Cherry-pick — Moving Commits Between Branches: Giải thích lý thuyết chi tiết

---

## 1. Bản chất: Cherry-pick thực sự làm gì?

### 1.1 Định nghĩa cốt lõi

**`git cherry-pick`** là lệnh **"nhặt" một commit cụ thể** từ branch này và **áp dụng nó** lên branch hiện tại — như thể commit đó được viết ngay tại đây.

> **Điểm lý thuyết quan trọng nhất**: Cherry-pick **KHÔNG di chuyển commit** — nó **tạo commit mới** với nội dung tương tự. Commit gốc **vẫn tồn tại** ở branch cũ với SHA cũ. Commit mới ở branch hiện tại có **SHA khác hoàn toàn**.

### 1.2 Tên gọi — Ẩn dụ "nhặt quả anh đào"

"Hái một quả anh đào từ cây này, gắn lên cây khác" — hình ảnh này mô tả chính xác:
- **Cây nguồn** (source branch): cây có quả (commit) bạn muốn.
- **Cây đích** (current branch): cây bạn muốn gắn quả vào.
- **Quả** (commit): được "nhặt" — nhưng thực chất là **bản sao** (không phải di chuyển).

### 1.3 Cơ chế bên trong — "Tái tạo qua diff"

Cherry-pick **không copy** commit object. Nó thực hiện **ba bước**:

```
Bước 1: Tính diff
  diff(commit, parent_of_commit) → patch
  → Patch chứa "commit này đã thay đổi gì so với cha nó"

Bước 2: Áp patch
  Áp patch lên HEAD hiện tại (branch đích)
  → Giống như "replay" thay đổi

Bước 3: Tạo commit mới
  Commit mới với:
    - Tree = HEAD + patch (nội dung sau khi áp)
    - Parent = HEAD hiện tại
    - Author = author của commit gốc (GIỮ NGUYÊN)
    - Committer = BẠN (thay đổi)
    - Message = message của commit gốc
    - SHA = MỚI hoàn toàn (vì parent khác, committer khác)
```

**Minh họa**:

```
Trước cherry-pick:
  A ← B ← C ← D   (main)
       ↑
       X ← Y       (feature — commit X, Y muốn nhặt)

git switch main
git cherry-pick X

Sau cherry-pick:
  A ← B ← C ← D ← X'   (main, HEAD)
       ↑
       X ← Y            (feature — X vẫn còn nguyên!)

  X' = commit mới, nội dung giống X, parent = D
```

**Điểm mấu chốt**:
- `X'` có SHA **khác** `X` — vì parent khác (`D` vs `B`) và committer khác.
- `X` vẫn tồn tại ở branch `feature` — không bị ảnh hưởng.
- Branch `feature` không đổi — vẫn ở `Y`.

### 1.4 Author giữ, committer đổi — Lý thuyết attribution

```bash
git log --format="%h author=%an <%ae> %ad | committer=%cn <%ce> %cd"
```

Sau cherry-pick:
```
X' author=Alice <alice@x.com> 2024-01-01 | committer=Bob <bob@x.com> 2024-01-15
```

- **Author**: Alice (người viết code gốc) — **giữ nguyên**.
- **Committer**: Bob (người cherry-pick) — **thay đổi**.

**Lý thuyết**: Git phân biệt **author** (người tạo nội dung) và **committer** (người tạo commit object). Cherry-pick **bảo toàn attribution** cho tác giả gốc — quan trọng cho audit và ghi công.

**Hệ quả**: `git blame` sẽ hiển thị **author gốc** (Alice), không phải Bob — dù Bob là người cherry-pick.

## 2. Cú pháp và các biến thể

### 2.1 Cú pháp cơ bản

```bash
git cherry-pick <commit>              # 1 commit
git cherry-pick <commit1> <commit2>   # nhiều commit (theo thứ tự)
git cherry-pick <start>..<end>        # range (KHÔNG bao gồm <start>)
git cherry-pick <start>^..<end>       # range (BAO GỒM <start>)
git cherry-pick <branch>              # commit cuối của branch
git cherry-pick -n <commit>           # không commit (--no-commit)
git cherry-pick -x <commit>           # ghi lại SHA gốc vào message
git cherry-pick -e <commit>           # mở editor để sửa message
git cherry-pick --continue            # tiếp tục sau conflict
git cherry-pick --abort               # hủy cherry-pick
git cherry-pick --skip                # bỏ qua commit đang conflict
```

### 2.2 Range `A..B` vs `A^..B`

**Điểm tinh tế quan trọng**:

```bash
git cherry-pick A..B           # nhặt commit (A, B] — KHÔNG có A
git cherry-pick A^..B          # nhặt commit [A, B] — CÓ A
```

**Lý thuyết**: `A..B` = `reachable(B) \ reachable(A)` — commit có ở B nhưng không ở A. Vì `A` thuộc `reachable(A)` → bị loại. `A^` = parent của A → `A^..B` bao gồm A.

**Ví dụ**:
```
A ← B ← C ← D   (feature)

git cherry-pick B..D
# → Nhặt C, D (không có B)

git cherry-pick B^..D
# → Nhặt B, C, D (có B)
```

**Cẩn thận**: `A..B` **không đảm bảo thứ tự** — Git áp theo thứ tự **topological** (cha trước con). Nếu B, C, D có quan hệ cha-con → đúng thứ tự. Nếu không → có thể conflict.

### 2.3 `-x` — Ghi lại nguồn gốc

```bash
git cherry-pick -x a1b2c3d
```

**Hành động**: Thêm dòng vào message commit mới:

```
feat: add login form

(cherry picked from commit a1b2c3d4e5f6...)
```

**Lý thuyết**: `-x` ghi lại **SHA gốc** — giúp **audit trail**: biết commit này được cherry-pick từ đâu. **Khuyến nghị** khi backport (cherry-pick từ main về release branch).

**Hạn chế**: Nếu cherry-pick nhiều lần (cherry-pick của cherry-pick) → dòng `(cherry picked from ...)` có thể **chồng chất** — khó đọc.

**Git chính thức khuyến nghị**: Dùng `-x` khi cherry-pick giữa **các branch public** (backport), không dùng cho branch cá nhân.

### 2.4 `-n` / `--no-commit` — Áp mà không commit

```bash
git cherry-pick -n a1b2c3d
```

**Hành động**: Áp **diff** của commit vào Working Tree + Index, nhưng **không tạo commit**.

**Ứng dụng**:
- **Gộp nhiều commit** thành một: `git cherry-pick -n A B C && git commit -m "gộp"`.
- **Sửa trước khi commit**: áp, sửa file, rồi commit.
- **Kiểm tra trước**: áp thử, xem diff, rồi quyết định.

**Lưu ý**: Sau `-n`, bạn có thể `git reset` để bỏ, hoặc `git checkout -- .` để hủy hoàn toàn.

### 2.5 `-e` / `--edit` — Sửa message

```bash
git cherry-pick -e a1b2c3d
```

**Hành động**: Áp commit, mở editor để sửa message. Nội dung giữ nguyên.

**Ứng dụng**: Khi message gốc không phù hợp với context mới (ví dụ: message tham chiếu issue của repo cũ).

### 2.6 `--mainline` — Cherry-pick merge commit

```bash
git cherry-pick -m 1 <merge-commit>
```

**Vấn đề**: Merge commit có **nhiều parent**. Cherry-pick cần biết "coi parent nào là base" để tính diff.

**`-m <n>`**: Chọn parent thứ `n` làm base. Thường `-m 1` = parent đầu tiên (branch chính của merge).

**Lý thuyết**: Merge commit `M` có parent 1 (main) và parent 2 (feature). `cherry-pick -m 1 M` = "áp **thay đổi của feature** (từ parent 1 đến M) lên branch hiện tại".

**Ví dụ**:
```
      A ← B ← M   (main)
           ↗
      X ← Y       (feature)

git cherry-pick -m 1 M
# → Áp diff(Y, M) lên branch hiện tại
# → Tức "nhặt toàn bộ thay đổi của feature"
```

**Cẩn thận**: `--mainline` **hiếm dùng** và dễ nhầm. Đa số trường hợp, cherry-pick **commit thường** (không phải merge) an toàn hơn.

## 3. Conflict trong cherry-pick

### 3.1 Tại sao conflict?

Cherry-pick áp **diff** (thay đổi của commit) lên **context khác** (branch đích). Nếu context xung quanh khác → **không thể áp sạch** → conflict.

**Ví dụ**:

```
Commit gốc (feature):
  function calculate(a, b) {
    return a + b;              ← commit sửa dòng này
  }

Branch đích (main):
  function calculate(a, b, c) {
    return a + b + c;          ← dòng đã khác!
  }
```

Cherry-pick cố áp "return a + b" → **conflict** vì dòng hiện tại khác.

### 3.2 Các loại conflict

| Loại                 | Nguyên nhân                                         |
| -------------------- | --------------------------------------------------- |
| **Content conflict** | Cùng vùng bị sửa khác nhau                          |
| **Modify/Delete**    | File bị sửa ở nguồn, bị xóa ở đích (hoặc ngược lại) |
| **Add/Add**          | Cả hai thêm file cùng tên khác nội dung             |
| **Rename**           | File bị đổi tên ở đích nhưng không ở nguồn          |

### 3.3 Quy trình giải quyết

```bash
git cherry-pick a1b2c3d
# CONFLICT (content): Merge conflict in file.js
# error: could not apply a1b2c3d... feat: something

# Bước 1: Xem trạng thái
git status
# You are currently cherry-picking commit a1b2c3d.
#   (fix conflicts and run "git cherry-pick --continue")
#   (use "git cherry-pick --skip" to skip this patch)
#   (use "git cherry-pick --abort" to cancel the cherry-pick operation)

# Bước 2: Sửa file conflict
vim file.js
# Chọn/ghép, xóa marker <<<<<<< ======= >>>>>>>

# Bước 3: Đánh dấu
git add file.js

# Bước 4: Tiếp tục
git cherry-pick --continue
```

### 3.4 `ours`/`theirs` trong cherry-pick

**Điểm quan trọng** — giống rebase:

```bash
# Trong cherry-pick conflict:
git checkout --ours <file>    # = HEAD hiện tại (branch đích)
git checkout --theirs <file>  # = commit đang cherry-pick
```

**So sánh**:
- **Merge**: `ours` = branch hiện tại; `theirs` = branch merge.
- **Cherry-pick**: `ours` = HEAD (branch đích); `theirs` = commit nguồn.
- **Rebase**: `ours` = base mới; `theirs` = commit đang áp.

**Cách nhớ cherry-pick**: `theirs` = **commit bạn đang nhặt** — chính là code của commit nguồn.

### 3.5 Các lựa chọn khi conflict

```bash
git cherry-pick --continue     # tiếp tục sau khi giải quyết
git cherry-pick --skip         # bỏ qua commit đang conflict
git cherry-pick --abort        # hủy toàn bộ, quay về trước
git cherry-pick --quit         # thoát cherry-pick nhưng giữ trạng thái hiện tại
```

**`--skip` — Lý thuyết**: Bỏ qua commit đang áp — commit đó **không có trong branch đích**. Dùng khi commit đã được áp bằng cách khác (ví dụ: đã có sẵn từ merge trước đó).

**`--abort`**: Quay về trạng thái **trước khi bắt đầu cherry-pick** — kể cả khi đã áp thành công nhiều commit trước đó trong range. Toàn bộ bị hủy.

**`--quit`**: Thoát cherry-pick nhưng **giữ** các commit đã áp thành công — chỉ dừng, không hủy.

### 3.6 Conflict với range

```bash
git cherry-pick A..D           # nhặt B, C, D
# → Có thể conflict khi áp B, C, hoặc D

git cherry-pick --continue     # tiếp tục từng commit
# → Mỗi commit conflict → giải quyết → continue
```

**Lý thuyết**: Cherry-pick range = **chuỗi cherry-pick tuần tự**. Conflict xảy ra **từng commit một** — giống rebase, không giống merge (một lần).

## 4. Ứng dụng thực tế

### 4.1 Backport hotfix — Ứng dụng phổ biến nhất

**Kịch bản**: Bug nghiêm trọng trên production (`release/1.5`), đã fix trên `main`. Cần áp fix về `release/1.5` mà không merge toàn bộ `main`.

```bash
# Trên main, đã có commit fix
git log --oneline main
# e5f6g7h fix: XSS vulnerability in login
# d5e6f7g feat: new feature (không muốn backport)
# ...

# Backport về release
git switch release/1.5
git cherry-pick -x e5f6g7h
# → Áp fix XSS lên release/1.5, với -x ghi lại SHA gốc

# Push
git push origin release/1.5
```

**Lý thuyết**: 
- `-x` ghi lại nguồn gốc → audit trail.
- **Không** merge `main` → tránh kéo theo feature mới.
- **Không** rebase `release` lên `main` → tránh viết lại lịch sử release.

### 4.2 Nhặt commit từ branch thử nghiệm

**Kịch bản**: Có branch `experiment` thử nhiều thứ. Chỉ 1-2 commit trong đó hữu ích. Muốn nhặt sang `main`.

```bash
git switch main
git cherry-pick a1b2c3d              # nhặt commit hữu ích
git cherry-pick -n e4f5g6h           # nhặt thử, xem diff
git diff                              # kiểm tra
# ... OK → commit
git commit -m "feat: từ experiment"
```

### 4.3 Cứu commit từ detached HEAD

```bash
git checkout a1b2c3d
# ... commit ...
# ... checkout main → commit mất (unreachable)

git cherry-pick a1b2c3d                # nếu nhớ SHA
# hoặc
git reflog                              # tìm SHA
git cherry-pick <sha>
```

### 4.4 Di chuyển commit sang branch khác

**Kịch bản**: Commit gần nhất thực ra thuộc branch `feature`, không phải `main`.

```bash
# Đang ở main, lỡ commit
git log --oneline
# a1b2c3d feat: thuộc feature (lỡ commit trên main)
# ...

# Cách 1: Cherry-pick + reset
git switch feature
git cherry-pick a1b2c3d                # áp lên feature

git switch main
git reset --hard HEAD~1                # bỏ commit trên main

# Cách 2: Cherry-pick với -x (nếu cần audit)
git switch feature
git cherry-pick -x a1b2c3d
```

**Lý thuyết**: Đây là "di chuyển commit" **thực sự** — commit cũ bị bỏ (reset), commit mới được tạo ở branch đích. SHA thay đổi, nhưng nội dung được bảo toàn.

### 4.5 Gộp nhiều commit qua `-n`

```bash
git switch main
git cherry-pick -n a1b2c3d e4f5g6h i7j8k9l
# → Áp cả 3 vào working tree, chưa commit

git status
# Changes to be committed: ...  (cả 3 thay đổi)

git commit -m "feat: gộp 3 commit từ feature"
# → 1 commit duy nhất chứa cả 3
```

**Lý thuyết**: `-n` + commit = "squash cherry-pick" — gộp nhiều commit từ nguồn thành một ở đích.

### 4.6 Cherry-pick merge commit

```bash
git cherry-pick -m 1 <merge-commit>
```

**Ứng dụng**: Hiếm. Thường dùng khi merge commit chứa **toàn bộ feature** và bạn muốn "nhặt" toàn bộ feature đó (từ parent chính).

**Cẩn thận**: Thường **không** phải ý muốn. Nếu muốn nhặt toàn bộ feature → merge hoặc rebase branch đó. Cherry-pick merge commit dễ gây conflict và mất commit con.

## 5. Cherry-pick vs Merge vs Rebase

### 5.1 Bảng so sánh toàn diện

| Tiêu chí                   | Cherry-pick             | Merge              | Rebase                      |
| -------------------------- | ----------------------- | ------------------ | --------------------------- |
| **Phạm vi**                | 1+ commit cụ thể        | Toàn bộ branch     | Toàn bộ branch              |
| **Tạo commit mới**         | ✅ (SHA mới)             | 1 merge commit     | N commit (SHA mới)          |
| **Commit gốc**             | Giữ nguyên              | Giữ nguyên         | Trở thành unreachable       |
| **Lịch sử đích**           | Tuyến tính + commit mới | Phân nhánh         | Tuyến tính                  |
| **Viết lại lịch sử nguồn** | ❌                       | ❌                  | ✅ (nếu rebase branch nguồn) |
| **Conflict**               | Có thể                  | Có thể             | Có thể                      |
| **Chọn lọc commit**        | ✅                       | ❌ (toàn bộ)        | ✅ (interactive)             |
| **Ứng dụng**               | Backport, hotfix        | Feature hoàn chỉnh | Dọn lịch sử cá nhân         |

### 5.2 Khi nào chọn cái nào?

**Cherry-pick**:
- **Backport** hotfix từ main về release.
- Nhặt **1-2 commit** từ branch thử nghiệm.
- Cứu commit từ detached HEAD/reflog.
- Di chuyển commit giữa branch không liên quan.

**Merge**:
- Branch hoàn chỉnh cần tích hợp **toàn bộ**.
- Branch **shared** (main, develop).
- Muốn giữ **topology** (audit trail).
- Commit đã **push**.

**Rebase**:
- Branch **cá nhân**, muốn lịch sử **tuyến tính**.
- Dọn dẹp commit trước khi merge.
- Commit **chưa push**.

### 5.3 "Cherry-pick = Rebase một phần"

**Lý thuyết sâu**: Cherry-pick **chính là** rebase nhưng chỉ chọn **một số commit** thay vì toàn bộ range.

```
Rebase:      áp lại TẤT CẢ commit trong (base, HEAD]
Cherry-pick: áp lại MỘT SỐ commit cụ thể
```

Cả hai đều dùng **cơ chế replay diff** và **tạo commit mới (SHA mới)**.

**Hệ quả**: Cherry-pick **có cùng rủi ro** với rebase — tạo duplicate commits (mục 6).

## 6. Cạm bẫy lớn nhất: Duplicate commits

### 6.1 Vấn đề

Cherry-pick tạo commit **SHA mới**. Nếu sau này bạn **merge** branch nguồn vào branch đích → Git thấy **hai commit khác SHA** với **nội dung giống nhau** → **duplicate commits** trong lịch sử.

**Kịch bản**:

```
1. Feature có commit X (fix bug)
2. Cherry-pick X → main có X' (SHA khác, nội dung giống)
3. Sau này merge feature → main

Kết quả:
  main: ... ← X' ← M (merge)
                  /
  feature: ... ← X

Git thấy X và X' là HAI commit khác nhau (SHA khác)
→ Cả hai đều trong lịch sử main
→ Duplicate nội dung
```

**Hệ quả**:
- Lịch sử **rối** — khó đọc.
- `git log` hiển thị **hai commit** cho cùng một thay đổi.
- Có thể gây conflict khi merge sau này (vì nội dung đã có).

### 6.2 `git cherry` — Phát hiện duplicate

```bash
git cherry -v main feature
```

**Hành động**: So sánh commit giữa hai branch **dựa trên patch-id** (không phải SHA). Output:

```
+ a1b2c3d4... feat: new feature          ← chưa có ở main
- e5f6g7h8... fix: XSS vulnerability     ← đã có ở main (dạng khác SHA)
```

- `+` = commit **chưa** có tương đương ở branch kia.
- `-` = commit **đã** có tương đương (cùng patch-id).

**Lý thuyết**: `git cherry` tính **patch-id** — hash của **diff nội dung** (không phải SHA commit). Hai commit có cùng patch-id → "tương đương" về nội dung → `git cherry` đánh dấu `-`.

### 6.3 `patch-id` — "SHA của nội dung"

```bash
git patch-id
```

**Lý thuyết**:
- **Commit SHA** = hash của (tree + parent + author + committer + message).
- **Patch-id** = hash của **diff** (chỉ nội dung thay đổi).

Hai commit có cùng nội dung nhưng khác SHA → **cùng patch-id**. Đây là cơ sở để Git phát hiện "đã cherry-pick chưa".

### 6.4 Cách tránh duplicate

**Cách 1: Không merge branch đã cherry-pick**

```bash
# Sau khi cherry-pick từ feature sang main
# → KHÔNG merge feature vào main nữa
# → Hoặc: merge với --no-commit, xử lý conflict (X đã có dạng X')
```

**Cách 2: Dùng `-x`**

```bash
git cherry-pick -x a1b2c3d
```

`-x` ghi lại SHA gốc → người review thấy `(cherry picked from ...)` → biết đây là bản sao.

**Cách 3: Rebase thay cherry-pick cho nhiều commit**

Nếu muốn **toàn bộ** branch → dùng rebase (không tạo duplicate khi merge sau này, vì rebase thay thế lịch sử).

**Cách 4: `git rebase --onto` cho range**

```bash
# Di chuyển range commit từ branch A sang branch B
git rebase --onto B <base> A
```

Không tạo duplicate — vì commit cũ trở thành unreachable (branch A được rebase).

## 7. Cherry-pick nâng cao

### 7.1 `--strategy` và `--strategy-option`

```bash
git cherry-pick -X theirs a1b2c3d         # conflict → auto chọn theirs
git cherry-pick -X ours a1b2c3d           # conflict → auto chọn ours
git cherry-pick -X patience a1b2c3d       # patience diff
git cherry-pick -s recursive a1b2c3d      # chiến lược recursive
```

**Lý thuyết**: Giống merge/rebase — `-X` áp dụng cho **conflict** trong quá trình cherry-pick.

**Cẩn thận**: `-X theirs` có thể **mất thay đổi** — chỉ dùng khi chắc chắn.

### 7.2 `--ff` — Fast-forward nếu có thể

```bash
git cherry-pick --ff a1b2c3d
```

**Lý thuyết**: Nếu commit được cherry-pick **chính là** commit kế tiếp (HEAD là parent của nó) → **fast-forward** thay vì tạo commit mới.

**Ứng dụng**: Hiếm — dùng khi cherry-pick commit liền kề (không tạo SHA mới).

### 7.3 `--allow-empty` — Cho commit rỗng

```bash
git cherry-pick --allow-empty a1b2c3d
```

**Lý thuyết**: Cherry-pick một commit mà **diff rỗng** (khi áp lên branch đích) → mặc định **từ chối** (vì không có gì thay đổi). `--allow-empty` cho phép tạo commit rỗng.

**Ứng dụng**: Khi commit gốc chỉ thay đổi thứ đã có ở branch đích — muốn giữ **dấu vết** trong lịch sử.

### 7.4 `--empty` — Xử lý commit rỗng

```bash
git cherry-pick --empty=drop a1b2c3d      # bỏ commit rỗng
git cherry-pick --empty=keep a1b2c3d      # giữ commit rỗng
git cherry-pick --empty=stop a1b2c3d      # dừng, hỏi
```

**Lý thuyết**: Tương tự rebase `--empty` — xử lý trường hợp commit trở thành rỗng sau khi áp.

### 7.5 `--rerere-autoupdate`

```bash
git cherry-pick --rerere-autoupdate a1b2c3d
```

**Lý thuyết**: Nếu `rerere` đã ghi nhớ resolution → tự động áp và **tự động commit** (không cần `git add` + `--continue`).

**Ứng dụng**: Cherry-pick nhiều commit có cùng pattern conflict → `rerere` tự giải quyết.

### 7.6 Cherry-pick với submodule

```bash
git cherry-pick a1b2c3d
# → Submodule pointer được áp theo commit
# → Cần update submodule:
git submodule update --init --recursive
```

### 7.7 Cherry-pick trong detached HEAD

```bash
git checkout a1b2c3d
git cherry-pick e4f5g6h
# → Tạo commit mới trong detached HEAD
# → Cần tạo branch ngay để không mất:
git switch -c rescue
```

## 8. Phục hồi và hủy

### 8.1 `--abort` — Hủy toàn bộ

```bash
git cherry-pick --abort
```

**Hành động**: Quay về trạng thái **trước khi bắt đầu cherry-pick**. Xóa `.git/CHERRY_PICK_HEAD` và `.git/sequencer/`.

**Lý thuyết**: `--abort` hoạt động **bất kỳ lúc nào** — kể cả khi đã áp thành công nhiều commit trong range. Toàn bộ bị hủy.

### 8.2 `--quit` — Dừng, giữ kết quả một phần

```bash
git cherry-pick --quit
```

**Hành động**: Dừng cherry-pick, **giữ** các commit đã áp thành công. Xóa trạng thái cherry-pick (`.git/CHERRY_PICK_HEAD`).

**Khác `--abort`**: `--abort` = quay về trước; `--quit` = giữ kết quả hiện tại.

### 8.3 Reflog — Cứu sau cherry-pick

```bash
git cherry-pick a1b2c3d
# ... không ưng ý ...

git reflog
# ... HEAD@{0}: cherry-pick: feat: something
# ... HEAD@{1}: commit: feat: trước đó

git reset --hard HEAD@{1}              # hủy cherry-pick
```

**Lý thuyết**: Cherry-pick tạo commit mới → reflog ghi lại. `HEAD@{1}` = trước cherry-pick.

### 8.4 `CHERRY_PICK_HEAD` — Trạng thái

```bash
cat .git/CHERRY_PICK_HEAD
# SHA của commit đang cherry-pick (khi conflict)
```

**Lý thuyết**: Khi conflict, Git lưu SHA trong `.git/CHERRY_PICK_HEAD`. Xóa file này = thoát trạng thái (tương đương `--quit`).

## 9. Cherry-pick và workflow team

### 9.1 Backport workflow chuẩn

```bash
# 1. Fix trên main
git switch main
git commit -m "fix: critical bug"       # a1b2c3d

# 2. Merge PR vào main
# (qua PR review)

# 3. Backport về release
git switch release/1.5
git cherry-pick -x a1b2c3d
# → Conflict? Giải quyết, --continue

# 4. Push
git push origin release/1.5

# 5. Nếu release/1.5 có PR protection:
git switch -c backport/critical-bug
git cherry-pick -x a1b2c3d
git push -u origin backport/critical-bug
# → Mở PR vào release/1.5
```

**Lý thuyết**: `-x` là **bắt buộc** trong backport — audit trail quan trọng cho compliance.

### 9.2 Hotfix workflow

```
main (production) ← hotfix branch ← cherry-pick từ develop
```

**Kịch bản**: Bug phát hiện trên production. Fix trên `main` (hoặc hotfix branch), rồi cherry-pick về các release branch đang support.

### 9.3 Tránh cherry-pick khi có thể merge/rebase

**Nguyên tắc**: Cherry-pick chỉ dùng khi **không thể** merge/rebase. Nếu có thể:

- **Merge** → an toàn nhất cho shared branch.
- **Rebase** → sạch nhất cho branch cá nhân.
- **Cherry-pick** → chỉ khi cần **chọn lọc** commit cụ thể.

### 9.4 Code review cho cherry-pick

**Lý thuyết**: Cherry-pick **không được miễn review** — vì:
- Diff áp lên context khác → có thể gây bug mới.
- Conflict resolution có thể sai.
- Cần đảm bảo test pass trên branch đích.

**Best practice**: Cherry-pick qua PR (không push trực tiếp), đặc biệt cho release branch.

## 10. Các tình huống đặc biệt

### 10.1 Cherry-pick commit đã có (duplicate)

```bash
git cherry-pick a1b2c3d
# The previous cherry-pick is now empty, possibly due to conflict resolution.
# If you wish to commit it anyway, use:
#     git commit --allow-empty
```

**Nguyên nhân**: Commit đã có ở branch đích (cùng nội dung) → diff rỗng.

**Giải pháp**: `git cherry-pick --skip` (bỏ qua) hoặc `--allow-empty` (giữ dấu vết).

### 10.2 Cherry-pick commit gốc (root)

```bash
git cherry-pick --root
# → Cherry-pick root commit của branch hiện tại
```

**Lý thuyết**: Root commit **không có parent** → diff = toàn bộ nội dung. Cherry-pick root = "copy toàn bộ file của root commit".

**Ứng dụng**: Hiếm — thường dùng để "khởi tạo" branch mới từ root.

### 10.3 Cherry-pick file cụ thể từ commit

**Vấn đề**: Cherry-pick áp **toàn bộ** commit. Nếu chỉ muốn 1 file?

**Giải pháp**:
```bash
# Cách 1: checkout file từ commit
git checkout a1b2c3d -- path/to/file.js

# Cách 2: cherry-pick -n + reset file không cần
git cherry-pick -n a1b2c3d
git reset HEAD -- path/to/unwanted.js
git checkout -- path/to/unwanted.js
git commit -m "chỉ lấy file cần"
```

**Lý thuyết**: `git checkout <commit> -- <path>` = "lấy file tại commit đó, đặt vào working tree + index". Đây là "cherry-pick file" thực sự.

### 10.4 Cherry-pick nhiều commit không liền kề

```bash
git cherry-pick a1b2c3d e4f5g6h i7j8k9l
# → Áp theo thứ tự đã liệt kê
```

**Lý thuyết**: Git áp **theo thứ tự argument** (không phải thứ tự topological). Nếu commit sau phụ thuộc commit trước → phải đúng thứ tự.

**Cẩn thận**: Nếu commit không liên quan → OK. Nếu có quan hệ cha-con → phải theo thứ tự cha trước.

### 10.5 Cherry-pick trong monorepo

```bash
git cherry-pick a1b2c3d
# → Áp toàn bộ diff (có thể chạm nhiều package)

# Hoặc chỉ lấy thay đổi của 1 package:
git checkout a1b2c3d -- packages/foo/
```

**Lý thuyết**: Monorepo thường có commit chạm nhiều package. Cherry-pick toàn bộ có thể conflict ở package không liên quan. `checkout -- <path>` an toàn hơn cho trường hợp này.

### 10.6 Cherry-pick với binary file

```bash
git cherry-pick a1b2c3d
# CONFLICT (binary): Merge conflict in logo.png
```

**Giải pháp**: Chọn ours/theirs (không thể merge binary):
```bash
git checkout --theirs logo.png       # lấy từ commit đang cherry-pick
git add logo.png
git cherry-pick --continue
```

### 10.7 Cherry-pick và LFS

```bash
# Nếu repo dùng Git LFS:
git lfs install
git cherry-pick a1b2c3d
# → LFS tự xử lý
```

## 11. Tổng kết lý thuyết

### Bảng tổng hợp

| Khái niệm                           | Định nghĩa cốt lõi                            | Lưu ý                        |
| ----------------------------------- | --------------------------------------------- | ---------------------------- |
| **Cherry-pick**                     | Áp diff của commit cụ thể lên branch hiện tại | **Tạo commit mới** (SHA mới) |
| **Commit gốc**                      | Vẫn tồn tại ở branch nguồn                    | Không bị di chuyển           |
| **Author/Committer**                | Author giữ, committer đổi                     | Bảo toàn attribution         |
| **`-x`**                            | Ghi SHA gốc vào message                       | Khuyến nghị cho backport     |
| **`-n`**                            | Áp không commit                               | Gộp nhiều commit             |
| **`-m 1`**                          | Cherry-pick merge commit                      | Hiếm dùng, dễ nhầm           |
| **Conflict**                        | Xảy ra khi context khác                       | `ours`=đích, `theirs`=nguồn  |
| **`--continue`/`--abort`/`--skip`** | Xử lý conflict                                | Giống rebase                 |
| **Duplicate commits**               | Commit trùng nội dung, khác SHA               | Cạm bẫy lớn nhất             |
| **`git cherry`**                    | Phát hiện duplicate (patch-id)                | `+` chưa có, `-` đã có       |
| **`patch-id`**                      | Hash của diff, không phải SHA                 | Cơ sở phát hiện trùng        |

### Nguyên tắc vàng

1. **Cherry-pick = tạo commit mới**, không di chuyển commit — SHA luôn thay đổi.
2. **Author giữ, committer đổi** — attribution được bảo toàn.
3. **Luôn dùng `-x` cho backport** — audit trail quan trọng.
4. **`ours`/`theirs` trong cherry-pick**: `theirs` = commit nguồn.
5. **Duplicate commits** — cạm bẫy lớn nhất; dùng `git cherry` để kiểm tra.
6. **Không merge branch đã cherry-pick** — nếu merge, xử lý conflict cẩn thận.
7. **Cherry-pick không miễn review** — qua PR, đặc biệt cho release branch.
8. **`--abort` khi rối** — dừng lại, xem lại, rồi quyết định.
9. **Reflog cứu được** — commit gốc + commit cherry-pick đều trong reflog.
10. **Chọn merge/rebase khi có thể** — cherry-pick chỉ khi cần **chọn lọc**.

### Điểm mấu chốt cần nhớ

**Cherry-pick là "rebase một phần"** — nó áp **diff** của commit cụ thể lên branch hiện tại, tạo **commit mới** với SHA khác. Về bản chất, nó dùng **cùng cơ chế replay** như rebase, nhưng chỉ chọn **một số commit** thay vì toàn bộ range.

**Ứng dụng chính**: **Backport** (hotfix từ main về release) và **chọn lọc commit** (nhặt 1-2 commit hữu ích từ branch thử nghiệm). Đây là công cụ **không thể thay thế** khi cần "di chuyển" commit giữa các branch **không liên quan trực tiếp**.

**Cạm bẫy lớn nhất**: **Duplicate commits** — khi cherry-pick rồi merge branch nguồn, Git thấy hai commit khác SHA cùng nội dung. `git cherry` (dựa trên patch-id) giúp phát hiện. Và `-x` giúp ghi lại nguồn gốc để audit.

**Nguyên tắc chọn lựa**: Merge cho **toàn bộ branch** (an toàn, giữ topology). Rebase cho **dọn lịch sử cá nhân** (tuyến tính). Cherry-pick cho **chọn lọc commit cụ thể** (backport, hotfix). Mỗi công cụ có chỗ đứng — hiểu rõ bản chất để chọn đúng.
