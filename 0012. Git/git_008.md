# PHẦN A — LÝ THUYẾT CẬP NHẬT LOCAL REPOSITORY

## 1. Nền tảng: Mô hình "ba cây" và remote-tracking branches

### 1.1 Nhắc lại mô hình ba cây

Trước khi nói về "cập nhật", cần khẳng định lại mô hình mà mọi lệnh trong phần này thao tác lên:

```
┌─────────────────────┐    ┌──────────────────┐    ┌─────────────────────┐
│  Working Directory  │    │  Index (Staging) │    │  Commit History     │
│  (file trên đĩa)    │◄──►│  (.git/index)    │◄──►│  (.git/objects +    │
│                     │    │                  │    │   refs/heads/)      │
└─────────────────────┘    └──────────────────┘    └─────────────────────┘
         Cây 1                    Cây 2                     Cây 3
```

**`git fetch`/`merge`/`pull` thao tác chủ yếu trên cây 3 (commit history + refs)**. Chỉ khi merge/checkout mới chạm cây 1 và cây 2.

### 1.2 Remote-tracking branch — "gương" của remote

Đây là khái niệm **quyết định toàn bộ lý thuyết cập nhật**:

```
refs/heads/main            ← branch local (BẠN di chuyển bằng commit/reset/merge)
refs/remotes/origin/main   ← remote-tracking (GIT di chuyển khi fetch/push)
```

**`origin/main` KHÔNG phải là "main trên server"**. Nó là **snapshot local** của `main` trên server **tại lần fetch/push gần nhất**. Server thực tế có thể đã khác xa.

**Hệ quả lý thuyết quan trọng**:
- `git status` báo "up to date with origin/main" → chỉ có nghĩa "khớp với **snapshot cũ**", không đảm bảo server thực tế cũng vậy.
- Git **không liên lạc với server** khi chạy `status`, `log`, `branch -vv` — mọi thứ đọc từ snapshot local.
- Chỉ `git fetch` (hoặc `push`) mới **cập nhật snapshot**.

### 1.3 Sơ đồ refs trước và sau fetch

```
Trước fetch:
  Server:        A ← B ← C ← D          (main thật trên server)
  refs/remotes/origin/main → C          (snapshot cũ trong máy bạn)
  refs/heads/main          → B          (branch local của bạn)

Sau `git fetch origin`:
  refs/remotes/origin/main → D          (CẬP NHẬT — Git di chuyển)
  refs/heads/main          → B          (KHÔNG ĐỔI — bạn vẫn ở B)
  Working tree             → không đổi
  Index                    → không đổi
```

**Lý thuyết cốt lõi**: `fetch` chỉ **tải objects mới** + **di chuyển remote-tracking refs**. Nó là thao tác **read-only** với mọi thứ thuộc về bạn — không thể mất dữ liệu.

## 2. `git fetch` — Tải về "bức ảnh" mới nhất

### 2.1 Cơ chế chi tiết

```
Bước 1: Kết nối tới remote (SSH/HTTPS)
Bước 2: Hỏi "refs/heads/* hiện đang trỏ tới đâu?" (ls-remote)
Bước 3: So sánh với refs/remotes/origin/* local
Bước 4: Tải về các object (commit/tree/blob) mà local CHƯA có
        → Dùng "negotiation protocol": gửi danh sách "have", server gửi "want"
Bước 5: Cập nhật refs/remotes/origin/* theo refspec
Bước 6: Tải tag mới (mặc định auto-follow tag)
```

**Điểm tinh tế**: Git **không tải lại toàn bộ**. Nó dùng **pack protocol** để negotiate — "tôi đã có A, B, C, cho tôi những gì mới". Đây là lý do fetch lần 2 rất nhanh dù repo lớn.

### 2.2 Các biến thể

```bash
git fetch                              # fetch từ origin (remote của upstream branch)
git fetch origin                       # fetch tất cả branches từ origin
git fetch origin main                  # fetch branch main cụ thể → cập nhật origin/main
git fetch --all                        # fetch từ MỌI remote
git fetch --prune                      # fetch + xóa remote-tracking không còn trên server
git fetch --all --prune                # combo phổ biến
git fetch --tags                       # tải cả tag không được auto-follow
git fetch --depth=1 origin main        # shallow fetch
git fetch --dry-run                    # mô phỏng (không tải)
git fetch origin main:refs/remotes/origin/main   # refspec tường minh
```

### 2.3 RefSpec — "hợp đồng" giữa remote và local

Cấu hình mặc định trong `.git/config`:

```ini
[remote "origin"]
    url = git@github.com:user/repo.git
    fetch = +refs/heads/*:refs/remotes/origin/*
```

Refspec này có nghĩa:
- `+`: cho phép **non-fast-forward** (ghi đè mù quáng — cần cho remote-tracking vì nó là cache, không phải branch thật).
- `refs/heads/*` (nguồn): mọi branch trên server.
- `refs/remotes/origin/*` (đích): tương ứng trong máy bạn.

**Lý thuyết**: Nếu bỏ `+`, Git sẽ từ chối cập nhật `origin/main` khi nó không phải fast-forward (ví dụ: ai đó force-push lên server). Đây là lý do mặc định có `+` — remote-tracking branch là **cache**, phải phản ánh đúng server kể cả khi server bị rewrite.

### 2.4 `--prune` — Tại sao cần?

Khi ai đó **xóa branch** trên server (`feature/old`), `git fetch` **không tự xóa** `origin/feature/old` local. Nó trở thành **stale** (mục rữa):

```
refs/remotes/origin/feature/old → a1b2c3d   (branch đã bị xóa trên server)
```

`git fetch --prune` bảo: "sau khi cập nhật, xóa mọi `refs/remotes/origin/*` không còn tương ứng trên server". Config vĩnh viễn:

```bash
git config --global fetch.prune true
```

**Điểm lý thuyết**: `--prune` **chỉ xóa remote-tracking refs**, không đụng tới branch local. Nếu bạn có branch local `feature/old` đang track `origin/feature/old`, nó vẫn còn (chỉ mất upstream link).

### 2.5 Khi nào `fetch` fail?

- **Network**: không kết nối được remote (firewall, DNS, SSH key).
- **Auth**: permission denied (key sai, token hết hạn).
- **Refspec lỗi**: refspec không match (hiếm).
- **Shallow repo**: fetch đòi objects mà shallow không có → cần `--unshallow`.

**Lý thuyết an toàn**: `fetch` **gần như không bao giờ** gây mất dữ liệu. Ngay cả khi server bị compromise và trả về objects độc hại, chúng chỉ nằm trong `.git/objects` — không tự áp vào working tree. `fetch` là bước "kiểm tra" an toàn trước khi merge/rebase.

## 3. `git merge` — Hợp nhất thay đổi vào branch local

### 3.1 Bối cảnh: Merge từ remote-tracking vào branch local

Khi bạn đã `fetch` (hoặc `pull` ngầm fetch), `origin/main` đã trỏ tới commit mới nhất trên server. Nhưng `main` local vẫn ở commit cũ. Để cập nhật:

```bash
git switch main
git merge origin/main
```

Đây là lệnh merge **nhánh remote-tracking** vào **nhánh local hiện tại**.

### 3.2 Ba tình huống lý thuyết

#### Tình huống 1: Up-to-date (local đã bằng hoặc đi trước)

```
main           → D
origin/main    → D   (hoặc C, ancestor của D)
```

`git merge origin/main` → **"Already up to date"**. Không làm gì.

#### Tình huống 2: Fast-forward (local là ancestor của remote)

```
main           → C
origin/main    → C ← D ← E
```

`git merge origin/main` → **Fast-forward**: Git chỉ di chuyển `main` từ C sang E. **Không tạo commit mới.**

```
Sau merge:
main           → E
origin/main    → E
```

**Lý thuyết**: FF an toàn tuyệt đối — không có "công việc hợp nhất" nào, chỉ là con trỏ nhảy về phía trước. Không conflict có thể xảy ra (vì local không có commit nào không nằm trong remote).

#### Tình huống 3: Diverged (phân kỳ — cần three-way merge)

```
main           → C ← X ← Y       (bạn có commit local X, Y)
origin/main    → C ← D ← E       (người khác push D, E)
```

`git merge origin/main` → **Three-way merge**: tạo **merge commit M** với hai parent (Y và E).

```
Sau merge:
main           → M
                / \
               Y   E
               |   |
               X   D
                \ /
                 C
origin/main    → E
```

**Có thể conflict** nếu X, Y thay đổi cùng vùng với D, E.

### 3.3 Merge options trong ngữ cảnh cập nhật

```bash
git merge origin/main              # mặc định: FF nếu có thể, ngược lại 3-way
git merge --ff-only origin/main    # CHỈ FF, fail nếu phải 3-way (an toàn nhất)
git merge --no-ff origin/main      # LUÔN tạo merge commit (kể cả FF được)
git merge --squash origin/main     # gộp tất cả commit thành 1 thay đổi chưa commit
git merge --abort                  # hủy merge đang dở (khi conflict)
```

**`--ff-only` — Lý thuyết quan trọng**: Đây là **chế độ an toàn nhất** cho cập nhật branch chính. Nếu `--ff-only` fail → có nghĩa local đã **phân kỳ** (bạn có commit mà remote không có). Lúc này, **bạn phải quyết định có ý thức**: merge (tạo merge commit), hay rebase (viết lại local), hay reset (bỏ commit local). `--ff-only` **không cho phép Git tự quyết định** — bảo vệ khỏi merge ngoài ý muốn.

### 3.4 Conflict khi merge từ remote

Khi conflict xảy ra:

```
<<<<<<< HEAD
code của BẠN (main local)
=======
code của REMOTE (origin/main)
>>>>>>> origin/main
```

**Lý thuyết**: Conflict xảy ra khi **cùng vùng** (dòng) của file bị thay đổi khác nhau ở hai phía, hoặc file bị **đổi tên/xóa** ở một phía. Git không thể quyết định "ai đúng" — đó là vấn đề **ngữ nghĩa**, không phải cú pháp.

**Quy trình giải quyết**:

```bash
# 1. Sửa file, chọn/ghép nội dung
vim conflicted.txt

# 2. Đánh dấu đã giải quyết
git add conflicted.txt

# 3. Hoàn tất merge
git commit                            # merge commit với message mặc định

# Hoặc hủy toàn bộ:
git merge --abort
```

**Công cụ hỗ trợ**:
```bash
git mergetool                        # mở tool đồ họa (vimdiff, kdiff3, meld...)
git diff --name-only --diff-filter=U # liệt kê file đang conflict
git checkout --ours <file>           # chọn toàn bộ "ours" cho file
git checkout --theirs <file>         # chọn toàn bộ "theirs" cho file
```

**Lý thuyết nâng cao**: `--ours`/`--theirs` khi merge **remote vào local**:
- `ours` = branch local (main).
- `theirs` = origin/main.

Nhưng khi **rebase**, hai khái niệm **đảo ngược** — một bẫy phổ biến (xem phần 4).

### 3.5 Merge strategies

Git có nhiều "merge strategy" — thuật toán quyết định cách hợp nhất:

| Strategy               | Khi nào dùng                     | Ghi chú                         |
| ---------------------- | -------------------------------- | ------------------------------- |
| `recursive` (mặc định) | Merge 2 nhánh thông thường       | Xử lý rename, criss-cross merge |
| `ort` (Git ≥2.34)      | Thay thế `recursive`             | Nhanh hơn, chính xác hơn        |
| `ours`                 | Bỏ qua hoàn toàn theirs          | `-s ours` — tree = ours         |
| `subtree`              | Merge subproject vào thư mục con | Cho subtree merge               |
| `resolve`              | Merge 2 nhánh đơn giản           | Hiếm dùng                       |

Và **strategy options** (`-X`):

```bash
git merge -X ours origin/main      # conflict → auto chọn ours
git merge -X theirs origin/main    # conflict → auto chọn theirs
git merge -X patience origin/main  # patience diff (chính xác hơn cho code)
git merge -X ignore-space-change   # bỏ qua whitespace
git merge -X renormalize            # chuẩn hóa line ending
```

**Phân biệt `-s ours` vs `-X ours`**:
- `-s ours`: **toàn bộ** tree = ours, bỏ hẳn theirs (chỉ dùng để "đánh dấu đã merge" mà không lấy nội dung).
- `-X ours`: vẫn merge bình thường, **chỉ conflict** mới auto chọn ours; thay đổi không conflict vẫn được áp.

## 4. `git pull` — Fetch + Merge trong một lệnh

### 4.1 Định nghĩa và cơ chế

```bash
git pull
# tương đương:
git fetch
git merge <upstream>
```

Trong đó `<upstream>` là remote-tracking branch tương ứng với branch local hiện tại, xác định bởi cấu hình:

```ini
[branch "main"]
    remote = origin
    merge = refs/heads/main
```

→ `git pull` = `git fetch origin` + `git merge origin/main`.

### 4.2 Biến thể

```bash
git pull                            # pull từ upstream của branch hiện tại
git pull origin                     # pull từ origin, merge theo config
git pull origin main                # pull branch main từ origin
git pull --rebase                   # fetch + REBASE thay vì merge
git pull --no-rebase                # fetch + merge (mặc định)
git pull --ff-only                  # fetch + merge --ff-only (an toàn nhất)
git pull --no-commit                # merge nhưng không auto-commit
git pull --autostash                # tự stash thay đổi chưa commit
```

### 4.3 `pull.rebase` — Cấu hình toàn cục

```bash
git config --global pull.rebase false      # merge (mặc định cũ)
git config --global pull.rebase true       # rebase
git config --global pull.rebase merges     # rebase nhưng giữ merge commit
git config --global pull.ff only           # chỉ FF (an toàn nhất, fail nếu diverged)
```

**Lý thuyết `pull.ff only`**: Đây là **cấu hình an toàn nhất** cho người mới. Nó biến `git pull` thành "chỉ cập nhật nếu có thể fast-forward". Nếu fail → bạn **buộc phải** xem xét (fetch + log + quyết định merge/rebase), không bao giờ bị "merge bất ngờ".

### 4.4 Rebase pull — Lý thuyết và cạm bẫy

```bash
git pull --rebase
# tương đương:
git fetch
git rebase origin/main
```

**Lý thuyết**: Rebase áp lại các commit **local** của bạn lên đầu `origin/main`. Kết quả: lịch sử **tuyến tính** — như thể bạn viết code sau khi đã pull mới nhất.

**Ưu điểm**:
- Không tạo merge commit "vô nghĩa" (merge không mang thông tin gì).
- Lịch sử sạch, dễ bisect.

**Nhược điểm**:
- **Viết lại SHA** của commit local → nếu đã push, phải `push --force-with-lease`.
- Conflict phải giải quyết **từng commit** (không phải một lần).
- **Cạm bẫy `ours`/`theirs`**: trong rebase, `ours` = **origin/main** (base mới!), `theirs` = **commit local đang được áp**. **Ngược** so với merge. Đây là nguồn gốc nhiều lỗi.

**Quy tắc vàng**: Chỉ `pull --rebase` khi các commit local **chưa push**. Nếu đã push lên branch chia sẻ → dùng `pull` (merge).

### 4.5 Pull fail — Các trường hợp và xử lý

#### 4.5.1 "fatal: refusing to merge unrelated histories"

Nguyên nhân: local và remote có **root commit khác nhau** (DAG không liên thông). Thường xảy ra khi:
- `git init` local + tạo commit.
- Tạo repo trên GitHub (có README → có commit).
- `git remote add` + `git pull`.

Giải pháp:
```bash
git pull origin main --allow-unrelated-histories
```

**Lý thuyết**: Git từ chối vì merge không có "common ancestor" — sẽ tạo commit cha kép mà DAG không liên thông. `--allow-unrelated-histories` chấp nhận rủi ro (có thể conflict nặng, đặc biệt nếu cả hai có file cùng tên).

**Cách tránh**: Khi tạo repo trên GitHub **không** init với README, hoặc khi clone về thay vì init local.

#### 4.5.2 "You have divergent branches and need to specify how to reconcile them"

Git ≥2.27 yêu cầu cấu hình `pull.rebase`/`pull.ff` khi phân kỳ. Giải pháp:

```bash
# Cách 1: chỉ định rõ
git pull --rebase            # hoặc --no-rebase, --ff-only
git pull --no-rebase

# Cách 2: cấu hình vĩnh viễn
git config --global pull.rebase false    # merge
git config --global pull.ff only         # an toàn nhất
```

**Lý thuyết**: Đây là **thay đổi có chủ đích** của Git — trước đây Git tự ý merge (có thể tạo merge commit bất ngờ), gây bối rối. Giờ nó **bắt buộc** người dùng có ý thức về chiến lược.

#### 4.5.3 "Your local changes would be overwritten by merge"

Có thay đổi chưa commit trong working tree mà merge sẽ ghi đè. Giải pháp:

```bash
# Cách 1: commit trước
git add . && git commit -m "wip"

# Cách 2: stash
git stash
git pull
git stash pop

# Cách 3: dùng autostash
git pull --autostash
```

### 4.6 Pull vs Fetch — Bảng so sánh lý thuyết

|                             | `fetch`                        | `pull`                       |
| --------------------------- | ------------------------------ | ---------------------------- |
| Tải objects                 | ✅                              | ✅                            |
| Cập nhật remote-tracking    | ✅                              | ✅                            |
| Cập nhật branch local       | ❌                              | ✅ (qua merge/rebase)         |
| Đụng working tree           | ❌                              | ✅ (khi merge/rebase)         |
| Có thể conflict             | ❌                              | ✅                            |
| An toàn (không mất dữ liệu) | ✅ tuyệt đối                    | ⚠️ phụ thuộc chiến lược       |
| Cần network                 | ✅                              | ✅                            |
| Khi nào dùng                | Muốn xem trước, kiểm soát chặt | Workflow đơn giản, tin tưởng |

**Lý thuyết cốt lõi**: `fetch` là **kiểm tra** (read-only), `pull` là **hành động** (write). Người dùng có kinh nghiệm thường `fetch` trước để xem `log origin/main` trước khi quyết định merge/rebase. Đây là lý do nhiều team khuyến nghị alias `git up = fetch + log + merge --ff-only` thay vì `pull` trực tiếp.

## 5. Xử lý phân kỳ (diverged history) — Các chiến lược

Khi `git status` báo `ahead N, behind M` (local có N commit remote chưa có, remote có M commit local chưa có):

### 5.1 Chiến lược 1: Merge (an toàn nhất)

```bash
git fetch origin
git log --oneline main..origin/main     # xem commit mới trên remote
git log --oneline origin/main..main     # xem commit local
git merge origin/main
# có thể conflict → giải quyết → commit
```

**Kết quả**: Merge commit + lịch sử phân nhánh. **An toàn** — không mất commit nào, không viết lại SHA.

### 5.2 Chiến lược 2: Rebase (sạch, nếu chưa push)

```bash
git fetch origin
git rebase origin/main
# có thể conflict từng commit → giải quyết → rebase --continue
```

**Kết quả**: Lịch sử tuyến tính, commit local có SHA mới. **Chỉ an toàn nếu commit local chưa push**.

### 5.3 Chiến lược 3: Reset (bỏ commit local — nguy hiểm)

```bash
git fetch origin
git reset --hard origin/main
```

**Kết quả**: Local = remote. **Mất tất cả commit local** (vẫn cứu được qua reflog trong ~30 ngày). Chỉ dùng khi chắc chắn muốn bỏ hết.

### 5.4 Chiến lược 4: Merge với `-X ours`/`-X theirs` (auto-resolve conflict)

```bash
git merge -X ours origin/main      # conflict → ưu tiên local
git merge -X theirs origin/main    # conflict → ưu tiên remote
```

**Cẩn thận**: Chỉ dùng khi bạn hiểu rõ — có thể mất thay đổi quan trọng của một phía.

### 5.5 Bảng quyết định

| Tình huống                     | Chiến lược                       |
| ------------------------------ | -------------------------------- |
| Branch cá nhân, chưa push      | `rebase` (sạch)                  |
| Branch chia sẻ (main, develop) | `merge` (an toàn)                |
| Muốn bỏ hoàn toàn commit local | `reset --hard` (cực kỳ cẩn thận) |
| Chỉ muốn xem trước             | `fetch` + `log` + `diff`         |
| Muốn pull an toàn tuyệt đối    | `git pull --ff-only`             |

## 6. Các công cụ hỗ trợ cập nhật

### 6.1 `git remote show origin`

```bash
git remote show origin
```

Output:
```
* remote origin
  HEAD branch: main
  Remote branches:
    main        tracked
    feature/x   tracked
    old-branch  stale (use 'git remote prune' to remove)
  Local branch configured for 'git pull':
    main merges with remote main
  Local ref configured for 'git push':
    main pushes to main (up to date)
```

Đây là lệnh **duy nhất** trong nhóm remote management **liên lạc với server** (khác `remote -v` chỉ đọc config). Nó cho biết upstream link, branch stale, và trạng thái ahead/behind.

### 6.2 `git branch -vv`

```bash
* main    a1b2c3d [origin/main: ahead 2, behind 1] feat: something
  feature e4f5g6h [origin/feature: gone]             fix: bug
```

- `ahead 2, behind 1`: local có 2 commit chưa push, remote có 1 commit chưa fetch.
- `gone`: upstream branch đã bị xóa → cần `fetch --prune`.

### 6.3 `git log` để kiểm tra trước khi merge

```bash
git fetch origin
git log --oneline HEAD..origin/main          # commit mới trên remote
git log --oneline origin/main..HEAD          # commit local chưa push
git log --left-right --graph HEAD...origin/main   # cả hai phía, có đánh dấu < >
git diff HEAD origin/main -- <path>          # diff cụ thể
```

### 6.4 `git ls-remote` — "Nhìn trộm" server thật

```bash
git ls-remote origin
```

Output:
```
a1b2c3d...	HEAD
a1b2c3d...	refs/heads/main
e4f5g6h...	refs/heads/feature
```

Đọc **trực tiếp** refs từ server — **không** cập nhật snapshot local, **không** tải objects. Dùng khi nghi ngờ snapshot cũ (ví dụ: muốn biết chính xác server đang ở đâu trước khi merge).

### 6.5 `git fetch && git diff` — Xem trước thay đổi

```bash
git fetch origin
git diff main origin/main                # xem tất cả thay đổi sẽ merge
git diff --stat main origin/main         # tóm tắt
git log -p main..origin/main             # commit + diff
```

Đây là **quy trình chuẩn của người dùng có kinh nghiệm**: fetch trước, xem kỹ, rồi mới merge/rebase.

# PHẦN B — TEAM DEVELOPMENT DEMO

Phần này mô phỏng một kịch bản phát triển nhóm thực tế với **3 lập trình viên** (Alice, Bob, Charlie) cùng làm việc trên một repo. Chúng ta sẽ đi qua các tình huống **cập nhật local repository** điển hình.

## Setup ban đầu

```
Remote: git@github.com:team/project.git (bare repo trên GitHub)
Có branch main với commit A (initial commit)

3 developers đều đã clone về máy:
- Alice: ~/alice/project
- Bob:   ~/bob/project
- Charlie: ~/charlie/project
```

Trạng thái ban đầu (mọi người giống nhau):

```
A   (main, origin/main)   ← tất cả đều ở A
```

---

## Kịch bản 1: Cập nhật đơn giản — Fast-forward

### Bước 1.1: Alice làm việc và push

```bash
# Alice
cd ~/alice/project
git switch -c feature/login        # tạo branch từ main
# ... code ...
git add .
git commit -m "feat: add login form"      # commit B
git commit -m "feat: add validation"      # commit C (sau khi sửa thêm)
git switch main
git merge feature/login                    # fast-forward main → C
git push origin main
```

Trạng thái sau push:

```
A ← B ← C   (main, origin/main)   ← SERVER có C
```

### Bước 1.2: Bob chưa biết — local vẫn ở A

```bash
# Bob
cd ~/bob/project
git status
# On branch main
# Your branch is up to date with 'origin/main'.   ← SAI! (snapshot cũ)
# nothing to commit, working tree clean

# Bob cần cập nhật
git fetch origin
# remote: Enumerating objects: 5, done.
# remote: Counting objects: 100% (5/5), done.
# From github.com:team/project
#    a1b2c3d..c3d4e5f  main       -> origin/main

git log --oneline main..origin/main
# c3d4e5f feat: add validation
# b2c3d4e feat: add login form

# Bob xem diff
git diff main origin/main

# Bob merge (fast-forward)
git switch main
git merge origin/main
# Updating a1b2c3d..c3d4e5f
# Fast-forward
#  login.js       | 42 ++++++++++++
#  validation.js  | 18 ++++++
#  2 files changed, 60 insertions(+)
```

Trạng thái sau merge của Bob:

```
A ← B ← C   (main, origin/main)   ← Bob giờ ở C
```

**Bài học**: `git status` báo "up to date" **trước khi fetch** là **vô nghĩa** — nó chỉ khớp snapshot cũ. Luôn `fetch` trước khi tin status.

---

## Kịch bản 2: Phân kỳ — Cần merge

### Bước 2.1: Alice push thêm

```bash
# Alice (tiếp tục từ C)
git switch main
# ... sửa file README ...
git commit -am "docs: update README"      # commit D
git push origin main
```

Server:
```
A ← B ← C ← D   (main, origin/main)
```

### Bước 2.2: Bob commit local (chưa push)

```bash
# Bob (đang ở C từ kịch bản 1)
# ... sửa file config.js ...
git commit -am "fix: update config"       # commit E
```

Bob local:
```
A ← B ← C ← E   (main)
```

**Hai bên đã phân kỳ**:
- Remote: `A ← B ← C ← D`
- Bob:    `A ← B ← C ← E`

### Bước 2.3: Bob fetch (chưa merge)

```bash
# Bob
git fetch origin
#    c3d4e5f..d5e6f7g  main -> origin/main

git status
# On branch main
# Your branch and 'origin/main' have diverged,
# and have 1 and 1 different commits each, respectively.
#   (use "git pull" to merge the remote branch into yours)
```

Đồ thị:
```
A ← B ← C ← E   (main, HEAD)
         ↖
          D     (origin/main)
```

### Bước 2.4: Bob xem trước

```bash
git log --oneline --graph --all
# * e5f6g7h (HEAD -> main) fix: update config
# | * d5e6f7g (origin/main) docs: update README
# |/
# * c3d4e5f feat: add validation
# * b2c3d4e feat: add login form
# * a1b2c3d chore: initial commit

git log origin/main..main            # commit Bob có, remote không có
# e5f6g7h fix: update config

git log main..origin/main            # commit remote có, Bob không có
# d5e6f7g docs: update README
```

### Bước 2.5: Bob chọn chiến lược

#### Option A: Merge (an toàn)

```bash
git merge origin/main
# Merge made by the 'ort' strategy.
#  README.md | 5 +++++
#  1 file changed, 5 insertions(+)
```

Kết quả:
```
A ← B ← C ← E ←─ M   (main, HEAD)
         ↖       /
          D ────
                (origin/main → D)
```

`M` là merge commit. Bob cần push `M`:
```bash
git push origin main
```

#### Option B: Rebase (sạch, nhưng viết lại SHA)

```bash
git rebase origin/main
# Successfully rebased and updated refs/heads/main.
```

Kết quả:
```
A ← B ← C ← D ← E'   (main, HEAD, origin/main... chưa)
```

`E'` là commit mới (SHA khác E, nội dung tương tự). Bob push:
```bash
git push origin main
# hoặc nếu remote đã có E (không thể), phải --force-with-lease
```

#### Option C: Pull với chiến lược cụ thể

```bash
# Nếu Bob chưa fetch (trong thực tế)
git pull --rebase origin main
# tương đương fetch + rebase

# Hoặc an toàn nhất
git pull --ff-only origin main
# fatal: Not possible to fast-forward, aborting.
# → Bob buộc phải xem xét và chọn merge/rebase
```

### Bước 2.6: Bob push

```bash
git push origin main
```

Nếu Bob chọn merge (Option A):
- Push thành công (fast-forward từ D → M, vì M có D là ancestor).

Nếu Bob chọn rebase (Option B):
- Push **thành công** vì E' có D là ancestor (rebase đã áp E lên D).

Nếu Bob chọn amend/rebase rồi muốn ghi đè:
- Cần `git push --force-with-lease origin main`.

## Kịch bản 3: Conflict khi pull

### Bước 3.1: Alice và Bob cùng sửa config.js

Alice:
```bash
# Alice
git switch main && git pull
vim config.js
# sửa: const TIMEOUT = 5000;
git commit -am "fix: increase timeout"
git push origin main
```

Bob (chưa fetch):
```bash
# Bob
git switch main && git pull
# Có thể conflict...
# hoặc nếu pull sau khi Alice push:
```

Giả sử Bob cũng sửa `config.js` (khác vùng hoặc cùng vùng). Khi pull:

```bash
git pull
# Auto-merging config.js
# CONFLICT (content): Merge conflict in config.js
# Automatic merge failed; fix conflicts and then commit the result.

git status
# You have unmerged paths.
#   (fix conflicts and run "git commit")
# Unmerged paths:
#   both modified:   config.js

cat config.js
# <<<<<<< HEAD
# const TIMEOUT = 3000;
# =======
# const TIMEOUT = 5000;
# >>>>>>> origin/main
```

### Bước 3.2: Giải quyết conflict

```bash
# Bob quyết định giữ 5000 (từ remote) vì phù hợp hơn
vim config.js
# Sửa thành: const TIMEOUT = 5000;

git add config.js
git commit
# [main f7g8h9i] Merge branch 'main' of github.com:team/project

git push origin main
```

### Bước 3.3: Bob dùng `mergetool` (nếu muốn)

```bash
git mergetool
# mở vimdiff, 3-way merge view:
#   LOCAL (ours)  |  BASE  |  REMOTE (theirs)
```

**Lưu ý lý thuyết**: Trong **pull/merge**, `ours` = branch local của Bob, `theirs` = origin/main. Trong **rebase**, ngược lại.

## Kịch bản 4: Rebase pull — Khi nào và tại sao

### Bước 4.1: Bob muốn lịch sử sạch

Bob có 2 commit local chưa push, Alice vừa push 1 commit. Thay vì merge (tạo merge commit), Bob dùng rebase:

```bash
# Bob
git fetch origin
git rebase origin/main
# First, rewinding head to replay your work on top of it...
# Applying: fix: update config
# Applying: feat: add helper
# Successfully rebased.
```

Kết quả:
```
Trước:
A ← B ← C ← E ← F   (main)
         ↖
          D         (origin/main)

Sau rebase:
A ← B ← C ← D ← E' ← F'   (main)
```

**Lý thuyết**: `E'` và `F'` có SHA mới (parent khác, committer date khác). Nội dung tương tự E, F nhưng áp lên D.

### Bước 4.2: Conflict trong rebase — Cẩn thận `ours`/`theirs`

Giả sử conflict xảy ra khi áp `E`:

```bash
git rebase origin/main
# CONFLICT (content): Merge conflict in config.js
# error: could not apply e5f6g7h... fix: update config
# Resolve all conflicts manually, mark them as resolved with
# "git add <conflicted_files>", then run "git rebase --continue".

cat config.js
# <<<<<<< HEAD
# const TIMEOUT = 5000;        ← HEAD = origin/main (base mới!)
# =======
# const TIMEOUT = 3000;        ← commit Bob đang áp
# >>>>>>> e5f6g7h (fix: update config)
```

**Cạm bẫy**: Trong rebase:
- `HEAD` = `origin/main` (base mới) — **KHÔNG phải commit Bob**.
- `>>>>>>> <sha>` = commit Bob đang áp lại.

→ `git checkout --ours` = **chọn origin/main**, `--theirs` = **chọn Bob**. **Ngược** với merge!

### Bước 4.3: Hoàn tất rebase

```bash
# Sửa file
vim config.js
git add config.js
git rebase --continue

# Nếu còn conflict tiếp → lặp lại
# Khi xong:
# Successfully rebased and updated refs/heads/main.
```

Bob push (vì commit local chưa push, rebase an toàn):
```bash
git push origin main
```

## Kịch bản 5: Pull với thay đổi chưa commit

### Bước 5.1: Bob đang code dở

```bash
# Bob
git status
# modified:   index.html
# modified:   style.css

# Alice vừa push, Bob pull
git pull
# error: Your local changes to the following files would be overwritten by merge:
#         index.html
# Please commit your changes or stash them before you merge.
# Aborting
```

**Lý thuyết**: Merge cần cập nhật `index.html` trên working tree, nhưng Bob có thay đổi chưa commit ở file đó → sẽ ghi đè → Git từ chối (bảo vệ).

### Bước 5.2: Các cách xử lý

#### Cách 1: Commit tạm

```bash
git add . && git commit -m "wip: index changes"
git pull
# (giải quyết conflict nếu có)
```

#### Cách 2: Stash

```bash
git stash push -m "wip: index changes"
git pull
git stash pop
# (giải quyết conflict nếu có)
```

#### Cách 3: Autostash

```bash
git pull --autostash
# Tự stash → pull → pop (có thể conflict nếu file bị pull chạm)
```

**Lý thuyết**: `--autostash` tiện nhưng **có thể che giấu conflict** — nếu stash pop conflict, Git sẽ báo sau. Nên kiểm tra `git status` sau khi autostash.

## Kịch bản 6: Feature branch workflow — Full cycle

Đây là workflow phổ biến nhất trong team hiện đại:

### Bước 6.1: Alice tạo feature branch

```bash
# Alice
git switch main
git pull --ff-only origin main         # đảm bảo main mới nhất
git switch -c feature/user-profile

# ... code ...
git add .
git commit -m "feat: add profile page"
git commit -m "feat: add avatar upload"
git push -u origin feature/user-profile
```

### Bước 6.2: Bob review trên GitHub, Alice sửa

Trên GitHub, Bob để lại comment. Alice sửa:

```bash
# Alice
git switch feature/user-profile
vim profile.js
git add .
git commit -m "fix: address review comments"
git push                              # đã có -u nên không cần tham số

### Bước 6.3: Main bị thay đổi — Alice cần rebase

- Merge: merge commit + các commit gốc.

```

## Kịch bản 7: Lỡ tay — Các tình huống khôi phục

### 7.1 `pull --rebase` fail giữa chừng

```bash
git pull --rebase
# CONFLICT...
# Bob hoảng, không biết làm gì
```

**Giải pháp**:
```bash
# Cách 1: Tiếp tục sau khi giải quyết
git add .
git rebase --continue

# Cách 2: Hủy hoàn toàn, quay lại trạng thái trước pull
git rebase --abort
# → Local trở về trạng thái trước khi pull (an toàn!)

# Cách 3: Bỏ qua commit đang conflict (nguy hiểm — mất nội dung)
git rebase --skip
```

### 7.2 Lỡ `reset --hard` mất commit

```bash
# Bob lỡ tay
git reset --hard origin/main
# Mất commit local!

# Cứu bằng reflog
git reflog
# f7g8h9i HEAD@{0}: reset: moving to origin/main
# e5f6g7h HEAD@{1}: commit: fix: update config   ← commit bị mất
# ...

git reset --hard e5f6g7h
# Đã cứu!
```

**Lý thuyết**: Reflog giữ **mọi di chuyển của HEAD** trong ~90 ngày. Commit "mất" vẫn trong objects, chỉ là unreachable. Reflog giữ SHA để cứu.

### 7.3 Lỡ force push đè commit người khác

```bash
# Bob vừa push --force, đè mất commit của Alice trên remote
```

**Cứu trên remote** (nếu có backup):
- GitHub: branch protection có thể chặn force push.
- GitHub: reflog trên server — không truy cập trực tiếp được, nhưng **Activity** có thể thấy SHA cũ.
- Nếu biết SHA cũ: `git push --force origin <sha>:main`.

**Phòng tránh**:
- Dùng `--force-with-lease` thay vì `--force`.
- Bật branch protection: "Do not allow force pushes" cho `main`.
- Thông báo team trước khi force push.

## Kịch bản 8: Cấu hình an toàn cho team

Sau tất cả các kịch bản trên, đây là cấu hình được khuyến nghị cho team:

```bash
# Cá nhân (mỗi developer)
git config --global pull.ff only          # pull chỉ FF, fail nếu phân kỳ
git config --global fetch.prune true      # tự xóa remote-tracking stale
git config --global push.default simple   # push chỉ branch hiện tại lên upstream
git config --global rebase.autoStash true # tự stash khi rebase
git config --global merge.conflictStyle diff3   # hiển thị base trong conflict
git config --global alias.sync "!git fetch --all --prune && git log --oneline --graph --all"

# Repo (branch protection trên GitHub/GitLab)
# - main: require PR, require review, require CI, no force push, no direct push
# - require linear history (nếu team dùng squash/rebase)
# - require conversation resolution (review comments phải resolved)
```

**Workflow khuyến nghị**:

```bash
# Đầu ngày / trước khi bắt đầu task
git switch main
git fetch --all --prune
git pull --ff-only

# Tạo feature branch
git switch -c feature/xyz

# ... code, commit ...

# Cập nhật feature branch khi main thay đổi
git fetch origin
git rebase origin/main
git push --force-with-lease

# Khi PR merged
git switch main
git pull --ff-only
git branch -d feature/xyz
```

## Tổng kết lý thuyết — Bảng tổng hợp

| Lệnh                           | Cập nhật gì                 | An toàn?             | Khi nào dùng                    |
| ------------------------------ | --------------------------- | -------------------- | ------------------------------- |
| `git fetch`                    | Remote-tracking + objects   | ✅ Tuyệt đối          | Luôn luôn — bước đầu tiên       |
| `git fetch --prune`            | + xóa stale refs            | ✅                    | Định kỳ, đầu ngày               |
| `git merge origin/main`        | Branch local (merge commit) | ✅                    | Branch chia sẻ, phân kỳ         |
| `git merge --ff-only`          | Chỉ khi FF được             | ✅                    | Branch chính, an toàn tuyệt đối |
| `git rebase origin/main`       | Branch local (SHA mới)      | ⚠️ Chỉ chưa push      | Branch cá nhân                  |
| `git pull`                     | Fetch + merge/rebase        | ⚠️ Phụ thuộc strategy | Workflow đơn giản               |
| `git pull --ff-only`           | Fetch + merge --ff-only     | ✅ An toàn nhất       | **Khuyến nghị mặc định**        |
| `git pull --rebase`            | Fetch + rebase              | ⚠️ Chỉ chưa push      | Branch cá nhân                  |
| `git reset --hard origin/main` | Tất cả                      | ❌ Mất commit local   | Chỉ khi chắc chắn               |

**Nguyên tắc vàng cho team development**:
1. **Luôn `fetch` trước khi tin `status`** — `status` chỉ so với snapshot cũ.
2. **`pull --ff-only` là mặc định an toàn** — nó buộc bạn có ý thức khi phân kỳ.
3. **Rebase chỉ cho commit chưa push** — commit đã push phải merge.
4. **`--force-with-lease` thay vì `--force`** — luôn luôn.
5. **Branch protection trên `main`** — không push trực tiếp, không force push.
6. **Reflog là phao cứu sinh** — commit "mất" vẫn cứu được trong ~90 ngày.
7. **`fetch` + `log` + `diff` trước khi merge/rebase** — hiểu mình đang làm gì trước khi làm.
