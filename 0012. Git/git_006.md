# Git Branching — Giải thích lý thuyết chi tiết

---

## 1. Bản chất: Branch là gì?

### 1.1 Định nghĩa cốt lõi — Điểm hay bị hiểu sai nhất

Trong nhiều VCS khác (SVN, CVS, Perforce), branch là **bản sao vật lý** của toàn bộ cây thư mục — tạo branch = copy toàn bộ file. Điều này khiến branch **tốn kém** và người ta hạn chế tạo.

**Git thì hoàn toàn khác**:

> **Branch trong Git chỉ là một con trỏ (pointer) 41 byte trỏ tới một commit.** Nó không chứa file, không chứa history, không copy gì cả.

Cụ thể, một branch là **một file text** trong `.git/refs/heads/` chứa **SHA-1 của một commit**:

```bash
cat .git/refs/heads/main
# a1b2c3d4e5f6... (40 ký tự hex)
```

**Hệ quả lý thuyết**:
- Tạo branch = **ghi một file 41 byte** → gần như tức thời, bất kể repo lớn cỡ nào.
- Xóa branch = **xóa một file** → cũng tức thời. Commit vẫn còn (nếu còn reachable từ ref khác hoặc reflog).
- Đổi branch = **đổi nội dung file HEAD + checkout working tree** → đây mới là phần tốn thời gian (cập nhật file trên đĩa).

### 1.2 Branch và DAG — Mô hình lý thuyết

Nhắc lại: Git lưu lịch sử dưới dạng **DAG (Directed Acyclic Graph)** — mỗi commit là một nút, mỗi cạnh là quan hệ parent. **Branch chỉ là nhãn (label) gắn lên một nút trong DAG**.

```
A ← B ← C ← D   (main)
         ↑
         E ← F   (feature)
```

- `main` trỏ tới `D`.
- `feature` trỏ tới `F`.
- Cả hai chia sẻ tổ tiên chung `C` (common ancestor).

**Điểm mấu chốt**: Commit `A`, `B`, `C` **không thuộc về branch nào cả** — chúng chỉ "reachable từ" các branch. Nếu xóa cả `main` và `feature`, các commit vẫn tồn tại trong objects cho tới khi GC, nhưng **không còn reachable** → sẽ bị dọn sau ~30 ngày (hoặc ngay khi `git gc --prune=now`).

### 1.3 `HEAD` — Con trỏ tới branch (symbolic ref)

`HEAD` là **một symbolic ref** — nó không chứa SHA trực tiếp, mà chứa **đường dẫn tới ref khác**:

```bash
cat .git/HEAD
# ref: refs/heads/main
```

Cấu trúc:
```
HEAD → refs/heads/main → a1b2c3d...
```

Khi `HEAD` trỏ tới branch → **attached HEAD** (trạng thái bình thường). Khi commit:
1. Tạo commit object mới với parent = commit hiện tại của branch.
2. **Cập nhật file** `refs/heads/main` = SHA mới.
3. `HEAD` **vẫn trỏ** `refs/heads/main` (không đổi).

**Lý thuyết quan trọng**: Khi bạn commit, **branch tự động "tiến lên"** — vì nó là con trỏ, nó luôn trỏ commit mới nhất trên nhánh đó. Đây là cơ chế "auto-advance" của Git.

## 2. Tạo và quản lý branch — Cơ chế

### 2.1 `git branch` — Các biến thể

```bash
git branch                        # liệt kê branch local
git branch -a                     # tất cả (local + remote-tracking)
git branch -r                     # chỉ remote-tracking
git branch -v                     # kèm SHA + commit subject
git branch -vv                    # kèm upstream tracking
git branch <name>                 # tạo branch tại HEAD (KHÔNG chuyển sang)
git branch <name> <commit>        # tạo branch tại commit bất kỳ
git branch -d <name>              # xóa (an toàn — fail nếu chưa merge)
git branch -D <name>              # xóa cưỡng bức
git branch -m <old> <new>         # đổi tên
git branch -m <new>               # đổi tên branch hiện tại
git branch --merged               # branch đã merge vào HEAD
git branch --no-merged            # branch chưa merge
git branch --contains <commit>    # branch chứa commit đó
```

**`-d` vs `-D`**: `-d` kiểm tra branch đã được merge vào upstream/branch hiện tại chưa. Nếu chưa → từ chối (bảo vệ commit chưa merge). `-D` bỏ qua kiểm tra → **có thể mất commit** (chỉ reachable qua reflog).

### 2.2 `git checkout` / `git switch` — Chuyển branch

**`git switch`** (Git ≥2.23) được tách ra từ `checkout` vì `checkout` quá tải nghĩa (vừa đổi branch, vừa restore file):

```bash
# Tạo + chuyển
git switch -c <branch>                    # từ HEAD
git switch -c <branch> <start-point>      # từ commit/branch khác
git switch <branch>                       # chuyển sang branch có sẵn
git switch -                              # quay lại branch trước (như cd -)

# Tương đương cũ với checkout
git checkout -b <branch>
git checkout <branch>
git checkout -                            # cũng có tác dụng
```

**Lý thuyết: checkout làm gì?**

Khi `git switch feature`:
1. Đọc tree của commit `feature` trỏ tới.
2. So sánh với working tree hiện tại.
3. Cập nhật **working tree + index** cho khớp tree đích (chỉ các file **khác nhau** — file giống nhau không bị chạm).
4. Cập nhật `HEAD` → `ref: refs/heads/feature`.

**Tại sao checkout đôi khi bị từ chối?** Nếu có thay đổi chưa commit trong working tree mà việc checkout sẽ **ghi đè** → Git từ chối (bảo vệ dữ liệu). Các thay đổi **không bị ghi đè** (file không tồn tại ở đích) → được mang theo sang branch mới (git "carry" changes).

```bash
git switch feature
# error: Your local changes to 'file.txt' would be overwritten by checkout
# → commit, stash, hoặc discard trước
```

### 2.3 `git branch` vs `git checkout -b` — Khác biệt then chốt

|              | `git branch X`      | `git switch -c X` / `checkout -b X` |
| ------------ | ------------------- | ----------------------------------- |
| Tạo branch   | ✅                   | ✅                                   |
| Chuyển sang  | ❌ (vẫn ở branch cũ) | ✅                                   |
| Working tree | Không đổi           | Cập nhật theo branch mới            |

## 3. Detached HEAD — Trạng thái nguy hiểm nhưng hữu ích

### 3.1 Định nghĩa

**Detached HEAD** xảy ra khi `HEAD` **trỏ trực tiếp tới một commit SHA**, không qua branch:

```bash
cat .git/HEAD
# a1b2c3d4e5f6... (SHA trực tiếp, không có "ref: refs/heads/...")
```

### 3.2 Cách rơi vào detached HEAD

```bash
git checkout <SHA>                 # hoặc tag, hoặc remote branch
git checkout v1.0.0
git checkout origin/main           # checkout remote-tracking → detached
git rebase <branch>                # trong lúc rebase, HEAD detached tạm thời
git bisect start                   # bisect dùng detached HEAD
```

### 3.3 Hệ quả lý thuyết — Tại sao nguy hiểm?

Khi commit trong detached HEAD:
- Commit **có được tạo** (object ghi vào `.git/objects/`).
- **Nhưng không branch nào trỏ tới nó** — `HEAD` chỉ trỏ thẳng commit đó.
- Nếu bạn `git switch main` → `HEAD` trỏ lại `main` → commit mới **trở thành unreachable** → **sẽ bị GC xóa** (~30 ngày mặc định).
- Chỉ reflog còn giữ SHA → cứu được nếu phát hiện sớm.

### 3.4 Cứu commit trong detached HEAD

```bash
# Cách 1: tạo branch ngay tại commit hiện tại (trước khi rời đi)
git switch -c rescue-branch

# Cách 2: nếu đã rời đi, dùng reflog
git reflog
# tìm SHA của commit đã tạo
git branch rescue-branch <sha>
```

### 3.5 Khi nào detached HEAD hữu ích?

- **Xem code ở commit cũ**: `git checkout v1.5.0` để inspect.
- **Rebase interactive**: Git detach HEAD tạm thời trong suốt quá trình.
- **Bisect**: tìm commit gây bug — Git checkout từng commit để test.
- **Build tại commit cụ thể** trong CI.

## 4. Merge — Hợp nhất lịch sử

### 4.1 Định nghĩa

**Merge** là thao tác kết hợp hai nhánh lịch sử thành một. Về mặt DAG, merge tạo ra một **commit mới có hai (hoặc nhiều) parent**.

### 4.2 Hai loại merge

#### Fast-forward (FF) — Khi có thể

Xảy ra khi nhánh đích **chưa có commit nào mới kể từ khi tách**:

```
Trước merge:
A ← B ← C   (main)
         ↑
         D ← E   (feature)

git switch main && git merge feature

Sau merge (fast-forward):
A ← B ← C ← D ← E   (main, feature)
```

**Cơ chế**: Git chỉ **di chuyển con trỏ `main`** từ `C` sang `E` — **không tạo commit mới**. Đây là fast-forward (tiến nhanh) vì không có "công việc hợp nhất" nào.

**Lý thuyết**: FF chỉ khả thi khi `main` là **ancestor của** `feature` — tức `main` không có commit nào `feature` chưa có.

#### Three-way merge — Khi FF không khả thi

Xảy ra khi cả hai nhánh đều có commit mới:

```
Trước merge:
A ← B ← C ← D   (main)
         ↑
         E ← F   (feature)

git switch main && git merge feature

Sau merge (three-way):
A ← B ← C ← D ←─── M   (main)
         ↑         /
         E ← F ───
```

- `M` là **merge commit** — có **hai parent**: `D` và `F`.
- Git dùng ba điểm: **base** (common ancestor `C`), **ours** (`D`), **theirs** (`F`).
- Với mỗi file khác nhau giữa 3 phiên bản → thử auto-merge; nếu không được → **conflict**.

**Tại sao gọi "three-way"?** Vì Git so sánh 3 phiên bản: base, ours, theirs — để quyết định thay đổi nào được giữ, thay đổi nào xung đột.

### 4.3 Merge options

```bash
git merge <branch>                 # mặc định — FF nếu có thể, ngược lại 3-way
git merge --no-ff <branch>         # LUÔN tạo merge commit, kể cả khi FF được
git merge --ff-only <branch>       # CHỈ FF, fail nếu không được (an toàn)
git merge --squash <branch>        # gộp tất cả commit thành 1 thay đổi chưa commit
git merge --no-commit <branch>     # merge nhưng không auto-commit (để review)
git merge --abort                  # hủy merge đang dở (khi conflict)
git merge -m "message"             # message cho merge commit
```

**`--no-ff` — Tại sao nhiều team dùng?**

Không có `--no-ff`, nếu merge được FF → lịch sử **không còn dấu vết** của branch (không biết feature được merge lúc nào). `--no-ff` **luôn tạo merge commit** → giữ ngữ nghĩa "feature X được merge vào main tại thời điểm Y". Đây là lý do Git Flow và nhiều workflow yêu cầu `--no-ff`.

**`--squash` — Tại sao?**

Gộp toàn bộ commit của feature thành **một thay đổi duy nhất** trong index, **không tạo merge commit, không giữ parent**. Bạn có thể commit như một commit bình thường. Ưu điểm: lịch sử main sạch (1 commit/feature). Nhược điểm: **mất lịch sử chi tiết** của feature; `git log --follow` không theo dõi được.

### 4.4 Conflict — Bản chất và cách xử lý

Conflict xảy ra khi **cùng một vùng của file** bị thay đổi khác nhau ở ours và theirs, hoặc **file bị đổi tên/xóa** ở một bên.

```
<<<<<<< HEAD
phiên bản ours (main)
=======
phiên bản theirs (feature)
>>>>>>> feature
```

**Lý thuyết**: Git không thể tự quyết định "ai đúng" — đây là vấn đề **ngữ nghĩa**, không phải cú pháp. Nên nó đánh dấu và **dừng lại** chờ con người giải quyết.

**Quy trình**:
```bash
# 1. Sửa file — chọn/ghép nội dung, xóa marker <<<<<<< ======= >>>>>>>
vim conflicted.txt

# 2. Đánh dấu đã giải quyết
git add conflicted.txt

# 3. Hoàn tất merge
git commit                        # dùng message mặc định của merge

# Hoặc hủy:
git merge --abort
```

**Các chiến lược merge nâng cao** (`-X`):

```bash
git merge -X ours <branch>        # conflict → auto chọn "ours"
git merge -X theirs <branch>      # conflict → auto chọn "theirs"
git merge -X patience <branch>    # dùng patience diff (chính xác hơn cho code)
git merge -X renormalize <branch> # bỏ qua khác biệt line ending
git merge -s ours <branch>        # STRATEGY ours (khác -X ours) — bỏ hoàn toàn theirs
```

**`-X ours` vs `-s ours`**: 
- `-X ours`: **chiến lược merge mặc định (recursive)**, chỉ áp dụng "ours wins" cho **các conflict**, các thay đổi không conflict vẫn merge.
- `-s ours`: **chiến lược khác hoàn toàn** — bỏ qua toàn bộ nội dung của theirs, chỉ tạo merge commit với tree = ours. Dùng để **đánh dấu** nhánh đã merge (vd: bỏ qua một branch mà không muốn nội dung).

### 4.5 Rename detection — Cái bẫy

Nếu một file bị đổi tên ở ours, và bị sửa nội dung ở theirs → Git cố detect rename (dựa trên similarity, ngưỡng mặc định 50%). Nếu không detect được → conflict kiểu "deleted by us" / "added by them". Có thể điều chỉnh:

```bash
git merge -X rename-threshold=70% <branch>
```

## 5. Rebase — Viết lại lịch sử

### 5.1 Định nghĩa và cơ chế

**Rebase** là thao tác **di chuyển** một chuỗi commit từ base cũ sang base mới. Về bản chất, Git **tạo commit mới** (SHA mới) với nội dung tương tự.

```
Trước rebase:
A ← B ← C ← D   (main)
         ↑
         E ← F   (feature)

git switch feature
git rebase main

Sau rebase:
A ← B ← C ← D   (main)
             ↑
             E' ← F'   (feature)
```

**Lý thuyết then chốt**:
- `E'` và `F'` là **commit mới** — SHA khác `E`, `F` (vì parent khác và committer date khác).
- Commit gốc `E`, `F` **không bị xóa** — chúng trở thành **unreachable** (chỉ reflog giữ).
- Lịch sử **tuyến tính**: như thể `E`, `F` được viết ngay sau `D`.
- **Không có merge commit** — lịch sử sạch.

### 5.2 Rebase vs Merge — Lý thuyết so sánh

|                            | Merge                     | Rebase                              |
| -------------------------- | ------------------------- | ----------------------------------- |
| Tạo commit mới             | Merge commit              | Commit mới (SHA khác)               |
| Lịch sử                    | Phân nhánh (giữ topology) | Tuyến tính (làm phẳng)              |
| Viết lại lịch sử           | Không                     | **Có**                              |
| An toàn cho shared history | ✅                         | ❌ (gây rối cho team)                |
| Conflict                   | Giải quyết 1 lần          | Giải quyết **từng commit**          |
| Dễ bisect                  | Đôi khi khó               | Dễ hơn (tuyến tính)                 |
| Attribution                | Giữ nguyên                | **Đổi committer date** (author giữ) |

**Quy tắc vàng**: **Không bao giờ rebase commit đã push lên branch chia sẻ** (main, develop). Chỉ rebase branch **cá nhân** hoặc commit **chưa push**.

### 5.3 Interactive rebase — Công cụ mạnh nhất

```bash
git rebase -i HEAD~5
git rebase -i <base-commit>
```

Mở editor với danh sách commit (cũ → mới):

```
pick a1b2c3d feat: add login
pick e4f5g6h fix: typo
pick i7j8k9l feat: add logout
pick m0n1o2p wip
```

Các lệnh:

| Lệnh     | Viết tắt | Chức năng                                         |
| -------- | -------- | ------------------------------------------------- |
| `pick`   | `p`      | Giữ commit                                        |
| `reword` | `r`      | Sửa message (giữ nội dung)                        |
| `edit`   | `e`      | Dừng lại để amend nội dung                        |
| `squash` | `s`      | Gộp vào commit trước, **giữ message** (mở editor) |
| `fixup`  | `f`      | Gộp vào commit trước, **bỏ message**              |
| `drop`   | `d`      | Xóa commit                                        |
| `exec`   | `x`      | Chạy lệnh shell                                   |
| `break`  | `b`      | Dừng (chèn `break` point)                         |

**Sắp xếp lại dòng = sắp xếp lại commit.** Xóa dòng = xóa commit. Đây là công cụ để **dọn dẹp lịch sử trước khi merge** vào branch chính.

### 5.4 Rebase nâng cao

```bash
git rebase --onto <newbase> <upstream> <branch>
```

**Lý thuyết**: "Lấy các commit của `branch` mà **không thuộc** `upstream`, rồi áp lên `newbase`". Công thức: `newbase..branch` rebase onto `newbase`.

Ví dụ: tách branch con khỏi branch cha:
```
A ← B ← C   (main)
         ↑
         D ← E ← F   (feature-parent)
                 ↑
                 G ← H   (feature-child — tách từ feature-parent)

git rebase --onto main feature-parent feature-child
# → G', H' áp lên main, bỏ D, E, F
```

### 5.5 Conflict khi rebase

Rebase có thể conflict **ở từng commit** (vì áp lại tuần tự). Quy trình:

```bash
git rebase main
# CONFLICT...

# 1. Sửa file
vim conflicted.txt
git add conflicted.txt

# 2. Tiếp tục
git rebase --continue

# Hoặc bỏ qua commit hiện tại (nguy hiểm — mất nội dung)
git rebase --skip

# Hoặc hủy toàn bộ rebase
git rebase --abort
```

**Lý thuyết**: `--skip` **bỏ commit đang conflict** — nội dung của nó mất. Chỉ dùng khi chắc chắn commit đó không cần (vd: đã bị cherry-pick).

### 5.6 Rebase an toàn — `--autostash`, `--rebase-merges`

```bash
git rebase --autostash main         # tự stash thay đổi chưa commit trước rebase
git rebase --rebase-merges main     # giữ cấu trúc merge commit (thay --preserve-merges cũ)
git rebase --keep-base              # giữ base cũ (dùng cho interactive)
```

**`--rebase-merges`** quan trọng khi rebase branch có chứa merge commit — mặc định rebase **làm phẳng** merge (mất cấu trúc). `--rebase-merges` giữ lại topology.

## 6. Cherry-pick — "Nhặt" commit

### 6.1 Định nghĩa

**Cherry-pick** = áp **một commit cụ thể** từ branch khác lên branch hiện tại. Khác merge (lấy cả nhánh) và rebase (áp chuỗi commit).

```bash
git cherry-pick <sha>
git cherry-pick <sha1> <sha2>       # nhiều commit
git cherry-pick <start>..<end>      # range
git cherry-pick -x <sha>            # thêm dòng "(cherry picked from ...)" vào message
git cherry-pick --no-commit <sha>   # áp vào index, không commit
git cherry-pick --continue / --abort / --skip   # xử lý conflict
```

### 6.2 Lý thuyết: Tại sao không "copy" mà lại "tái tạo"?

Cherry-pick **không** copy nguyên commit — nó **tính diff** giữa commit và parent, rồi **áp diff đó** lên HEAD hiện tại, tạo **commit mới** (SHA mới). Vì vậy:

- Commit gốc vẫn tồn tại ở branch cũ.
- Commit mới ở branch hiện tại có nội dung tương tự nhưng SHA khác.
- **Có thể conflict** nếu code xung quanh khác.

### 6.3 Khi nào dùng cherry-pick?

- **Backport hotfix**: fix bug trên `main`, cherry-pick về branch release (vd: `release/1.5`).
- **Áp commit nhỏ** từ branch thử nghiệm mà không muốn merge cả branch.
- **Cứu commit** sau khi làm mất (từ reflog).

**Cạm bẫy**: Cherry-pick nhiều lần từ cùng branch → tạo **commit trùng lặp nội dung**, và khi merge branch đó sau này → conflict khó hiểu. `git cherry` có thể detect commit đã cherry-pick:

```bash
git cherry -v main feature
# +  a1b2c3d... commit A (chưa cherry-pick)
# -  e4f5g6h... commit B (đã cherry-pick — có patch-id tương đương)
```

## 7. Branching strategies — Lý thuyết workflow

Đây là phần **áp dụng lý thuyết** vào thực tế — các chiến lược phổ biến và lý do đằng sau.

### 7.1 Git Flow (Vincent Driessen, 2010)

**Cấu trúc branch**:
- `main` (hoặc `master`): production, chỉ merge từ `release`/`hotfix`.
- `develop`: integration, chứa code mới nhất đã merge.
- `feature/*`: tách từ `develop`, merge về `develop`.
- `release/*`: tách từ `develop`, chuẩn bị release, merge về `main` + `develop`.
- `hotfix/*`: tách từ `main`, merge về `main` + `develop`.

**Ưu**: Rõ ràng vai trò, phù hợp release theo version (mobile app, desktop, sản phẩm có version cứng).
**Nhược**: Nặng nề, nhiều branch, không phù hợp CI/CD (liên tục deploy).

### 7.2 GitHub Flow (đơn giản)

- `main` luôn deploy được.
- Mỗi feature = 1 branch tách từ `main`.
- Tạo **Pull Request** → review → merge về `main`.
- Deploy ngay sau merge.

**Ưu**: Đơn giản, phù hợp web app deploy liên tục.
**Nhược**: Không quản lý version release phức tạp; branch tồn tại ngắn.

### 7.3 Trunk-Based Development

- Chỉ `main` (trunk) là branch dài hạn.
- Feature branch **rất ngắn** (< 1 ngày) hoặc dùng **feature flag** thay vì branch.
- Merge thường xuyên (nhiều lần/ngày).

**Ưu**: Giảm "merge hell", phù hợp CI/CD nghiêm ngặt, Google/Facebook dùng.
**Nhược**: Yêu cầu kỷ luật cao, test tự động mạnh, feature flag system.

### 7.4 Lý thuyết chung: Trade-off

| Yếu tố                   | Git Flow   | GitHub Flow | Trunk-Based        |
| ------------------------ | ---------- | ----------- | ------------------ |
| Số branch sống song song | Nhiều      | Ít          | Rất ít (gần như 0) |
| Thời gian sống branch    | Dài        | Ngắn        | Rất ngắn           |
| Yêu cầu CI/CD            | Thấp       | Trung bình  | Cao                |
| Yêu cầu test             | Trung bình | Trung bình  | Rất cao            |
| Rủi ro conflict          | Cao        | Trung bình  | Thấp               |
| Version release          | Cứng       | Mềm (tag)   | Tag                |

**Không có "chiến lược đúng"** — chọn theo: quy mô team, tần suất release, loại sản phẩm, văn hóa CI/CD.

## 8. So sánh branch — Công cụ debug

### 8.1 `git log` với range

```bash
git log main..feature              # commit có ở feature, không ở main
git log feature..main              # commit có ở main, không ở feature
git log main...feature             # symmetric diff (cả 2 phía)
git log --left-right --graph main...feature   # đánh dấu < (main) / > (feature)
```

### 8.2 `git diff` giữa branch

```bash
git diff main..feature             # diff cuối
git diff main...feature            # diff từ common ancestor (đúng nghĩa "thay đổi của feature")
git diff --stat main..feature
git diff --name-only main..feature
```

**`..` vs `...` trong diff**: `A..B` = diff trực tiếp giữa A và B. `A...B` = diff giữa **merge base** của A, B và B — tức "feature đã thay đổi gì so với lúc tách nhánh". Đây là công cụ chuẩn cho code review.

### 8.3 `git merge-base`

```bash
git merge-base main feature        # common ancestor
git merge-base --is-ancestor A B   # exit code: A có phải ancestor của B?
git merge-base --fork-point main  # điểm tách (an toàn hơn khi rebase)
```

### 8.4 `git branch --merged` / `--no-merged`

```bash
git branch --merged main           # branch đã merge vào main (an toàn để xóa)
git branch --no-merged main        # branch chưa merge (cảnh báo trước khi xóa)
git branch -r --merged main        # remote-tracking tương tự
```

**Ứng dụng**: Dọn branch đã merge — lệnh kinh điển:
```bash
git branch --merged main | grep -v "main\|develop" | xargs git branch -d
```

## 9. Các chủ đề nâng cao

### 9.1 Orphan branch — Branch không có lịch sử

```bash
git switch --orphan gh-pages        # branch mới với working tree rỗng, không parent
git checkout --orphan gh-pages      # syntax cũ
```

**Lý thuyết**: Branch **không có commit cha** — bắt đầu DAG mới hoàn toàn. Thường dùng cho:
- `gh-pages` (GitHub Pages) — nội dung build riêng.
- Branch chứa documentation, không liên quan code.
- **Initial commit** của repo — bản thân `main` ban đầu cũng là orphan.

### 9.2 `git worktree` — Nhiều working tree cùng lúc

```bash
git worktree add ../hotfix-dir hotfix    # checkout hotfix vào thư mục khác
git worktree list
git worktree remove ../hotfix-dir
```

**Lý thuyết**: Thông thường 1 repo = 1 working tree. `worktree` cho phép **nhiều working tree** cùng trỏ về 1 `.git/` — mỗi worktree ở một branch khác nhau. Rất hữu ích khi:
- Cần sửa hotfix khẩn cấp trong khi đang code feature (không muốn stash/switch).
- Build song song nhiều branch.

**Cơ chế**: Mỗi worktree là 1 thư mục riêng, có file `.git` (không phải thư mục) trỏ về `.git/worktrees/<name>` chính. Objects, refs **dùng chung** — tiết kiệm dung lượng.

### 9.3 `git stash` — Branch tạm thời

```bash
git stash                          # cất thay đổi chưa commit
git stash push -m "message"        # có message
git stash -u                       # bao gồm untracked
git stash list
git stash pop                      # apply + xóa khỏi stack
git stash apply                    # apply, giữ trong stack
git stash drop                     # xóa stash
git stash branch <name>            # tạo branch từ stash
```

**Lý thuyết**: Stash lưu **index + working tree** dưới dạng **commit object đặc biệt** (không thuộc branch nào, chỉ reachable qua `refs/stash`). Đây là "branch tạm ẩn" — không phải branch thật.

### 9.4 Branch protection (server-side)

Trên GitHub/GitLab:
- **Protected branches**: không ai push trực tiếp, chỉ merge qua PR.
- **Required reviews**: cần ≥N approval.
- **Required status checks**: CI phải pass.
- **Require linear history**: từ chối merge commit (khuyến khích rebase/squash).
- **Restrict who can push/merge**.

Đây là **policy layer** trên Git — Git bản thân không có khái niệm này; server implement.

### 9.5 Branch naming conventions

Không có chuẩn chính thức, nhưng phổ biến:
- `feature/JIRA-123-add-login`
- `bugfix/JIRA-456-fix-crash`
- `hotfix/v1.5.1`
- `release/v2.0`
- `chore/update-deps`
- `docs/readme`

**Lý thuyết**: Tên branch không ảnh hưởng Git, nhưng ảnh hưởng **con người** — giúp filter, tìm kiếm, tự động hóa (CI trigger theo prefix).

## 10. Tổng kết lý thuyết

| Khái niệm              | Định nghĩa cốt lõi                        | Lưu ý                                  |
| ---------------------- | ----------------------------------------- | -------------------------------------- |
| **Branch**             | File 41 byte trong `refs/heads/` chứa SHA | Không phải copy — chỉ là con trỏ       |
| **HEAD**               | Symbolic ref → branch                     | Attached vs detached                   |
| **Detached HEAD**      | HEAD trỏ SHA trực tiếp                    | Commit có thể mất nếu không tạo branch |
| **Fast-forward**       | Di chuyển con trỏ, không tạo commit       | Khi target là ancestor                 |
| **Three-way merge**    | Tạo merge commit 2 parent                 | Dùng base, ours, theirs                |
| **Conflict**           | Cùng vùng bị sửa khác nhau                | Giải quyết tay, `git add` + `commit`   |
| **Rebase**             | Áp lại commit lên base mới                | Tạo SHA mới, **viết lại lịch sử**      |
| **Interactive rebase** | Sắp xếp/squash/edit/drop commit           | Công cụ dọn lịch sử trước merge        |
| **Cherry-pick**        | Áp 1 commit cụ thể                        | Tạo commit mới, có thể conflict        |
| **Merge base**         | Common ancestor                           | Nền tảng của 3-way merge               |
| **`A..B` vs `A...B`**  | Direct diff vs từ common ancestor         | `...` đúng cho code review             |
| **Worktree**           | Nhiều working tree chung 1 repo           | Không cần stash/switch                 |

**Nguyên tắc vàng**:
1. **Branch = con trỏ**, không phải thư mục — tạo/xóa gần như miễn phí.
2. **Không rebase/amend commit đã push lên branch chia sẻ** — gây rối lịch sử team.
3. **Detached HEAD**: tạo branch ngay nếu có commit quan trọng, trước khi `switch` đi.
4. **Merge vs Rebase**: merge giữ topology (an toàn cho shared), rebase làm phẳng (sạch cho branch cá nhân).
5. **Cherry-pick có thể tạo commit trùng** — dùng `git cherry` để kiểm tra trước khi merge.
6. **Không có branching strategy đúng cho mọi team** — chọn theo quy mô, tần suất release, độ trưởng thành CI/CD.
