# Git Reflog — Restoring Lost Snapshots: Giải thích lý thuyết chi tiết

---

## 1. Bản chất: Reflog là gì?

### 1.1 Định nghĩa cốt lõi

**Reflog** (reference log) là **nhật ký ghi lại mọi sự di chuyển của các ref** (đặc biệt là `HEAD` và branch) trong repo local. Nó là **"hộp đen"** của Git — ghi lại **mọi thao tác làm thay đổi con trỏ ref**, kể cả những thao tác "phá hủy" như `reset --hard`, `rebase`, `amend`, `branch -D`.

> **Điểm lý thuyết quan trọng nhất**: **Reflog là công cụ cứu hộ số một của Git**. Nó cho phép bạn **quay ngược thời gian** — khôi phục commit "đã mất", branch "đã xóa", trạng thái "trước khi rebase". Nhưng nó **chỉ tồn tại ở local** — không được push, không được clone, không chia sẻ với ai.

### 1.2 Reflog vs `git log` — Khác biệt căn bản

Đây là điểm phân biệt **quan trọng nhất**:

|                     | `git log`                   | `git reflog`               |
| ------------------- | --------------------------- | -------------------------- |
| **Đọc gì**          | DAG commit (theo parent)    | Nhật ký di chuyển ref      |
| **Phạm vi**         | Commit **reachable** từ ref | **Mọi** di chuyển của ref  |
| **Commit "mất"**    | ❌ Không thấy                | ✅ Thấy                     |
| **Commit "mồ côi"** | ❌ Không thấy                | ✅ Thấy                     |
| **Chia sẻ**         | ✅ (qua clone/push)          | ❌ Chỉ local                |
| **Bị GC xóa**       | Không (nếu reachable)       | Có (sau ~90 ngày)          |
| **Mục đích**        | Xem lịch sử dự án           | Cứu hộ, debug, audit local |

**Ví dụ minh họa**:

```
Lịch sử thực:
  A ← B ← C ← D ← E   (main)

Bạn lỡ: git reset --hard C

Sau reset:
  A ← B ← C           (main)     ← git log thấy C, B, A
      D ← E           (unreachable)  ← git log KHÔNG thấy

  git reflog:
  c3d4e5f HEAD@{0}: reset: moving to C
  e5f6g7h HEAD@{1}: commit: E       ← commit E bị "mất"!
  d5e6f7g HEAD@{2}: commit: D
  c3d4e5f HEAD@{3}: commit: C
```

**Kết luận**: `git log` **chỉ thấy quá khứ hiện tại** (những gì còn reachable). `git reflog` **thấy cả quá khứ đã bị bỏ** — đó là lý do nó cứu được commit "mất".

### 1.3 Tại sao reflog tồn tại?

**Lý thuyết thiết kế của Git**:
- Git là **content-addressable filesystem** — commit không bị xóa khi "không còn ai trỏ tới", chỉ trở thành **unreachable**.
- **Garbage collector (GC)** dọn dẹp unreachable objects — nhưng **chờ** (mặc định ~30 ngày cho unreachable, ~90 ngày cho reflog).
- **Reflog là "bộ nhớ đệm" của GC** — nó giữ commit unreachable "sống" thêm thời gian, cho bạn cơ hội cứu.

**Hệ quả**: Reflog không phải "tính năng thêm" — nó là **cơ chế an toàn cốt lõi** của Git. Không có reflog, mọi thao tác `reset --hard`/`rebase` sẽ là **không thể hoàn tác**.

## 2. Cơ chế bên trong — Reflog lưu ở đâu và như thế nào?

### 2.1 Vị trí lưu trữ

Reflog là **file text** trong `.git/logs/`:

```bash
.git/logs/
├── HEAD                          # reflog của HEAD
├── refs/
│   ├── heads/
│   │   ├── main                  # reflog của branch main
│   │   ├── feature/login         # reflog của feature/login
│   │   └── ...
│   ├── remotes/
│   │   └── origin/
│   │       ├── main              # reflog của origin/main
│   │       └── ...
│   └── stash                     # reflog của stash
```

**Mỗi ref có reflog riêng**. `HEAD` có reflog đặc biệt — ghi **mọi di chuyển** của HEAD (kể cả khi đổi branch).

### 2.2 Format một dòng reflog

```bash
cat .git/logs/HEAD
```

Output:
```
0000000000000000000000000000000000000000 a1b2c3d4e5f6... Alice <alice@x.com> 1700000000 +0700	commit (initial): Initial commit
a1b2c3d4e5f6... e5f6g7h8i9j0... Alice <alice@x.com> 1700000100 +0700	commit: feat: add login
e5f6g7h8i9j0... c3d4e5f6a7b8... Alice <alice@x.com> 1700000200 +0700	reset: moving to HEAD~1
```

**Cấu trúc một dòng** (phân tách bằng TAB):

```
<old-sha> <new-sha> <author-name> <<email>> <timestamp> <timezone>\t<message>
```

| Trường        | Ý nghĩa                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------ |
| `<old-sha>`   | SHA **trước** thao tác (0000... nếu là lần đầu)                                                        |
| `<new-sha>`   | SHA **sau** thao tác (đích của ref)                                                                    |
| `<author>`    | Người thực hiện (từ config user.name/email)                                                            |
| `<timestamp>` | Unix timestamp                                                                                         |
| `<timezone>`  | Múi giờ (+0700)                                                                                        |
| `<message>`   | Mô tả thao tác: `commit:`, `reset:`, `rebase:`, `checkout:`, `merge:`, `pull:`, `branch:`, `clone:`... |

**Lý thuyết**: Reflog là **append-only log** — mỗi thao tác ghi thêm một dòng. **Không bao giờ sửa** dòng cũ. Chỉ bị **cắt bớt** (expire) khi quá cũ hoặc quá nhiều.

### 2.3 Các loại message phổ biến

| Message prefix      | Nguyên nhân                                       |
| ------------------- | ------------------------------------------------- |
| `commit:`           | `git commit` (thường)                             |
| `commit (amend):`   | `git commit --amend`                              |
| `commit (initial):` | Commit đầu tiên                                   |
| `commit (merge):`   | Merge commit                                      |
| `reset:`            | `git reset`                                       |
| `rebase:`           | `git rebase` (start/finish)                       |
| `rebase -i:`        | Interactive rebase                                |
| `rebase (finish):`  | Hoàn tất rebase                                   |
| `checkout:`         | `git checkout` / `git switch` (đổi branch/commit) |
| `merge:`            | `git merge`                                       |
| `pull:`             | `git pull`                                        |
| `branch:`           | Tạo/xóa/đổi tên branch                            |
| `clone:`            | `git clone` (reflog đầu tiên)                     |
| `cherry-pick:`      | `git cherry-pick`                                 |
| `revert:`           | `git revert`                                      |
| `stash:`            | `git stash` (apply/pop/drop)                      |

### 2.4 Reflog của branch và HEAD

**Điểm tinh tế quan trọng**:

- **Reflog của `HEAD`** (`.git/logs/HEAD`): ghi **mọi di chuyển** của HEAD — kể cả khi đổi branch, detach, reset, commit...
- **Reflog của branch** (`.git/logs/refs/heads/main`): chỉ ghi **di chuyển của branch đó** — không ghi khi HEAD detach hoặc đổi branch.

**Ví dụ**:

```bash
git switch feature             # HEAD di chuyển → ghi vào logs/HEAD
git commit                     # feature + HEAD di chuyển → ghi cả hai
git switch main                # HEAD di chuyển → chỉ ghi logs/HEAD
```

**Hệ quả**: `git reflog` (mặc định) đọc `logs/HEAD` — thấy **mọi thứ**. `git reflog show main` đọc `logs/refs/heads/main` — chỉ thấy **di chuyển của branch main**.

## 3. Cú pháp và các biến thể

### 3.1 Cú pháp cơ bản

```bash
git reflog                     # reflog của HEAD (mặc định)
git reflog show <ref>          # reflog của ref cụ thể
git reflog show main           # reflog của branch main
git reflog show origin/main    # reflog của remote-tracking
git reflog show stash          # reflog của stash
```

**`git reflog` = `git reflog show HEAD`** — viết tắt.

### 3.2 Các tùy chọn quan trọng

```bash
git reflog --date=iso              # timestamp dạng ISO
git reflog --date=relative         # "2 hours ago"
git reflog --date=unix             # epoch
git reflog -n 10                   # 10 dòng gần nhất
git reflog --all                   # tất cả refs
git reflog --since="2 days ago"
git reflog --until="2024-01-01"
git reflog --grep="reset"          # lọc theo message
```

### 3.3 Các lệnh con của `git reflog`

```bash
git reflog show <ref>              # hiển thị reflog
git reflog expire <ref>            # xóa entry cũ (thủ công)
git reflog delete <ref>@{n}        # xóa entry cụ thể
git reflog exists <ref>            # kiểm tra reflog tồn tại
```

**`expire` và `delete`** — dùng cẩn thận, thường không cần thiết (GC tự động làm).

### 3.4 Alias `@{n}` — "Tham chiếu thời gian"

Reflog cho phép tham chiếu ref **theo thời điểm** qua cú pháp `@{n}`:

```bash
HEAD@{0}                      # HEAD hiện tại (mới nhất)
HEAD@{1}                      # HEAD trước thao tác gần nhất
HEAD@{2}                      # trước đó nữa
HEAD@{5}                      # 5 thao tác trước
main@{3}                      # main 3 thao tác trước
origin/main@{yesterday}       # origin/main ngày hôm qua
HEAD@{2.days.ago}             # 2 ngày trước
HEAD@{2024-01-15}             # ngày cụ thể
```

**Lý thuyết**: `@{n}` **không phải** "n commit trước" (như `~n`) — nó là **"n thao tác reflog trước"**. Một `git commit` = 1 entry; một `git reset` = 1 entry; một `git switch` = 1 entry... Đây là điểm khác biệt căn bản với `~n`/`^n`.

**Ví dụ minh họa**:

```
git reflog:
  e5f6g7h HEAD@{0}: commit: feat: E
  d5e6f7g HEAD@{1}: commit: feat: D
  c3d4e5f HEAD@{2}: reset: moving to C
  c3d4e5f HEAD@{3}: commit: feat: C
  b2c3d4e HEAD@{4}: commit: feat: B
  a1b2c3d HEAD@{5}: commit (initial): Initial commit

HEAD@{1} = d5e6f7g   ← commit D
HEAD@{3} = c3d4e5f   ← commit C (cùng SHA với HEAD@{2} nhưng khác thời điểm!)
```

**Điểm tinh tế**: `HEAD@{2}` và `HEAD@{3}` **cùng trỏ tới `c3d4e5f`** — vì `reset` không tạo commit mới, chỉ di chuyển ref. Nhưng chúng là **hai entry khác nhau** (một do commit, một do reset).

## 4. Đọc hiểu output reflog

### 4.1 Output mẫu

```bash
git reflog
```

```
e5f6g7h (HEAD -> main) HEAD@{0}: commit: feat: add logout
c3d4e5f HEAD@{1}: reset: moving to HEAD~1
f7g8h9i HEAD@{2}: commit (amend): feat: add login form
a1b2c3d HEAD@{3}: commit: feat: add login
b2c3d4e HEAD@{4}: commit (initial): Initial commit
```

**Cột**:
1. **Short SHA** — commit mà ref trỏ tới **sau** thao tác.
2. **Ref name** — `(HEAD -> main)` nếu là HEAD hiện tại.
3. **`HEAD@{n}`** — index trong reflog.
4. **Message** — thao tác gì đã xảy ra.

### 4.2 Đọc theo "dòng thời gian ngược"

- `HEAD@{0}` = **hiện tại** (mới nhất).
- `HEAD@{1}` = **trước thao tác gần nhất**.
- `HEAD@{n}` = **càng lớn càng cũ**.

**Đây là điểm dễ nhầm**: `HEAD@{0}` là **hiện tại**, không phải "commit đầu tiên". Số càng lớn → càng lùi về quá khứ.

### 4.3 Ví dụ đọc chi tiết

```
e5f6g7h HEAD@{0}: commit: feat: add logout
```
→ "Ở thời điểm hiện tại (`HEAD@{0}`), HEAD trỏ tới `e5f6g7h`, vì vừa commit `feat: add logout`."

```
c3d4e5f HEAD@{1}: reset: moving to HEAD~1
```
→ "Trước đó (`HEAD@{1}`), HEAD trỏ tới `c3d4e5f`, vì vừa `reset` về `HEAD~1`. Commit trước `e5f6g7h` **bị bỏ**."

```
f7g8h9i HEAD@{2}: commit (amend): feat: add login form
```
→ "Trước nữa (`HEAD@{2}`), HEAD trỏ tới `f7g8h9i`, vì vừa `amend` commit `feat: add login form`. Commit gốc (trước amend) **bị bỏ**."

### 4.4 Kết hợp với `git log`

```bash
git log -g                         # "log theo reflog" — như reflog nhưng format log
git log -g --oneline
git log -g --date=iso
git log -g HEAD@{2}..HEAD@{0}     # range theo reflog
```

**Lý thuyết**: `git log -g` = `git reflog` nhưng hiển thị **đầy đủ commit object** (diff, author, date...) thay vì chỉ message reflog. Hữu ích khi cần xem chi tiết commit bị mất.

## 5. Cứu commit đã mất — Quy trình chuẩn

### 5.1 Kịch bản 1: `reset --hard` mất commit

```bash
# Bước 1: Lỡ tay
git reset --hard HEAD~3
# → Mất 3 commit gần nhất

# Bước 2: Xem reflog
git reflog
# e5f6g7h HEAD@{0}: reset: moving to HEAD~3
# f7g8h9i HEAD@{1}: commit: feat: 3       ← commit cuối trước reset
# a1b2c3d HEAD@{2}: commit: feat: 2
# b2c3d4e HEAD@{3}: commit: feat: 1
# c3d4e5f HEAD@{4}: commit: feat: 0
# ...

# Bước 3: Cứu
git reset --hard HEAD@{1}          # cách 1: dùng index reflog
git reset --hard f7g8h9i           # cách 2: dùng SHA
# → Đã cứu 3 commit!
```

### 5.2 Kịch bản 2: Rebase sai

```bash
git rebase main
# → Lịch sử bị thay đổi, conflict nhiều, không ưng ý

git reflog
# ... HEAD@{0}: rebase (finish): returning to refs/heads/feature
# ... HEAD@{1}: rebase (start): checkout main
# ...
# ... HEAD@{15}: commit: feat: cuối cùng trước rebase   ← cần cái này

git reset --hard HEAD@{15}         # cứu
# hoặc
git reset --hard ORIG_HEAD         # nhanh hơn (ORIG_HEAD = trước rebase)
```

### 5.3 Kịch bản 3: Amend commit nhưng muốn lấy lại commit gốc

```bash
git commit --amend -m "feat: sửa message"
# → Commit gốc bị thay thế

git reflog
# a1b2c3d HEAD@{0}: commit (amend): feat: sửa message
# b2c3d4e HEAD@{1}: commit: feat: message gốc       ← commit gốc

# Xem commit gốc
git show b2c3d4e

# Cứu nếu cần (tạo branch mới)
git branch rescue b2c3d4e           # tạo branch mới từ commit gốc
```

**Lý thuyết**: `--amend` tạo commit **mới** thay thế commit cũ. Commit cũ vẫn trong objects + reflog. Tạo branch mới để giữ nó — **không** `reset --hard` (vì sẽ mất commit amend).

### 5.4 Kịch bản 4: Xóa branch nhầm

```bash
git branch -D feature              # xóa branch feature
# → Commit của feature vẫn trong objects, nhưng unreachable

git reflog
# ... HEAD@{5}: checkout: moving from feature to main   ← SHA của feature tại thời điểm checkout
# ...

# Cứu
git branch feature HEAD@{5}        # tạo lại branch
# hoặc
git branch feature a1b2c3d         # nếu biết SHA
```

**Lý thuyết**: `git branch -D` **chỉ xóa ref**, không xóa commit. Reflog của HEAD ghi lại SHA của feature tại lần checkout cuối → cứu được.

**Cẩn thận**: Nếu bạn **chưa bao giờ checkout branch đó** sau khi tạo, hoặc **đã GC**, có thể không cứu được. `git fsck --lost-found` là "phao" cuối (mục 8).

### 5.5 Kịch bản 5: Merge sai

```bash
git merge feature
# Merge xong, thấy sai, muốn hủy

git reflog
# ... HEAD@{0}: merge feature: Merge made by the 'ort' strategy
# ... HEAD@{1}: commit: feat: cuối trước merge   ← cần cái này

git reset --hard HEAD@{1}          # hủy merge
# hoặc
git reset --hard ORIG_HEAD         # nhanh hơn
# hoặc
git merge --abort                   # nếu còn đang merge (chưa commit)
```

### 5.6 Kịch bản 6: Pull sai (merge/rebase)

```bash
git pull                            # pull xong, lịch sử rối

git reflog
# ... HEAD@{0}: pull origin main: Merge made by...
# ... HEAD@{1}: commit: feat: cuối trước pull

git reset --hard HEAD@{1}          # hủy pull
git fetch origin                    # fetch lại, xem kỹ
git log --oneline main..origin/main
# ... quyết định merge/rebase có ý thức
```

### 5.7 Kịch bản 7: Commit trên detached HEAD bị mất

```bash
git checkout a1b2c3d                # detach
# ... commit ...
git checkout main                  # rời detached → commit mất (unreachable)

git reflog
# ... HEAD@{2}: commit: feat: trên detached   ← cần cái này
# ... HEAD@{3}: checkout: moving from main to a1b2c3d

git branch rescue HEAD@{2}          # tạo branch từ commit đó
```

**Lý thuyết**: Detached HEAD commit **không thuộc branch nào**. Khi rời đi → unreachable. Reflog của HEAD ghi lại SHA → cứu được.

### 5.8 Kịch bản 8: Stash pop conflict rồi mất stash

```bash
git stash pop
# CONFLICT... hoảng, gõ git checkout .
# → Mất thay đổi + stash đã pop

git reflog show stash
# ... stash@{0}: WIP on main: a1b2c3d feat: ...
# → Stash vẫn còn trong reflog!

git stash apply stash@{0}          # áp lại
```

**Lý thuyết**: `git stash pop` **xóa** stash khỏi `refs/stash`, nhưng **reflog của stash vẫn giữ**. `stash@{0}` có thể không còn, nhưng `stash@{1}`, `stash@{2}`... vẫn còn — và reflog giữ SHA.

### 5.9 Bảng tóm tắt các kịch bản

| Thao tác lỡ          | Cứu bằng                                     |
| -------------------- | -------------------------------------------- |
| `reset --hard`       | `git reset --hard HEAD@{n}`                  |
| `rebase`             | `git reset --hard ORIG_HEAD` hoặc `HEAD@{n}` |
| `commit --amend`     | `git branch rescue HEAD@{1}`                 |
| `branch -D`          | `git branch <name> HEAD@{n}`                 |
| `merge`              | `git reset --hard ORIG_HEAD`                 |
| `pull`               | `git reset --hard HEAD@{n}`                  |
| Detached commit      | `git branch rescue HEAD@{n}`                 |
| `stash pop` conflict | `git stash apply stash@{n}`                  |

## 6. `ORIG_HEAD` — "Reflog tức thời"

### 6.1 Định nghĩa

`ORIG_HEAD` là **ref đặc biệt** — Git tự động lưu **vị trí HEAD trước thao tác nguy hiểm gần nhất** (reset, merge, rebase, pull, cherry-pick).

```bash
git rev-parse ORIG_HEAD
# f7g8h9i...
```

### 6.2 Lý thuyết

- Được **tự động cập nhật** bởi các lệnh "nguy hiểm" — không cần làm gì.
- **Chỉ giữ 1 giá trị** — thao tác nguy hiểm mới nhất.
- **Không có index** (`@{n}`) — chỉ trỏ tới SHA.
- **Khác reflog**: reflog giữ **toàn bộ lịch sử**, `ORIG_HEAD` chỉ giữ **1 vị trí**.

### 6.3 Ứng dụng

```bash
git rebase main
# ... thấy sai ...
git reset --hard ORIG_HEAD         # hủy rebase — nhanh hơn reflog

git merge feature
# ... thấy sai ...
git reset --hard ORIG_HEAD         # hủy merge
```

**Lý thuyết**: `ORIG_HEAD` = "reflog của thao tác nguy hiểm gần nhất". Nhanh hơn `reflog` khi mới lỡ tay — nhưng **không cứu được nếu đã làm thêm thao tác khác** (vì bị ghi đè).

### 6.4 So sánh `ORIG_HEAD` vs `HEAD@{1}`

|                   | `ORIG_HEAD`                              | `HEAD@{1}`                                |
| ----------------- | ---------------------------------------- | ----------------------------------------- |
| Được cập nhật khi | Thao tác nguy hiểm                       | Mọi thao tác di chuyển HEAD               |
| Giá trị           | Vị trí trước thao tác nguy hiểm gần nhất | Vị trí trước thao tác **bất kỳ** gần nhất |
| Bị ghi đè         | Thao tác nguy hiểm tiếp theo             | Mọi thao tác tiếp theo                    |
| Dùng khi          | Mới lỡ tay                               | Bất kỳ lúc nào (trong ~90 ngày)           |

**Điểm tinh tế**: `git commit` **không** cập nhật `ORIG_HEAD` (commit không nguy hiểm). Nên `ORIG_HEAD` có thể **khác** `HEAD@{1}`:
```bash
git reset --hard HEAD~3          # ORIG_HEAD = commit cũ
git commit -m "new"              # ORIG_HEAD vẫn = commit cũ, HEAD@{1} = commit trước commit này
```

## 7. Cấu hình và expiration

### 7.1 Cấu hình thời gian giữ

```bash
# Reflog của HEAD và branch
git config --global gc.reflogExpire "90 days"          # mặc định

# Reflog của unreachable commits
git config --global gc.reflogExpireUnreachable "30 days"   # mặc định

# Reflog của stash (giữ lâu hơn)
git config --global gc.reflogExpire "never"            # giữ vĩnh viễn (không khuyến nghị)
```

**Lý thuyết**:
- `gc.reflogExpire`: thời gian giữ **entry reflog** của refs còn tồn tại (branch còn).
- `gc.reflogExpireUnreachable`: thời gian giữ **entry của commit unreachable** (bị reset/rebase/branch -D).

**Mặc định**: HEAD/branch giữ 90 ngày; commit unreachable giữ 30 ngày. Sau đó, `git gc` (chạy tự động) sẽ dọn.

### 7.2 `gc.reflogExpire` chi tiết

```bash
# Giá trị có thể:
# - "90 days", "2 weeks", "3 months"...
# - "never" — giữ vĩnh viễn
# - "now" — xóa ngay (nguy hiểm)
# - "all" — alias của "never"
```

### 7.3 `git reflog expire` — Xóa thủ công

```bash
git reflog expire --expire=now --all       # xóa toàn bộ reflog NGAY
git reflog expire --expire=30.days --all   # xóa entry cũ hơn 30 ngày
git reflog expire --dry-run --all          # xem trước
```

**Cẩn thận**: `--expire=now --all` **xóa sạch reflog** → mất khả năng cứu hộ. Chỉ dùng khi chắc chắn (ví dụ: trước khi chia sẻ repo nhạy cảm).

### 7.4 `git gc` và reflog

```bash
git gc                              # dọn objects unreachable (theo reflog expire)
git gc --prune=now                  # dọn ngay — XÓA commit unreachable
git gc --prune=2.weeks.ago          # dọn objects cũ hơn 2 tuần
```

**Lý thuyết**: `git gc` = "garbage collect" — dọn objects không reachable. Nó **tuân theo reflog** — chỉ xóa khi reflog hết hạn. `--prune=now` **bỏ qua** reflog → xóa ngay.

**Cảnh báo**: `git gc --prune=now` **không thể hoàn tác** — mọi commit unreachable mất vĩnh viễn. Không bao giờ dùng trừ khi thực sự cần.

### 7.5 Cấu hình cho repo lớn

```bash
# Giữ reflog lâu hơn (an toàn hơn)
git config gc.reflogExpire "180 days"
git config gc.reflogExpireUnreachable "90 days"

# Hoặc tắt auto-gc (không khuyến nghị — repo sẽ phình)
git config gc.auto 0
```

## 8. Giới hạn của Reflog — Khi nào KHÔNG cứu được?

### 8.1 Reflog chỉ tồn tại ở local

**Điểm lý thuyết quan trọng nhất**:

- Reflog **không được push** lên remote.
- Reflog **không được clone** — mỗi máy có reflog riêng.
- Reflog **không chia sẻ** với đồng nghiệp.

**Hệ quả**:
- Nếu bạn `--force push` đè commit của đồng nghiệp → **reflog của họ** có thể cứu (nếu họ đã fetch), nhưng **reflog của bạn** không có.
- Nếu ổ cứng hỏng → reflog mất → **commit unreachable mất** (sau GC).
- Nếu clone repo mới → **không có reflog cũ** — chỉ có reflog từ lúc clone.

### 8.2 Reflog bị giới hạn thời gian

- **90 ngày** cho HEAD/branch (mặc định).
- **30 ngày** cho commit unreachable.
- Sau đó → `git gc` dọn → **không cứu được**.

**Giải pháp**: Cấu hình `gc.reflogExpire` dài hơn nếu cần. Hoặc backup định kỳ (tag, mirror).

### 8.3 Reflog không cứu được unstaged changes

**Điểm cực kỳ quan trọng**:

```
Reflog cứu được:
  ✅ Commit (Git object)
  ✅ Branch (ref)
  ✅ Staged changes (trong index — khó nhưng có thể)

Reflog KHÔNG cứu được:
  ❌ Unstaged changes trong working tree (chưa từng là Git object)
  ❌ File untracked (chưa từng biết tới Git)
```

**Lý thuyết**: Reflog ghi **di chuyển của ref** (commit SHA). Nó **không ghi** nội dung working tree. `reset --hard` xóa unstaged changes → **không có gì trong reflog để cứu**.

**Nguyên tắc**: **Commit thường xuyên** — mọi thứ đã commit đều cứu được; mọi thứ chưa commit đều có thể mất.

### 8.4 Reflog và `fsck` — Phao cuối cùng

Nếu reflog hết hạn (hoặc bị xóa), commit unreachable vẫn có thể trong objects **cho tới khi GC**. `git fsck --lost-found` tìm chúng:

```bash
git fsck --lost-found
# dangling commit a1b2c3d
# dangling commit e4f5g6h
# dangling blob ...
```

**Lý thuyết**: 
- **Dangling commit**: commit không reachable từ ref nào.
- **Dangling blob/tree**: object tương tự.
- Output nằm trong `.git/lost-found/commit/` (SHA file).

**Cứu**:
```bash
git show a1b2c3d                # xem commit
git branch rescue a1b2c3d       # tạo branch
```

**Giới hạn**: `fsck` chỉ tìm được **trong objects còn tồn tại** — nếu đã `gc --prune=now` → mất.

### 8.5 Bảng giới hạn

| Tình huống                                   | Cứu được?                                    |
| -------------------------------------------- | -------------------------------------------- |
| Commit bị reset/rebase/amend (trong 90 ngày) | ✅ Reflog                                     |
| Commit unreachable (trong 30 ngày)           | ✅ Reflog                                     |
| Commit unreachable (sau 30 ngày, trước GC)   | ⚠️ `fsck --lost-found`                        |
| Commit unreachable (sau GC)                  | ❌ Mất                                        |
| Branch bị xóa (trong 90 ngày)                | ✅ Reflog                                     |
| Stash bị pop/drop (trong 90 ngày)            | ✅ Reflog stash                               |
| **Unstaged changes**                         | ❌ **Không bao giờ**                          |
| **File untracked**                           | ❌ (không bị `reset` đụng, nhưng `clean` xóa) |
| Reflog bị xóa thủ công                       | ❌ (trừ `fsck` nếu chưa GC)                   |
| Force push đè commit (không có reflog)       | ⚠️ Phụ thuộc server                           |

## 9. Reflog vs các công cụ khác

### 9.1 So sánh toàn diện

| Công cụ                         | Cứu gì                                   | Phạm vi           | Giới hạn             |
| ------------------------------- | ---------------------------------------- | ----------------- | -------------------- |
| **`git reflog`**                | Mọi di chuyển ref                        | Local, ~90 ngày   | Chỉ local            |
| **`ORIG_HEAD`**                 | Vị trí trước thao tác nguy hiểm gần nhất | 1 giá trị         | Bị ghi đè            |
| **`git fsck --lost-found`**     | Objects unreachable                      | Local, tới khi GC | Chậm, thủ công       |
| **`git log -g`**                | Như reflog, format log                   | Local             | Như reflog           |
| **`git stash list`**            | Stash                                    | Local             | Chỉ stash            |
| **`git branch --contains`**     | Branch chứa commit                       | Local             | Chỉ commit reachable |
| **Server-side reflog** (GitHub) | Push events                              | Remote            | Qua UI/API, ~90 ngày |

### 9.2 Quy trình cứu hộ chuẩn

```
1. Bình tĩnh — đừng làm gì thêm (mỗi thao tác ghi đè reflog)
2. git reflog                    ← xem lịch sử
3. Tìm entry cần cứu             ← thường HEAD@{1} hoặc commit SHA
4. git show <sha>                ← xác nhận đúng commit
5. git reset --hard <sha>        ← cứu (nếu muốn di chuyển branch)
   HOẶC git branch rescue <sha>  ← cứu (nếu muốn giữ branch hiện tại)
6. git reflog                    ← xác nhận đã cứu
```

**Nguyên tắc**: **Đừng hoảng** — mỗi thao tác bạn làm (kể cả `git status`) có thể **không** ghi reflog, nhưng `git commit`/`git reset`/`git switch` **sẽ** ghi → có thể **ghi đè entry cần cứu**. **Dừng lại, xem reflog trước**.

### 9.3 `git log -g` — Reflog với format log

```bash
git log -g --oneline
# a1b2c3d HEAD@{0}: commit: feat: E
# e5f6g7h HEAD@{1}: commit: feat: D
# ...

git log -g --stat                # kèm thống kê file
git log -g -p                    # kèm diff (chậm nhưng chi tiết)
git log -g HEAD@{2}..HEAD@{0}    # range
```

**Lý thuyết**: `-g` = `--walk-reflogs` — duyệt theo reflog thay vì parent. Kết quả **giống reflog** nhưng format **giống log** — hữu ích khi cần xem chi tiết commit bị mất.

## 10. Tình huống thực tế nâng cao

### 10.1 Cứu commit sau `git filter-repo` (rewrite lịch sử)

```bash
git filter-repo --path secret.txt --invert-paths
# → Viết lại toàn bộ lịch sử, SHA mới

git reflog
# ... HEAD@{0}: filter-repo: ...
# ... HEAD@{1}: commit: feat: cuối trước filter-repo   ← lịch sử cũ

git branch old-history HEAD@{1}   # giữ lịch sử cũ
```

**Lưu ý**: `filter-repo` **xóa reflog** theo mặc định (để tránh secret leak). Phải `--preserve-commit-hashes` hoặc backup trước.

### 10.2 Cứu branch bị xóa không checkout

```bash
git branch -D feature              # xóa
# Nếu chưa bao giờ checkout feature:
git reflog
# ... không thấy feature (vì chưa checkout)
```

**Giải pháp**: 
- `git fsck --lost-found` — tìm dangling commit.
- Hoặc: nếu biết SHA (từ log cũ, PR, CI) → `git branch feature <sha>`.
- **Phòng tránh**: `git branch -d` (thường) thay vì `-D` — không xóa nếu chưa merge.

### 10.3 Cứu stash bị drop

```bash
git stash drop                     # xóa stash gần nhất
# ... hoảng ...

git reflog show stash
# ... stash@{0}: WIP on main: a1b2c3d feat: ...
# ... stash@{1}: WIP on main: e4f5g6h fix: ...   ← stash bị drop

git stash apply stash@{1}          # áp lại
# hoặc
git stash store <sha>              # lưu lại vào stash list
```

**Lý thuyết**: `git stash drop` xóa entry khỏi `refs/stash`, nhưng **reflog của stash** vẫn giữ SHA. `stash@{n}` trong reflog **khác** `stash@{n}` trong stash list — cẩn thận.

### 10.4 Cứu commit bị mất do rebase tương tác phức tạp

```bash
git rebase -i HEAD~10
# ... squash, drop, edit nhiều ...
# ... thấy sai, muốn quay lại ...

git reflog
# ... HEAD@{0}: rebase (finish): ...
# ... HEAD@{1}: rebase (start): checkout ...
# ...
# ... HEAD@{20}: commit: feat: cuối trước rebase   ← cần cái này

git reset --hard HEAD@{20}
# → Quay về trước rebase
```

**Hoặc**: `git reset --hard ORIG_HEAD` — nhanh hơn nếu rebase là thao tác nguy hiểm gần nhất.

### 10.5 Cứu khi `ORIG_HEAD` không đủ

```bash
git reset --hard HEAD~3
git commit -m "new"                # ORIG_HEAD vẫn = commit cũ, nhưng ...
git reset --hard HEAD~1             # ... ORIG_HEAD giờ = "new"
# → ORIG_HEAD không còn trỏ commit cũ nữa
```

**Giải pháp**: Dùng reflog — `HEAD@{n}` giữ **toàn bộ lịch sử**.

### 10.6 Reflog cho submodule

```bash
cd submodule/
git reflog                          # reflog của submodule
```

**Lý thuyết**: Mỗi submodule là **repo riêng** — có reflog riêng. Phải `cd` vào submodule để xem.

### 10.7 Reflog trên bare repo

```bash
git init --bare
# → Không có working tree, nhưng vẫn có reflog
git reflog                          # có (nếu có thao tác)
```

**Lý thuyết**: Bare repo vẫn có reflog — vì reflog ghi **di chuyển ref**, không cần working tree. Nhưng bare repo thường **không có thao tác local** → reflog thường rỗng.

## 11. Bảo mật và quyền riêng tư

### 11.1 Reflog chứa thông tin nhạy cảm

**Điểm lý thuyết quan trọng**:

- Reflog ghi **mọi commit** — kể cả commit chứa secret đã bị "xóa" bằng `reset`/`rebase`.
- Nếu bạn commit `.env` rồi `reset --hard`, **reflog vẫn giữ** commit đó → `git show HEAD@{n}` xem được secret.
- Khi chia sẻ repo (zip, USB), **reflog đi kèm** → secret leak.

**Giải pháp**:
```bash
# Trước khi chia sẻ repo
git reflog expire --expire=now --all
git gc --prune=now
# → Xóa sạch reflog + objects unreachable
```

**Cảnh báo**: Sau lệnh này, **không cứu được** commit nào nữa. Chỉ làm khi chắc chắn.

### 11.2 Reflog và audit

**Ứng dụng tích cực**: Reflog là **audit trail** — biết ai làm gì, khi nào (trong phạm vi local).

```bash
git reflog --date=iso
# Xem lịch sử thao tác với timestamp
```

**Hạn chế**: Reflog **chỉ local** — không phải audit trail đáng tin cậy (user có thể xóa). Server-side audit (GitHub events) đáng tin hơn.

### 11.3 Reflog và GDPR/compliance

Nếu repo chứa dữ liệu cá nhân (PII):
- Reflog giữ **mọi phiên bản** — kể cả đã "xóa".
- Cần `reflog expire + gc --prune=now` để **thực sự xóa**.
- **Và** rewrite history (`filter-repo`) để xóa khỏi mọi commit.
- **Và** thông báo team force-pull.

## 12. Tổng kết lý thuyết

### Bảng tổng hợp

| Khái niệm                 | Định nghĩa cốt lõi                         | Lưu ý                                   |
| ------------------------- | ------------------------------------------ | --------------------------------------- |
| **Reflog**                | Nhật ký di chuyển ref (local, append-only) | **Chỉ local**, không chia sẻ            |
| **`HEAD@{n}`**            | Tham chiếu theo reflog index               | `@{0}` = hiện tại; số lớn = cũ          |
| **`git log` vs `reflog`** | Reachable vs mọi di chuyển                 | Reflog thấy commit "mất"                |
| **`ORIG_HEAD`**           | Vị trí trước thao tác nguy hiểm gần nhất   | 1 giá trị, bị ghi đè                    |
| **`fsck --lost-found`**   | Tìm dangling objects                       | Phao cuối khi reflog hết hạn            |
| **Expiration**            | 90 ngày (HEAD), 30 ngày (unreachable)      | Cấu hình qua `gc.reflogExpire`          |
| **Giới hạn**              | Không cứu unstaged/untracked               | **Commit thường xuyên**                 |
| **Bảo mật**               | Chứa secret đã "xóa"                       | `expire + gc --prune=now` trước chia sẻ |

### Nguyên tắc vàng

1. **Reflog là phao cứu sinh số một** — cứu được mọi commit "mất" trong ~90 ngày.
2. **`HEAD@{n}` = "n thao tác trước"**, không phải "n commit trước" — khác `~n`.
3. **Đừng hoảng khi lỡ tay** — mỗi thao tác ghi đè reflog; dừng lại, xem reflog trước.
4. **`ORIG_HEAD` nhanh hơn** — dùng khi mới lỡ tay (reset/rebase/merge/pull).
5. **Reflog chỉ local** — không cứu được commit bị người khác force push (trừ khi họ có reflog).
6. **Không cứu unstaged changes** — chỉ cứu commit. **Commit thường xuyên**.
7. **`fsck --lost-found` là phao cuối** — khi reflog hết hạn nhưng chưa GC.
8. **`gc --prune=now` xóa vĩnh viễn** — không bao giờ dùng trừ khi chắc chắn.
9. **Reflog chứa secret** — `expire + gc` trước khi chia sẻ repo.
10. **Branch protection + backup** — phòng tránh hơn cứu hộ.

### Điểm mấu chốt cần nhớ

**Reflog là "hộp đen" của Git** — nó ghi lại **mọi thao tác di chuyển ref**, cho phép **quay ngược thời gian** để cứu commit "mất". Về bản chất, nó là **append-only log** trong `.git/logs/` — mỗi thao tác thêm một dòng, không bao giờ sửa. Nó **chỉ tồn tại ở local** (không push, không clone), giữ trong ~90 ngày (cấu hình được), và **không cứu được unstaged changes** (vì chúng chưa từng là Git object).

**Quy trình cứu hộ chuẩn**: `git reflog` → tìm SHA → `git show` xác nhận → `git reset --hard <sha>` (hoặc `git branch rescue <sha>`) → xác nhận. Với thao tác nguy hiểm mới lỡ: `git reset --hard ORIG_HEAD` nhanh hơn. Với commit unreachable sau khi reflog hết hạn: `git fsck --lost-found`.

**Bài học lớn nhất**: Git **rất khó mất dữ liệu đã commit** — reflog + objects + GC delay tạo ra nhiều lớp bảo vệ. Nhưng **dữ liệu chưa commit thì có thể mất ngay** — không có reflog nào cứu được. Vì vậy, **commit thường xuyên** là nguyên tắc bất biến.
