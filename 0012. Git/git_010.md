# Git Rebasing & Force Update of Remote Repository — Giải thích lý thuyết chi tiết

---

# PHẦN A — GIT REBASING: LÝ THUYẾT CHUYÊN SÂU

## 1. Bản chất: Rebase thực sự làm gì?

### 1.1 Định nghĩa chính xác

**Rebase** là thao tác **tái tạo (re-create)** một chuỗi commit từ base cũ sang base mới. Từ "rebase" = "re-base" = "đặt lại nền tảng".

> **Điểm lý thuyết cốt lõi**: Rebase **không di chuyển commit** — nó **tạo commit mới** với nội dung tương tự, rồi di chuyển con trỏ branch sang chuỗi commit mới. Commit cũ **không bị xóa** — chúng trở thành **unreachable** (chỉ còn reflog giữ).

### 1.2 Cơ chế bên trong — "Replay" từng commit

Giả sử bạn có:

```
A ← B ← C ← D   (main)
         ↑
         E ← F   (feature — đang đứng ở F)

git switch feature
git rebase main
```

**Git thực hiện tuần tự**:

```
Bước 1: Tìm merge-base của feature và main → C
Bước 2: Xác định commit cần replay: feature..merge-base = E, F
Bước 3: Reset feature về main (D) — tạm thời
Bước 4: Với từng commit trong [E, F]:
   4a. Tính diff(E, parent=C) → patch_E
   4b. Áp patch_E lên D → tạo E' (SHA mới)
   4c. Nếu conflict → dừng, chờ giải quyết
   4d. Tính diff(F, parent=E) → patch_F
   4e. Áp patch_F lên E' → tạo F' (SHA mới)
Bước 5: Di chuyển refs/heads/feature → F'
Bước 6: HEAD vẫn trỏ refs/heads/feature (giờ là F')
```

**Kết quả**:

```
A ← B ← C ← D ← E' ← F'   (feature, HEAD)
         ↑
         (C vẫn tồn tại — unreachable)
         E, F vẫn tồn tại — unreachable
```

### 1.3 Tại sao SHA thay đổi?

Commit SHA-1 được tính từ **toàn bộ nội dung commit object**:

```
tree <tree-sha>
parent <parent-sha>       ← THAY ĐỔI khi rebase
author <name> <email> <author-timestamp>
committer <name> <email> <committer-timestamp>   ← THAY ĐỔI
<message>
```

Khi rebase:
- **`parent` thay đổi** (E' có parent D thay vì C).
- **`committer` thay đổi** (timestamp mới = thời điểm rebase, danh tính người rebase).
- **`author` giữ nguyên** (tên, email, timestamp gốc của người viết ban đầu).

→ Hash thay đổi hoàn toàn. Đây là lý do **rebase "viết lại lịch sử"** — mọi commit bị rebase có SHA mới.

**Hệ quả lý thuyết**: Bất kỳ ai đã clone commit cũ (E, F) sẽ thấy lịch sử **phân kỳ** với bạn (E', F'). Nếu họ merge → tạo commit trùng lặp nội dung. Đây là lý do **không rebase commit đã push**.

### 1.4 Rebase preserve author, not committer

```bash
git log --format="%h author=%an <%ae> %ad | committer=%cn <%ce> %cd"
```

Sau rebase:
```
F' author=Alice <alice@x.com> 2024-01-01 | committer=Bob <bob@x.com> 2024-01-15
```

- **Author**: Alice (người viết code gốc) — **giữ nguyên**.
- **Committer**: Bob (người rebase) — **thay đổi**.

**Lý thuyết**: Git phân biệt **author** (người tạo nội dung) và **committer** (người tạo commit object). Rebase là hành động "áp lại nội dung của author dưới danh nghĩa committer mới". Điều này bảo toàn **attribution** (ghi công) cho tác giả gốc.

## 2. Rebase vs Merge — So sánh lý thuyết sâu

### 2.1 Mô hình DAG

**Trước**:
```
A ← B ← C ← D   (main)
         ↑
         E ← F   (feature)
```

**Sau merge** (`git merge feature` từ main):
```
A ← B ← C ← D ←──── M   (main)
         ↑         /
         E ← F ───
```
- `M` có **2 parent**: D (main), F (feature).
- Commit E, F **giữ nguyên SHA**.
- Lịch sử **phân nhánh** — thấy rõ feature tách ra và merge lại.

**Sau rebase** (`git rebase main` từ feature):
```
A ← B ← C ← D ← E' ← F'   (feature)
         ↑
         (main vẫn ở D)
```
- Không có merge commit.
- E', F' có **SHA mới**.
- Lịch sử **tuyến tính** — như thể E, F được viết sau D.

### 2.2 Bảng so sánh toàn diện

| Khía cạnh                     | Merge                        | Rebase                              |
| ----------------------------- | ---------------------------- | ----------------------------------- |
| **Tạo commit mới**            | 1 merge commit               | N commit mới (N = số commit rebase) |
| **Giữ commit gốc**            | ✅ (SHA nguyên)               | ❌ (SHA mới)                         |
| **Lịch sử**                   | Phân nhánh (topology)        | Tuyến tính (phẳng)                  |
| **Viết lại lịch sử**          | ❌                            | ✅                                   |
| **An toàn cho shared branch** | ✅                            | ❌                                   |
| **Conflict**                  | 1 lần (tất cả cùng lúc)      | N lần (từng commit)                 |
| **Dễ bisect**                 | Khó hơn (nhiều nhánh)        | Dễ hơn (tuyến tính)                 |
| **Revert feature**            | ✅ (revert 1 merge commit)    | ❌ (phải revert N commit)            |
| **Attribution**               | Giữ nguyên                   | Author giữ, committer đổi           |
| **Performance**               | Nhanh (1 thao tác)           | Chậm hơn (N thao tác)               |
| **Có thể undo**               | `git reset --hard ORIG_HEAD` | `git reset --hard ORIG_HEAD`        |

### 2.3 Khi nào chọn cái nào — Lý thuyết quyết định

**Chọn Merge khi**:
- Branch là **shared** (main, develop, release) — nhiều người dùng.
- Muốn **bảo toàn ngữ nghĩa** "feature X được merge lúc Y".
- Commit đã **push** lên remote.
- Team policy yêu cầu **audit trail** đầy đủ.

**Chọn Rebase khi**:
- Branch là **cá nhân** (feature branch chưa ai khác dùng).
- Muốn lịch sử **tuyến tính, sạch**.
- Commit **chưa push** (hoặc đã push nhưng chỉ mình bạn dùng).
- Cần **dọn dẹp commit** trước khi merge (interactive rebase).

**Lý thuyết cốt lõi**: Merge bảo toàn **sự thật lịch sử** (cái gì đã xảy ra). Rebase tạo **câu chuyện lịch sử** (cái gì nên xảy ra). Merge cho auditor, rebase cho developer.

## 3. Interactive Rebase — Công cụ mạnh nhất của Git

### 3.1 Định nghĩa

**Interactive rebase** (`git rebase -i`) cho phép **can thiệp vào từng commit** trong quá trình replay — sắp xếp lại, gộp, sửa, xóa.

### 3.2 Cú pháp

```bash
git rebase -i <base>
```

`<base>` là commit **trước** commit đầu tiên bạn muốn sửa. Ví dụ:
- `HEAD~5`: 5 commit gần nhất.
- `HEAD~3`: 3 commit gần nhất.
- `<sha>`: mọi commit sau sha đó.
- `--root`: từ commit đầu tiên (root commit).

### 3.3 Editor hiện ra

```bash
git rebase -i HEAD~4
```

```
pick a1b2c3d feat: add login form
pick e4f5g6h fix: typo in validation
pick i7j8k9l feat: add logout
pick m0n1o2p wip

# Rebase d5e6f7g..m0n1o2p onto d5e6f7g (4 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup <commit> = like "squash", but discard this commit's log message
# x, exec <command> = run command (the rest of the line) using shell
# b, break = stop here (continue rebase later with 'git rebase --continue')
# d, drop <commit> = remove commit
# l, label <label> = label current HEAD with a name
# t, reset <label> = reset HEAD to a label
# m, merge [-C <commit> | -c <commit>] <label> [# <oneline>]
```

### 3.4 Các lệnh chi tiết

#### `pick` (p) — Giữ nguyên

```
pick a1b2c3d feat: add login form
```
Áp commit, giữ message và nội dung.

#### `reword` (r) — Sửa message

```
reword a1b2c3d feat: add login form
```
Áp commit, nhưng mở editor để sửa message. Nội dung giữ nguyên.

**Lý thuyết**: Tạo commit mới (SHA khác) vì message thay đổi → hash thay đổi. Chỉ message khác, tree giống.

#### `edit` (e) — Dừng để amend

```
edit a1b2c3d feat: add login form
```
Áp commit, rồi **dừng lại** — cho phép bạn:
- Sửa nội dung (`git commit --amend`).
- Thêm file (`git add` + `git commit --amend`).
- Tách commit (`git reset HEAD^` rồi commit lại nhiều lần).
- Bất kỳ thao tác nào.

Sau khi xong: `git rebase --continue`.

#### `squash` (s) — Gộp, giữ message

```
pick a1b2c3d feat: add login form
squash e4f5g6h fix: typo
```
Gộp `e4f5g6h` vào `a1b2c3d` → **1 commit mới**. Mở editor để **kết hợp message** (mặc định là concat cả hai).

**Kết quả**: Commit `a1b2c3d` chứa nội dung của cả hai. SHA mới.

#### `fixup` (f) — Gộp, bỏ message

```
pick a1b2c3d feat: add login form
fixup e4f5g6h fix: typo
```
Giống squash, nhưng **bỏ message của commit sau** — chỉ giữ message của commit đầu. Dùng khi commit sau là "fix nhỏ" không cần message riêng.

**Lý thuyết**: `fixup` là "squash không cần editor". Phổ biến cho các commit "wip", "fix typo", "address review".

#### `drop` (d) — Xóa commit

```
drop m0n1o2p wip
```
Commit bị **bỏ hoàn toàn** khỏi lịch sử mới. Tương đương xóa dòng.

**Cẩn thận**: Nội dung commit bị mất (vẫn trong reflog, nhưng branch không còn trỏ tới).

#### `exec` (x) — Chạy lệnh

```
pick a1b2c3d feat: add login form
exec npm test
pick e4f5g6h feat: add logout
```
Chạy `npm test` **sau** khi áp `a1b2c3d`. Nếu fail → rebase dừng.

**Ứng dụng**: Chạy test sau mỗi commit, đảm bảo mỗi commit đều "xanh" (atomic commits có thể build/test độc lập).

#### `break` (b) — Dừng có chủ đích

Chèn điểm dừng — cho phép bạn thao tác thủ công rồi `git rebase --continue`.

#### `label`/`reset`/`merge` — Cho `--rebase-merges`

Dùng để tái tạo cấu trúc merge trong interactive rebase.

### 3.5 Sắp xếp lại commit

**Chỉ cần đổi thứ tự dòng** trong editor:

```
# Trước
pick a1b2c3d feat: add login form
pick e4f5g6h feat: add logout
pick i7j8k9l fix: typo

# Sau khi sắp xếp
pick e4f5g6h feat: add logout
pick a1b2c3d feat: add login form
pick i7j8k9l fix: typo
```

Git sẽ áp lại theo thứ tự mới. **Có thể conflict** nếu commit phụ thuộc lẫn nhau về nội dung.

### 3.6 `--autosquash` — Tự động sắp xếp fixup

Nếu commit message có prefix `fixup! <message>` hoặc `squash! <message>`, `git rebase -i --autosquash` tự động sắp xếp chúng sau commit tương ứng và đánh dấu `fixup`/`squash`.

```bash
git commit -m "fixup! feat: add login form"     # commit sửa nhỏ
git rebase -i --autosquash HEAD~3
# → Tự động: fixup! commit được đặt sau "feat: add login form" với lệnh fixup
```

**Ứng dụng**: Workflow "commit thoải mái, dọn dẹp sau". Bạn commit nhiều lần nhỏ, rồi `--autosquash` để Git tự sắp xếp.

Cấu hình mặc định:
```bash
git config --global rebase.autoSquash true
```

### 3.7 `--rebase-merges` — Giữ cấu trúc merge

**Vấn đề**: Rebase mặc định **làm phẳng** merge — nếu branch có merge commit, nó biến mất, các commit con được áp tuần tự.

```bash
git rebase -i --rebase-merges main
```

**Lý thuyết**: `--rebase-merges` tạo lại merge commit trong lịch sử mới — giữ topology. Dùng khi branch có chứa merge từ branch khác và bạn muốn giữ ngữ nghĩa đó.

Trong editor:
```
label onto
reset onto
pick a1b2c3d commit A
label branch1
reset onto
pick e4f5g6h commit B
merge -C abc1234 branch1 # Merge branch 'branch1'
```

## 4. `git rebase --onto` — Rebase có kiểm soát

### 4.1 Cú pháp và lý thuyết

```bash
git rebase --onto <newbase> <upstream> [<branch>]
```

**Công thức**: "Lấy các commit của `<branch>` mà **không thuộc** `<upstream>`, áp lên `<newbase>`".

Tức là: `newbase` ← (các commit trong `upstream..branch`).

### 4.2 Ví dụ: Tách branch con

```
A ← B ← C   (main)
         ↑
         D ← E ← F   (feature-parent)
                 ↑
                 G ← H   (feature-child — tách từ F)

# Muốn tách feature-child khỏi feature-parent, áp lên main
git rebase --onto main feature-parent feature-child
```

**Kết quả**:
```
A ← B ← C ← G' ← H'   (feature-child)
         ↑
         D ← E ← F   (feature-parent — không đổi)
```

`G`, `H` được áp lên `C` (main), bỏ qua `D, E, F`.

### 4.3 Ứng dụng thực tế

- **Tách branch** đã tách sai base.
- **Rebase một phần** của branch.
- **Di chuyển commit** từ branch này sang branch khác (thay cherry-pick cho nhiều commit).

### 4.4 `--onto` với `--root`

```bash
git rebase --onto main --root
```

Áp **toàn bộ** lịch sử (từ root commit) lên `main`. Dùng để "gắn" một repo không liên quan vào lịch sử hiện có.

## 5. Rebase và các vấn đề tinh tế

### 5.1 Conflict trong rebase — Đặc điểm

**Khác merge**: Merge conflict **một lần** (tất cả commit cùng lúc). Rebase conflict **từng commit một** (theo thứ tự replay).

```bash
git rebase main
# CONFLICT khi áp E
# → giải quyết → git rebase --continue
# CONFLICT khi áp F
# → giải quyết → git rebase --continue
# Done
```

**Hệ quả**: Rebase có thể conflict **nhiều lần** — mỗi commit replay có thể conflict độc lập. Tuy nhiên, mỗi conflict thường **nhỏ hơn** (chỉ liên quan đến thay đổi của 1 commit).

### 5.2 `ours`/`theirs` đảo ngược — Cạm bẫy lớn nhất

Trong rebase:
- **`ours`** = **base mới** (main, commit đang áp lên).
- **`theirs`** = **commit đang được áp** (commit gốc của bạn).

**Ngược** hoàn toàn với merge. Đây là nguồn gốc nhiều lỗi.

```bash
# Trong rebase conflict:
git checkout --ours <file>    # chọn base mới (thường KHÔNG phải ý muốn)
git checkout --theirs <file>  # chọn commit của bạn (thường LÀ ý muốn)
```

**Cách nhớ**: Trong rebase, "theirs" = "commit bạn đang cố áp vào" — chính là code của bạn.

### 5.3 `rerere` — Cứu tinh cho rebase dài

Rebase branch 50 commit có thể gặp **cùng conflict** nhiều lần. `rerere` (REuse REcorded REsolution) ghi nhớ cách giải quyết:

```bash
git config --global rerere.enabled true
```

**Cơ chế**:
- Khi conflict, `rerere` lưu `(base, ours, theirs)` → resolution vào `.git/rr-cache/`.
- Lần sau gặp **cùng bộ ba** → tự áp resolution.
- Bạn vẫn phải `git add` (rerere không tự stage) — nhưng **không cần sửa tay**.

**Lý thuyết**: `rerere` dựa trên **preimage hash** — hash của `(base, ours, theirs)`. Nếu trùng → áp resolution. Cực kỳ hiệu quả khi rebase qua nhiều commit có cùng pattern thay đổi.

### 5.4 Rebase với submodule

Rebase branch có submodule **có thể gây conflict submodule** — commit của submodule thay đổi. Cần cẩn thận:

```bash
git submodule update --init --recursive
# sau rebase, kiểm tra submodule
git submodule status
```

### 5.5 `rebase.autoStash`

```bash
git config --global rebase.autoStash true
```

**Lý thuyết**: Nếu có thay đổi chưa commit, rebase sẽ **từ chối** (không thể đổi branch khi working tree dirty). `autoStash` tự động `git stash` trước, rebase, rồi `git stash pop` sau. **Tiện nhưng có thể conflict khi pop** — cần kiểm tra.

### 5.6 Rebase và reflog — Cứu hộ

Sau rebase, commit cũ vẫn trong reflog:

```bash
git reflog
# F' HEAD@{0}: rebase (finish): returning to refs/heads/feature
# F  HEAD@{1}: rebase (start): checkout main
# ...
# F  HEAD@{5}: commit: feat: add logout   ← commit gốc F

git reset --hard HEAD@{5}     # quay lại trước rebase
```

**Lý thuyết**: Rebase không xóa commit cũ — chỉ làm chúng unreachable. Reflog giữ SHA trong ~90 ngày. `git reset --hard` hoặc `git branch rescue <sha>` cứu được.

**`ORIG_HEAD`**: Git lưu ref đặc biệt `ORIG_HEAD` = vị trí trước thao tác nguy hiểm gần nhất (rebase, merge, reset). `git reset --hard ORIG_HEAD` = hủy thao tác.

## 6. Rebase nâng cao — Các kỹ thuật

### 6.1 `--exec` để chạy test

```bash
git rebase -i HEAD~5 --exec "npm test"
```

Chạy `npm test` **sau mỗi commit**. Nếu fail → dừng. Đảm bảo **mỗi commit đều testable** — nguyên tắc "atomic commit" (mỗi commit là một trạng thái hợp lệ).

**Ứng dụng**: "Test-driven history" — mỗi commit đều pass test, dễ bisect.

### 6.2 `--keep-base` — Giữ base cũ

```bash
git rebase -i --keep-base main
```

Giữ base cũ thay vì update lên đầu main. Dùng khi muốn **sửa commit mà không cập nhật base**.

### 6.3 `--fork-point` — Xử lý rebase upstream

```bash
git rebase --fork-point main
```

**Vấn đề**: Nếu upstream (`main`) đã rebase, `git rebase main` có thể áp **sai** — vì nó dùng `merge-base` không chính xác.

**`--fork-point`**: Dùng **reflog** của upstream để tìm điểm tách **thực sự** — an toàn hơn khi upstream thay đổi.

**Lý thuyết**: `merge-base` thông thường dựa trên DAG hiện tại. Nếu upstream rebase (SHA mới), DAG thay đổi → `merge-base` có thể sai. `--fork-point` dùng **reflog** — biết upstream **đã từng** ở đâu → tìm điểm tách chính xác.

### 6.4 Rebase với `--empty` và `--no-keep-empty`

```bash
git rebase --empty=drop main       # bỏ commit rỗng (sau khi áp)
git rebase --empty=keep main       # giữ commit rỗng
git rebase --empty=ask main        # hỏi
```

**Lý thuyết**: Sau rebase, một commit có thể trở thành **rỗng** (nội dung đã có trong base mới). Git mặc định **bỏ** — có thể gây bất ngờ. `--empty=keep` giữ lại.

### 6.5 Rebase và `--committer-date-is-author-date`

```bash
git rebase --committer-date-is-author-date main
```

Giữ **committer date = author date** — SHA vẫn thay đổi (vì parent), nhưng date không "nhảy" về hiện tại.

## 7. Lý thuyết "Rebase an toàn"

### 7.1 Quy tắc vàng

> **Không bao giờ rebase commit đã push lên branch chia sẻ.**

**Lý do lý thuyết**: Rebase tạo SHA mới. Nếu người khác đã clone commit cũ, lịch sử **phân kỳ** — họ có E, F; bạn có E', F'. Khi họ pull → merge → **commit trùng lặp nội dung**. Lịch sử trở nên rối loạn, khó audit.

### 7.2 Ngoại lệ

- **Branch cá nhân** (chỉ mình bạn dùng) — rebase thoải mái.
- **Feature branch chưa merge** — rebase OK (nhưng báo team nếu có ai checkout).
- **Sau khi force-push** — thông báo team, họ phải `git fetch && git reset --hard origin/feature`.

### 7.3 `git pull --rebase` — Cẩn thận

```bash
git pull --rebase
```

**Lý thuyết**: `pull --rebase` = `fetch` + `rebase origin/main`. Nó rebase **commit local chưa push** lên `origin/main`. **An toàn** nếu commit local chưa push. **Nguy hiểm** nếu đã push (viết lại SHA).

**Best practice**:
```bash
git config --global pull.rebase false      # an toàn: merge
# hoặc
git config --global pull.ff only           # an toàn nhất: chỉ FF
# hoặc
git config --global pull.rebase true       # nếu team dùng rebase workflow
```

### 7.4 So sánh "an toàn"

| Chiến lược        | An toàn với shared       | An toàn với cá nhân |
| ----------------- | ------------------------ | ------------------- |
| `pull --ff-only`  | ✅ Tuyệt đối              | ✅                   |
| `pull` (merge)    | ✅                        | ✅                   |
| `pull --rebase`   | ❌ (viết lại nếu có push) | ✅                   |
| `rebase` thủ công | ❌                        | ✅                   |

# PHẦN B — FORCE UPDATE OF REMOTE REPOSITORY

## 8. Tại sao cần force push?

### 8.1 Bối cảnh

Sau khi rebase, amend, hoặc reset, commit local có **SHA mới**. Remote vẫn trỏ commit cũ. Khi push:

```bash
git push origin feature
# ! [rejected]        feature -> feature (non-fast-forward)
# error: failed to push some refs to 'github.com:...'
# hint: Updates were rejected because the tip of your current branch is behind
# hint: its remote counterpart...
```

**Lý thuyết**: Git từ chối push vì commit đích trên remote (`F`) **không phải ancestor** của commit local (`F'`). Push bình thường yêu cầu **fast-forward** — bảo vệ commit trên remote khỏi bị ghi đè.

### 8.2 Cơ chế kiểm tra non-fast-forward

Khi push, server kiểm tra:
```
remote_ref (F) có phải ancestor của local_ref (F') không?
```

- **Có** → fast-forward → chấp nhận.
- **Không** → non-fast-forward → từ chối (trừ khi force).

**Lý thuyết**: Đây là **cơ chế bảo vệ** — ngăn push vô tình ghi đè commit của người khác. Force push **tắt** cơ chế này.

---

## 9. `--force` vs `--force-with-lease` — Lý thuyết bảo mật

### 9.1 `--force` — Ghi đè mù quáng

```bash
git push --force origin feature
# hoặc
git push -f origin feature
```

**Cơ chế**: Bỏ qua mọi kiểm tra non-fast-forward. Server **ghi đè** `feature` = `F'` bất kể ai đã push gì.

**Nguy hiểm**:
- Nếu đồng nghiệp đã push commit mới lên `feature` **sau lần fetch cuối của bạn** → commit đó **bị xóa** khỏi branch (vẫn trong reflog server, nhưng khó cứu).
- Không có cảnh báo, không có cơ hội ngăn chặn.

### 9.2 `--force-with-lease` — Ghi đè có kiểm tra

```bash
git push --force-with-lease origin feature
```

**Cơ chế**: Kiểm tra **lease** trước khi ghi đè:

```
Server: remote_ref hiện tại = ?
Client: remote-tracking ref (origin/feature) local = ?

Nếu khớp → cho phép force push.
Nếu khác → TỪ CHỐI (ai đó đã push từ lần fetch cuối).
```

**Lý thuyết**: `--force-with-lease` dựa trên **remote-tracking branch** local (`refs/remotes/origin/feature`) làm "lease" (hợp đồng thuê). Nó nói: "Tôi chỉ ghi đè nếu remote vẫn ở trạng thái tôi biết (snapshot lần fetch cuối). Nếu ai đó đã thay đổi → dừng lại."

### 9.3 Ví dụ minh họa

```
Lần fetch cuối: origin/feature → F
Bạn rebase local: feature → F'

Trường hợp A: Server vẫn ở F
  → --force-with-lease: lease khớp → push OK (ghi đè F bằng F')

Trường hợp B: Đồng nghiệp push G (F → G) sau lần fetch cuối
  → --force-with-lease: lease KHÔNG khớp (local biết F, server là G)
  → TỪ CHỐI: "stale info"
  → Bạn phải fetch, xem G, quyết định (merge? rebase? force?)
```

**Đây là điểm mấu chốt**: `--force-with-lease` **bảo vệ commit của người khác** — không cho bạn vô tình ghi đè.

### 9.4 `--force-with-lease=<ref>:<expect>` — Lease tường minh

```bash
git push --force-with-lease=feature:a1b2c3d origin feature
```

**Lý thuyết**: Chỉ định **chính xác** SHA mà bạn mong đợi remote đang trỏ tới. Nếu khác → từ chối.

**Ứng dụng**: Khi bạn biết chính xác trạng thái server (qua `git ls-remote`), dùng lease tường minh để kiểm soát tuyệt đối.

### 9.5 `--force-if-includes` — Bảo vệ bổ sung (Git ≥2.30)

```bash
git push --force-with-lease --force-if-includes origin feature
```

**Lý thuyết**: `--force-with-lease` có **lỗ hổng**: nếu bạn `fetch` (cập nhật lease) nhưng **chưa thực sự tích hợp** commit mới của người khác vào local → lease khớp (vì đã fetch) → force push **vẫn ghi đè** commit của họ.

`--force-if-includes` kiểm tra thêm: **commit mới nhất của remote có nằm trong lịch sử local không?** Nếu không → từ chối.

**Ví dụ lỗ hổng**:
```bash
git fetch origin              # lease giờ = G (commit mới nhất của đồng nghiệp)
git rebase origin/main        # rebase local, KHÔNG tích hợp G
git push --force-with-lease   # lease khớp (G) → GHI ĐÈ G! (mất commit đồng nghiệp)
```

Với `--force-if-includes`: phát hiện G không có trong local → từ chối.

**Best practice**: Luôn dùng **cả hai**:
```bash
git push --force-with-lease --force-if-includes origin feature
```

Hoặc cấu hình alias:
```bash
git config --global alias.pushf "push --force-with-lease --force-if-includes"
```

## 10. Bảng so sánh các loại force push

| Lệnh                                     | Kiểm tra lease | Kiểm tra include | An toàn           |
| ---------------------------------------- | -------------- | ---------------- | ----------------- |
| `--force` / `-f`                         | ❌              | ❌                | ❌ Nguy hiểm nhất  |
| `--force-with-lease`                     | ✅              | ❌                | ⚠️ Tốt, có lỗ hổng |
| `--force-with-lease --force-if-includes` | ✅              | ✅                | ✅ An toàn nhất    |

**Lý thuyết**: `--force-with-lease` bảo vệ khỏi "ai đó push từ lần fetch cuối". `--force-if-includes` bảo vệ khỏi "tôi fetch nhưng không tích hợp". Kết hợp cả hai = bảo vệ toàn diện.

## 11. Các tình huống force push điển hình

### 11.1 Sau rebase feature branch

```bash
git switch feature
git fetch origin
git rebase origin/main
# ... giải quyết conflict ...
git push --force-with-lease origin feature
```

**Lý do**: Rebase tạo SHA mới → non-fast-forward → cần force. `--force-with-lease` bảo vệ nếu ai đó push lên feature.

### 11.2 Sau amend commit

```bash
git commit --amend -m "feat: better message"
git push --force-with-lease origin feature
```

### 11.3 Sau reset --hard

```bash
git reset --hard HEAD~3
git push --force-with-lease origin feature
```

### 11.4 Xóa commit trên remote

```bash
# Local
git reset --hard HEAD~1

# Remote — force push để đồng bộ
git push --force-with-lease origin feature
```

### 11.5 Sửa lịch sử branch cá nhân

```bash
git rebase -i HEAD~5
# ... squash, reword, drop ...
git push --force-with-lease origin feature
```

### 11.6 Force push lên `main` — Cực kỳ nguy hiểm

```bash
git push --force origin main    # ❌ KHÔNG BAO GIỜ
```

**Lý do**: `main` là branch chia sẻ. Force push lên `main` có thể:
- Xóa commit của người khác.
- Gây rối loạn cho toàn team.
- Phá vỡ CI/CD, deployment.

**Phòng tránh**: **Branch protection** trên GitHub/GitLab — chặn force push lên `main` ở cấp server. Đây là **lớp bảo vệ bắt buộc** cho mọi team.

## 12. Branch protection — Lớp bảo vệ server-side

### 12.1 Cấu hình trên GitHub

**Settings → Branches → Branch protection rules**:

- ✅ **Require pull request before merging** — không push trực tiếp.
- ✅ **Require approvals** — cần review.
- ✅ **Dismiss stale approvals** — approval cũ bị hủy khi có commit mới.
- ✅ **Require status checks** — CI phải pass.
- ✅ **Require conversation resolution** — comment phải resolved.
- ✅ **Require linear history** — từ chối merge commit (khuyến khích squash/rebase).
- ✅ **Do not allow force pushes** — chặn force push.
- ✅ **Do not allow deletions** — không ai xóa branch.

### 12.2 Trên GitLab

**Settings → Repository → Protected branches**:

- **Allowed to merge**: ai được merge.
- **Allowed to push**: ai được push (thường `No one` cho `main`).
- **Allowed to force push**: tắt cho `main`.

### 12.3 Lý thuyết

**Branch protection là "hợp đồng xã hội" được enforce ở server**. Nó:
- Không thể bypass bởi `git push --force` (server từ chối).
- Bảo vệ **tính toàn vẹn lịch sử** của branch chính.
- Cho phép **workflow review** (PR/MR bắt buộc).

**Không có branch protection = không có an toàn**. Dù bạn dùng `--force-with-lease` cẩn thận, người khác có thể `--force`. Chỉ server-side enforcement mới đảm bảo.

## 13. Phục hồi sau force push — Cứu commit bị mất

### 13.1 Trên máy local (nếu có clone)

```bash
# Nếu bạn từng có commit bị force push đè
git reflog
# tìm SHA của commit bị mất
git reset --hard <sha>
git push --force-with-lease origin main    # phục hồi (nếu có quyền)
```

### 13.2 Trên GitHub — Reflog server

GitHub lưu **reflog server-side** trong ~90 ngày. Có thể truy cập qua:
- **GitHub API**: `GET /repos/{owner}/{repo}/events` — xem push events.
- **GitHub UI**: **Activity** tab → **Force-push** events → xem SHA trước/sau.
- Nếu biết SHA cũ: `git push --force origin <sha>:main` để phục hồi.

### 13.3 Trên GitLab

- **Project → Repository → Commits** → xem SHA cũ.
- **Admin → Monitoring → Logs** (nếu self-hosted).
- Nếu biết SHA: `git push --force origin <sha>:branch`.

### 13.4 Phòng tránh

- **Branch protection** — chặn force push.
- **Backup**: mirror repo, hoặc tag định kỳ.
- **Thông báo team** trước khi force push branch chia sẻ.
- **`--force-with-lease --force-if-includes`** — không bao giờ `--force`.

## 14. Tổng kết lý thuyết

### Về Rebase

| Khái niệm               | Định nghĩa cốt lõi                      | Lưu ý                                         |
| ----------------------- | --------------------------------------- | --------------------------------------------- |
| **Rebase**              | Tái tạo commit từ base cũ sang base mới | **Tạo commit mới** (SHA mới), không di chuyển |
| **Replay**              | Áp từng patch theo thứ tự               | Conflict từng commit                          |
| **Author vs Committer** | Author giữ, committer đổi               | Bảo toàn attribution                          |
| **Interactive rebase**  | `-i` — can thiệp từng commit            | pick/reword/edit/squash/fixup/drop            |
| **`--onto`**            | Rebase có kiểm soát                     | Tách branch, di chuyển commit                 |
| **`ours`/`theirs`**     | **Đảo ngược** trong rebase              | Cạm bẫy lớn nhất                              |
| **`rerere`**            | Ghi nhớ resolution, tự áp               | Cứu tinh cho rebase dài                       |
| **`ORIG_HEAD`**         | Vị trí trước thao tác                   | `reset --hard ORIG_HEAD` = hủy                |
| **Quy tắc vàng**        | Không rebase commit đã push             | Tránh rối loạn lịch sử team                   |

### Về Force Update

| Khái niệm                 | Định nghĩa cốt lõi                       | Lưu ý                               |
| ------------------------- | ---------------------------------------- | ----------------------------------- |
| **Non-fast-forward**      | Remote ref không phải ancestor của local | Cơ chế bảo vệ                       |
| **`--force`**             | Ghi đè mù quáng                          | Nguy hiểm nhất — tránh              |
| **`--force-with-lease`**  | Ghi đè có kiểm tra lease                 | Bảo vệ commit người khác            |
| **Lease**                 | Remote-tracking ref local = "hợp đồng"   | Khớp → cho phép; khác → từ chối     |
| **`--force-if-includes`** | Kiểm tra commit remote có trong local    | Vá lỗ hổng của `--force-with-lease` |
| **Best practice**         | `--force-with-lease --force-if-includes` | Luôn dùng cả hai                    |
| **Branch protection**     | Chặn force push ở server                 | Lớp bảo vệ bắt buộc                 |
| **Phục hồi**              | Reflog (local + server)                  | Trong ~90 ngày                      |

### Nguyên tắc vàng

1. **Rebase chỉ cho commit chưa push** — commit đã push phải merge.
2. **`ours`/`theirs` đảo ngược trong rebase** — luôn kiểm tra trước khi dùng.
3. **`--force-with-lease --force-if-includes`** — không bao giờ `--force`.
4. **Branch protection trên `main`** — không thể bypass, bảo vệ toàn team.
5. **`reflog` là phao cứu sinh** — commit "mất" vẫn cứu được trong ~90 ngày.
6. **Thông báo team trước force push** — dù branch cá nhân, nếu có ai checkout.
7. **Rebase branch dài → bật `rerere`** — tiết kiệm hàng giờ giải quyết conflict.
8. **Interactive rebase là công cụ dọn lịch sử** — dùng trước khi mở PR để có lịch sử sạch, dễ review.
