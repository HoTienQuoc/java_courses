# Git Ignoring (.gitignore) & Git Log — Giải thích lý thuyết chi tiết

---

# PHẦN A — GIT IGNORING (.gitignore)

## 1. Bản chất: Ignore là gì và KHÔNG là gì?

### Định nghĩa cốt lõi

`.gitignore` là **file cấu hình pattern** — nó **chỉ ảnh hưởng tới các file ở trạng thái untracked** (chưa được Git theo dõi). Đây là điểm lý thuyết quan trọng nhất, hầu hết người dùng hiểu sai:

> **`.gitignore` không "xóa" file khỏi Git, không "chặn" file đã tracked. Nó chỉ khiến `git status` và `git add` *bỏ qua* file untracked khớp pattern.**

Cơ chế bên trong: khi Git quét working tree để tìm untracked file (trong `git status`, `git add .`, `git add -A`), nó duyệt **cây thư mục** và với mỗi đường dẫn, kiểm tra theo thứ tự ưu tiên (mục 4). Nếu khớp ignore rule → **đường dẫn bị loại khỏi tập ứng viên**. Nếu file đã có trong **index** (đã track), ignore rule **không được xét tới** — Git vẫn theo dõi như thường.

### Hệ quả lý thuyết

| Tình huống                                   | `.gitignore` có tác dụng?                                     |
| -------------------------------------------- | ------------------------------------------------------------- |
| File **untracked** khớp pattern              | ✅ Bị bỏ qua khi `git add`/`status`                            |
| File **đã tracked** (đã commit) khớp pattern | ❌ Vẫn track bình thường                                       |
| File **đã add vào index** nhưng chưa commit  | ❌ Vẫn track (ignore không gỡ khỏi index)                      |
| Thư mục untracked khớp pattern               | ✅ Toàn bộ nội dung bị bỏ qua                                  |
| File trong submodule                         | ❌ `.gitignore` của repo cha không áp dụng vào trong submodule |

Vì vậy **thứ tự thao tác đúng là: tạo `.gitignore` TRƯỚC khi `git add` lần đầu**. Nếu đã lỡ track, phải dùng `git rm --cached` (xem mục 7).

## 2. Cú pháp pattern — Ngữ nghĩa đầy đủ

`.gitignore` không phải glob thông thường, nó là **gitignore pattern** — có quy tắc riêng. Mỗi dòng là một pattern.

### 2.1 Quy tắc cơ bản

| Cú pháp          | Ý nghĩa                                                        | Ví dụ                                           |
| ---------------- | -------------------------------------------------------------- | ----------------------------------------------- |
| `file.txt`       | Khớp file/thư mục tên `file.txt` ở **bất kỳ cấp nào**          | Khớp `a/file.txt`, `b/c/file.txt`               |
| `/file.txt`      | Chỉ khớp ở **root của repo**                                   | Chỉ `file.txt` ở gốc                            |
| `dir/`           | Chỉ khớp **thư mục** tên `dir` (dấu `/` cuối = directory-only) | Bỏ qua `dir/` nhưng KHÔNG bỏ qua file tên `dir` |
| `*.log`          | Khớp mọi file đuôi `.log` ở mọi cấp                            | `a.log`, `logs/x.log`                           |
| `**/logs`        | `**` = khớp 0 hoặc nhiều thư mục                               | `logs/`, `a/logs/`, `a/b/logs/`                 |
| `a/**/b`         | Khớp `a/b`, `a/x/b`, `a/x/y/b`...                              | —                                               |
| `!pattern`       | **Phủ định** (negation) — bỏ ignore                            | Xem mục 3                                       |
| `# comment`      | Dòng comment                                                   | Bỏ qua                                          |
| `\#file`         | Escape ký tự đặc biệt                                          | Khớp file tên `#file`                           |
| ` ` (space cuối) | Bị strip — trừ khi escape `\ `                                 | Cẩn thận với editor auto-strip                  |
| `[abc]`, `[0-9]` | Character class (glob)                                         | `file[0-9].txt`                                 |
| `?`              | Khớp 1 ký tự bất kỳ (không khớp `/`)                           | `file?.txt`                                     |
| `*`              | Khớp 0+ ký tự (không khớp `/`)                                 | `*.tmp`                                         |

### 2.2 Điểm tinh tế: `/` ở đầu vs giữa vs cuối

```gitignore
build/          # thư mục "build" ở BẤT KỲ cấp nào
/build/         # chỉ thư mục "build" ở GỐC repo
build           # khớp cả file và thư mục tên "build" ở bất kỳ cấp
*.o             # mọi file .o
doc/*.txt       # chỉ file .txt trực tiếp trong doc/ (không đệ quy)
doc/**/*.txt    # file .txt trong doc/ đệ quy
```

**Nguyên tắc lý thuyết**: Dấu `/` **ở bất kỳ vị trí nào khác đầu/cuối** khiến pattern được neo tương đối so với vị trí file `.gitignore` chứa nó. Nếu pattern **không chứa `/`** (trừ dấu `/` cuối cùng), nó khớp ở **mọi cấp**.

## 3. Negation `!` và giới hạn của nó

### 3.1 Cơ chế

Pattern có `!` sẽ **"un-ignore"** — nhưng chỉ có tác dụng với các đường dẫn mà **pattern trước đó đã ignore** và **chưa bị loại khỏi quá trình duyệt**. Ví dụ điển hình:

```gitignore
*.log
!important.log     # vẫn track important.log
```

### 3.2 Giới hạn quan trọng — "không thể re-include nếu parent bị ignore"

Đây là **cái bẫy lý thuyết** kinh điển:

```gitignore
logs/
!logs/keep.txt     # ❌ KHÔNG có tác dụng!
```

**Lý do**: Khi Git duyệt cây thư mục, gặp `logs/` → khớp ignore → **nó dừng duyệt vào bên trong thư mục đó**. Vì Git không đi vào `logs/`, nó **không bao giờ thấy** `logs/keep.txt` để áp pattern `!`. Negation chỉ áp dụng **trong phạm vi đã được duyệt**.

Cách đúng:

```gitignore
logs/*
!logs/keep.txt     # ✅ OK: ignore nội dung nhưng vẫn duyệt vào logs/
```

Hoặc:

```gitignore
logs/**
!logs/keep.txt
```

**Nguyên tắc tổng quát**: Để re-include một file, **mọi thư mục cha của nó phải không bị ignore ở mức "chặn duyệt"**. Nếu cha bị ignore bằng `dir/` hoặc `dir`, bạn không thể re-include file con. Phải ignore nội dung cha bằng `dir/*` rồi mở ngoại lệ.

## 4. Thứ tự ưu tiên — Khi nhiều nguồn mâu thuẫn

Git xét ignore theo **thứ tự ưu tiên giảm dần** (nguồn sau **ghi đè** nguồn trước — pattern cuối cùng khớp "thắng"):

| Ưu tiên       | Nguồn                                                    | Phạm vi            | Commit được không |
| ------------- | -------------------------------------------------------- | ------------------ | ----------------- |
| 1 (cao nhất)  | Command-line (`git add -f`, `--exclude`)                 | Tức thời           | —                 |
| 2             | `.gitignore` trong **thư mục hiện tại** (và thư mục con) | Local              | ✅ Commit được     |
| 3             | `.gitignore` ở **thư mục cha**                           | Local              | ✅ Commit được     |
| 4             | `$GIT_DIR/info/exclude`                                  | Chỉ local repo này | ❌ Không commit    |
| 5 (thấp nhất) | `core.excludesFile` (mặc định `~/.config/git/ignore`)    | Toàn user          | ❌ Không commit    |

**Quy tắc "cuối cùng thắng"**: Trong **cùng một file**, pattern ở dòng dưới ghi đè dòng trên. Giữa các file, file ở thư mục **sâu hơn** (gần file hơn) ghi đè file ở thư mục cha.

Ví dụ:
```gitignore
# .gitignore ở root
*.log
!debug.log
```
```gitignore
# logs/.gitignore
*.log          # quay lại ignore tất cả .log trong logs/
```
→ `logs/debug.log` **bị ignore** (vì `logs/.gitignore` sâu hơn ghi đè negation ở root). Đây là hiệu ứng **tương đối theo vị trí file `.gitignore`** — một khái niệm rất hay bị bỏ qua.

### 4.1 `.git/info/exclude` vs `.gitignore`

- `.git/info/exclude`: ignore **cục bộ**, **không** được chia sẻ khi clone — dùng cho file cá nhân (vd: `.vscode/`, `.idea/` nếu bạn không muốn commit).
- `.gitignore`: được commit → **cả team** dùng chung.
- Global `~/.config/git/ignore` (hoặc `core.excludesFile`): áp dụng cho **mọi repo** của user — dùng cho OS junk (`.DS_Store`, `Thumbs.db`, `.idea/`).

## 5. Các tình huống đặc biệt

### 5.1 File `.gitignore` lồng nhau

Mỗi thư mục có thể có `.gitignore` riêng. Git **áp dụng tất cả** — file ở thư mục con áp dụng cho phạm vi thư mục đó và con cháu. Đây là cách tổ chức ignore theo module:

```
project/
├── .gitignore          # quy tắc chung
├── backend/
│   └── .gitignore      # quy tắc riêng cho backend (vd: *.pyc)
└── frontend/
    └── .gitignore      # quy tắc riêng (vd: node_modules/)
```

### 5.2 Symlink và submodule

- Symlink **không** bị theo pattern trong `.gitignore` của target — pattern áp dụng cho đường dẫn symlink.
- Nội dung bên trong **submodule** không bị `.gitignore` của repo cha chi phối (vì submodule có repo riêng).

### 5.3 Case sensitivity

Mặc định Git tôn trọng **case sensitivity của filesystem**, nhưng trên Windows/macOS (case-insensitive), `*.TMP` và `*.tmp` có thể bị coi là như nhau. `core.ignoreCase` điều khiển điều này — nó **tự detect** khi init. Lưu ý: đây là về **tên file**, còn pattern ignore **luôn** phân biệt hoa/thường (Git dùng fnmatch case-sensitive trừ khi cấu hình).

### 5.4 Debug: Tại sao file này bị/không bị ignore?

```bash
git check-ignore -v <path>
```

Output ví dụ:
```
.gitignore:3:*.log	debug.log
```
→ Dòng 3 của `.gitignore`, pattern `*.log`, khớp `debug.log`. Đây là **công cụ chẩn đoán chuẩn** cho mọi vấn đề ignore.

```bash
git check-ignore -v --no-index <path>   # ép kiểm tra cả file đã track
git ls-files -i -c --exclude-standard   # file đã tracked NHƯNG khớp ignore — "ô uế"
git status --ignored                    # liệt kê cả file bị ignore
```

`git ls-files -i -c --exclude-standard` rất hữu ích để phát hiện file **đã lỡ commit** mà ignore rule muốn chặn — dấu hiệu cần `git rm --cached`.

### 5.5 Template `.gitignore`

Git hỗ trợ **template** theo ngôn ngữ:

```bash
git config --global init.templateDir ~/.git-templates
# hoặc dùng gitignore.io / github/gitignore repo
```

Các mẫu chuẩn (Node, Python, Go, Java...) được cộng đồng duy trì tại `github/gitignore`. Không có "template tự động" tích hợp — nhưng nhiều IDE/CLI (`gitignore.io`, `gibo`) sinh ra từ bộ template.

## 6. Khi nào KHÔNG nên dùng `.gitignore`

- **Bí mật** (`.env`, `credentials.json`): `.gitignore` **không đủ an toàn** vì một khi đã commit, lịch sử vẫn chứa. Phải coi trọng như "phòng thủ nhiều lớp": ignore + pre-commit hook + secret scanning (git-secrets, gitleaks, trufflehog).
- **File generated nhưng cần commit** (vd: `package-lock.json`, `Cargo.lock`): **không** ignore — chúng đảm bảo reproducible build. Quyết định ignore phụ thuộc ngữ nghĩa dự án, không phải mặc định.
- **File cần versioned nhưng tạm thời không** — dùng `git update-index --assume-unchanged` hoặc `--skip-worktree` (xem mục 7.2).

## 7. Xử lý khi đã lỡ track

### 7.1 `git rm --cached`

```bash
git rm --cached <path>       # bỏ khỏi index, GIỮ file trên đĩa
git rm -r --cached <dir>     # đệ quy
git commit -m "chore: stop tracking <path>"
```

**Cơ chế**: `git rm --cached` chỉ xóa entry khỏi **index**, không chạm working tree. File thành untracked → ignore rule áp dụng lại. Commit cần thiết để **ghi nhận việc xóa khỏi repo** (không phải xóa khỏi lịch sử — file vẫn tồn tại trong các commit cũ, ai clone về vẫn xem được lịch sử cũ!).

**Lưu ý lý thuyết quan trọng**: `git rm --cached` **không** xóa file khỏi lịch sử. Muốn xóa hoàn toàn phải **rewrite history** (`git filter-repo`, `BFG Repo-Cleaner`) — thao tác phá hủy, đổi mọi SHA từ commit đó về sau, cần `force push` và notify team.

### 7.2 `--assume-unchanged` vs `--skip-worktree`

Hai cờ **tinh tế**, hay bị nhầm:

| Cờ                   | Mục đích thiết kế                                                              | Ngữ nghĩa                                                                                                      |
| -------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `--assume-unchanged` | Tăng performance — Git **tin** file không đổi, không check                     | Nếu file đổi, Git **không** phát hiện — nguy hiểm, có thể ghi đè mất thay đổi khi checkout                     |
| `--skip-worktree`    | File **đã track** nhưng bạn muốn thay đổi local mà không commit (config riêng) | Git **biết** sẽ có thay đổi nhưng vẫn giữ nguyên index; an toàn hơn khi pull/merge (nhưng vẫn có thể conflict) |

```bash
git update-index --skip-worktree config/local.yaml
git update-index --no-skip-worktree config/local.yaml
git ls-files -v | grep ^S      # liệt kê file skip-worktree
```

**Không dùng hai cờ này thay thế `.gitignore`** — chúng là workaround cho trường hợp không thể ignore (file config chia sẻ giữa team).

# PHẦN B — GIT LOG

## 1. Lý thuyết: `git log` đọc cái gì?

`git log` **không** đọc working tree, **không** đọc index. Nó **duyệt đồ thị commit** (DAG) bắt đầu từ một hoặc nhiều **đỉnh xuất phát** (revision/commit) và in ra thông tin commit object.

### 1.1 Các đỉnh xuất phát (revision)

```bash
git log                    # HEAD (branch hiện tại)
git log main               # ref main
git log HEAD~3             # tổ tiên bậc 3 (3 commit cha liên tiếp)
git log HEAD~3..HEAD       # range
git log main..feature      # commit có ở feature nhưng KHÔNG ở main
git log main...feature     # symmetric difference — cả hai phía, trừ common ancestor
git log --all              # tất cả refs
git log --all --graph      # vẽ DAG
git log <SHA>              # commit bất kỳ
git log <tag>              # tag (annotated tag → commit nó trỏ tới)
```

### 1.2 Cách Git duyệt DAG

Mặc định: **topological + chronological** — nó duyệt từ đỉnh ngược về cha, ưu tiên commit mới hơn về thời gian (committer date), nhưng đảm bảo **không in commit con trước commit cha** (topo order). Với DAG nhiều nhánh, `--date-order`, `--author-date-order`, `--topo-order` điều khiển thứ tự.

**Điểm mấu chốt**: `git log` mặc định duyệt **tất cả tổ tiên có thể đến được từ đỉnh** (reachable). Nó **không** liệt kê commit "mồ côi" (unreachable) — chúng nằm trong `git fsck --lost-found` và reflog nhưng không hiển thị qua `git log`.

### 1.3 Range `..` và `...`

| Range   | Nghĩa                                  | Công thức tập hợp                   |
| ------- | -------------------------------------- | ----------------------------------- |
| `A..B`  | Commit có ở B nhưng không ở A          | `reachable(B) \ reachable(A)`       |
| `A...B` | Symmetric diff                         | `reachable(A) △ reachable(B)` (XOR) |
| `A^!`   | A và các cha trực tiếp (trừ cha chung) | merge commit "loại bỏ cha"          |
| `A^@`   | Tất cả cha của A                       | —                                   |
| `A^-`   | —                                      | —                                   |

`A..B` là **công cụ lọc commit cho review**: `main..feature` = "commit trên nhánh feature chưa merge vào main".

## 2. Định dạng output — `--pretty` và `--format`

### 2.1 Các chế độ `--pretty`

| Mode              | Nội dung                            |
| ----------------- | ----------------------------------- |
| `oneline`         | `<short-SHA> <subject>`             |
| `short`           | SHA + author + subject              |
| `medium`          | Mặc định — đầy đủ header + body     |
| `full`            | Medium + committer                  |
| `fuller`          | Full + author date + committer date |
| `reference`       | `<short-SHA> (<subject>, <date>)`   |
| `email`           | Raw patch format                    |
| `raw`             | Mọi trường kể cả tree/parent SHA    |
| `format:<string>` | Custom                              |

### 2.2 Placeholder quan trọng (`--pretty=format:`)

| Placeholder             | Ý nghĩa                    |
| ----------------------- | -------------------------- |
| `%H`                    | Full commit SHA            |
| `%h`                    | Short SHA                  |
| `%T` / `%t`             | Tree SHA                   |
| `%P` / `%p`             | Parent SHA                 |
| `%an` / `%ae` / `%ad`   | Author name/email/date     |
| `%cn` / `%ce` / `%cd`   | Committer name/email/date  |
| `%s`                    | Subject (dòng đầu message) |
| `%b`                    | Body (phần sau subject)    |
| `%B`                    | Toàn bộ message            |
| `%d` / `%D`             | Ref names (branch, tag)    |
| `%N`                    | Notes                      |
| `%e`                    | Encoding                   |
| `%n`                    | Newline                    |
| `%C(color)` / `%Creset` | Màu                        |

Ví dụ hữu ích:

```bash
git log --pretty=format:"%h %ad | %s%d [%an]" --date=short
git log --pretty=format:"%H" > commits.txt      # danh sách SHA cho tooling
```

### 2.3 Date format

```bash
--date=relative     # "2 days ago"
--date=local        # timezone local
--date=iso          # 2024-01-15 10:30:00 +0700
--date=iso-strict   # 2024-01-15T10:30:00+07:00
--date=short        # 2024-01-15
--date=unix         # epoch
--date=format:"%Y-%m-%d %H:%M"
```

## 3. Lọc commit — Đây là "sức mạnh thực sự"

### 3.1 Lọc theo tác giả / thời gian

```bash
git log --author="Nguyen"              # substring hoặc regex
git log --committer="CI Bot"
git log --since="2 weeks ago"
git log --until="2024-12-31"
git log --after="2024-01-01" --before="2024-06-30"
git log --grep="fix bug"               # tìm trong message
git log --grep="^feat" -i              # regex, case-insensitive
git log --invert-grep --grep="WIP"     # loại trừ
git log --merges                       # chỉ merge commit
git log --no-merges                    # bỏ merge commit
git log --first-parent                 # theo "main line" — bỏ nhánh phụ
```

**`--first-parent`** quan trọng về lý thuyết: với lịch sử merge, `git log` thường đi vào **cả nhánh phụ** (duyệt toàn bộ DAG). `--first-parent` chỉ đi theo **cha đầu tiên** (nhánh đích của merge) → cho **cái nhìn "lịch sử chính"** như release history. Rất hữu ích cho release notes.

### 3.2 Lọc theo nội dung thay đổi

```bash
git log -S "function_name"        # "pickaxe": commit thay đổi SỐ LẦN xuất hiện của chuỗi
git log -G "regex"                # commit mà diff của nó khớp regex (kể cả thay đổi nhỏ)
git log -S "foo" --pickaxe-regex
git log -- <path>                 # commit chạm tới path
git log --follow -- <file>        # theo dõi file qua rename (chỉ 1 file)
git log --diff-filter=A -- <path> # chỉ commit ADD file
git log --diff-filter=DM          # Deleted hoặc Modified
```

**Phân biệt `-S` vs `-G`**: `-S` (pickaxe) tìm commit mà **số lần xuất hiện** của chuỗi thay đổi (thêm hoặc xóa). `-G` tìm commit mà **diff chứa thay đổi khớp regex** (kể cả dòng sửa trong đó). `-S` là "khi nào dòng này xuất hiện/mất đi", `-G` là "khi nào có sửa đổi liên quan".

### 3.3 Lọc theo pickaxe (path)

```bash
git log -- "src/*.ts"
git log --no-merges -- "README.md"
```

### 3.4 Giới hạn số lượng

```bash
git log -n 10          # 10 commit gần nhất
git log --max-count=10
git log --skip=5 -n 10 # pagination
```

## 4. Hiển thị thay đổi (diff trong log)

```bash
git log -p                    # kèm patch (diff)
git log --stat                # thống kê file thay đổi (+/-)
git log --shortstat           # 1 dòng tổng kết
git log --numstat             # số dòng thêm/xóa cho mỗi file (machine-readable)
git log --name-only           # tên file
git log --name-status         # tên + trạng thái (M/A/D/R)
git log --word-diff           # diff theo từ, không theo dòng
git log -p -U3                # context 3 dòng (mặc định)
```

**Lưu ý lý thuyết**: `git log -p` tính diff **giữa mỗi commit và cha nó**, tại thời điểm in — nó **không lưu diff** trong commit object. Commit object chỉ có tree; diff được **tính lại** khi cần. Đây là lý do `git show`/`git log -p` trên repo lớn có thể chậm.

## 5. Log đồ thị (`--graph`)

```bash
git log --graph --oneline --all --decorate
```

**`--decorate`** hiển thị ref (branch, tag) — mặc định bật từ Git 2.13 với `oneline`. Output:

```
*   a1b2c3d (HEAD -> main, origin/main) Merge pull request #42
|\
| * e4f5g6h (feature/login) fix: validate email
| * i7j8k9l feat: login form
|/
* m0n1o2p chore: initial commit
```

**Cách đọc**: `*` = commit; `|` = nhánh đang đi xuống; `/\` = merge/fork. Cột trái là thời gian (mới nhất trên cùng).

Alias phổ biến:
```bash
git config --global alias.lg "log --graph --oneline --all --decorate"
```

## 6. Các lệnh "anh em" của `git log`

| Lệnh                    | Khác `git log` ở đâu                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------- |
| `git show <rev>`        | 1 commit (hoặc tag/blob/tree) — mặc định HEAD. Hiển thị message + diff                                        |
| `git show <tag>^{}`     | Dereference annotated tag tới commit                                                                          |
| `git show <rev>:<path>` | Nội dung blob tại path trong rev (không cần checkout)                                                         |
| `git whatchanged`       | Như log --raw --no-merges (legacy)                                                                            |
| `git reflog`            | Lịch sử di chuyển của HEAD — **kể cả commit "mất"** không hiển thị trong log. Cứu hồi commit sau reset/rebase |
| `git shortlog`          | Tổng hợp theo author (dùng cho release notes)                                                                 |
| `git blame`             | Theo dòng, không theo commit — nhưng cùng nguồn dữ liệu                                                       |

### 6.1 `git shortlog` — Công cụ tổng hợp

```bash
git shortlog -sn --all                     # số commit theo author, sort desc
git shortlog -sne --since="1 month ago"    # kèm email
git shortlog --no-merges -w                 # wrap
git shortlog -e                            # kèm email
```

Dùng để **thống kê đóng góp** hoặc **sinh release notes** (kết hợp với range `v1.0..v2.0`).

### 6.2 `git reflog` — "hộp đen" của HEAD

```bash
git reflog                    # HEAD reflog
git reflog show main          # reflog của branch main
git reflog --date=iso
```

Reflog ghi **mọi thay đổi của ref** trong ~90 ngày (mặc định `gc.reflogExpire`). Đây là **công cụ cứu hộ** khi `git reset --hard` hay `git rebase` làm mất commit: commit vẫn nằm trong objects, chỉ không còn reachable từ ref → reflog giữ SHA để bạn `git reset --hard <sha>` quay lại. **`git log` không thấy** các commit này, nhưng `reflog` thì có.

## 7. Một số option nâng cao về lý thuyết

### 7.1 `--boundary` và range

`git log main..feature --boundary` hiển thị thêm các commit biên (ngay dưới điểm rẽ nhánh) — dùng để hiểu ngữ cảnh merge.

### 7.2 `--cherry-pick` và `--cherry-mark`

Với `A...B`, `--cherry-pick` loại các commit có **patch-id tương đương** ở cả hai phía (đã cherry-pick qua lại). `--cherry-mark` đánh dấu `=` (tương đương) và `+` (mới). Hữu ích khi review nhánh đã rebase/cherry-pick.

### 7.3 `--ancestry-path`

`git log --ancestry-path A..B` chỉ giữ commit **nằm trên đường đi từ A đến B** — kể cả commit merge. Khác `A..B` thông thường: nó lọc cả commit nhánh phụ không nằm trên đường A→B.

### 7.4 `--reverse`

Đảo thứ tự — hữu ích khi muốn đọc commit từ cũ đến mới (vd: hiểu evolution của feature).

### 7.5 `--no-renames`, `-M`, `-C`

Ảnh hưởng **phát hiện rename** khi diff:
- `-M` (mặc định bật): phát hiện rename (dựa trên similarity).
- `-C`: phát hiện copy.
- `--no-renames`: tắt hẳn.

Điều này ảnh hưởng `--stat`, `-p` — vì Git phải so sánh similarity giữa các file.

### 7.6 `log.follow` và follow file qua rename

`git log --follow -- file` **chỉ follow 1 file** (giới hạn của Git — không hỗ trợ đa file). Cơ chế: mỗi commit, Git thử match similarity để tìm nguồn gốc file trong commit trước. Đây là heuristic, không phải dữ liệu lưu sẵn.

## 9. Tổng kết lý thuyết

### Về `.gitignore`
- Ignore **chỉ áp dụng untracked file** — đã track thì vô hiệu.
- Thứ tự ưu tiên: CLI > `.gitignore` sâu > `.gitignore` cha > `info/exclude` > global. Trong cùng file: **dòng cuối thắng**.
- Negation `!` **không thể** re-include file nếu thư mục cha bị ignore "chặn duyệt" — phải dùng `dir/*`.
- Dấu `/` đầu = neo root; `/` giữa = neo tương đối; `/` cuối = directory-only; không có `/` = khớp mọi cấp.
- `git rm --cached` chỉ bỏ khỏi index — **không xóa khỏi lịch sử**. Muốn xóa hoàn toàn phải rewrite history.
- Dùng `git check-ignore -v` để debug.

### Về `git log`
- `git log` duyệt **DAG các commit reachable từ đỉnh**, không đọc working tree.
- Range `A..B` = reachable(B) − reachable(A); `A...B` = symmetric diff.
- `--first-parent` = "main line view"; `--graph` vẽ DAG; `--decorate` hiển thị ref.
- `-S` (pickaxe) tìm thay đổi **số lần xuất hiện**; `-G` tìm **regex trong diff**.
- `--follow` chỉ 1 file, dùng heuristic rename.
- `reflog` cứu commit "mất" — thứ `log` không thấy.
- Commit object **không chứa diff** — diff được tính lại mỗi lần in (`-p`, `--stat`), nên các option rename-detection (`-M`, `-C`) ảnh hưởng output nhưng không ảnh hưởng dữ liệu.

**Điểm chung cốt lõi**: Git là **content-addressable filesystem** với DAG commit. `.gitignore` là bộ lọc **đầu vào** (quyết định file nào vào index), `git log` là cửa sổ **đọc DAG** (duyệt và trình bày commit). Cả hai đều không "lưu trạng thái" riêng — `.gitignore` là text pattern, `git log` là truy vấn trên đối tượng bất biến.
