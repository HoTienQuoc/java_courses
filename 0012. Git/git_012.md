# Git Reset — Giải thích lý thuyết chi tiết

---

## 1. Bản chất: `git reset` thực sự làm gì?

### 1.1 Định nghĩa cốt lõi

**`git reset`** là lệnh **di chuyển con trỏ `HEAD`** (và/hoặc branch hiện tại) về một commit khác, đồng thời **tùy chọn** cập nhật **Index** và **Working Directory** để khớp với commit đó.

> **Điểm lý thuyết quan trọng nhất**: `git reset` **không xóa commit**. Nó chỉ **di chuyển con trỏ** (branch ref) về commit cũ hơn. Các commit "bị bỏ" vẫn tồn tại trong objects — chúng chỉ trở thành **unreachable** (không còn branch nào trỏ tới), và sẽ bị garbage collector dọn sau ~30 ngày (mặc định).

### 1.2 `reset` là "nghịch đảo" của `commit`

Đây là cách hiểu trực quan nhất:

```
COMMIT (tiến lên):
  Working Tree ──add──► Index ──commit──► Commit mới
                                          ↑
                                          HEAD di chuyển tới

RESET (lùi lại):
  Working Tree ◄──?── Index ◄──?── Commit cũ
                                    ↑
                                    HEAD di chuyển về
```

**Lý thuyết**: `commit` ghi **từ Working Tree → Index → History**. `reset` có thể **di chuyển HEAD ngược lại** và **tùy chọn** đồng bộ Index/Working Tree theo commit đích.

### 1.3 Ba "cây" — Nền tảng để hiểu `reset`

Mọi mode của `reset` được định nghĩa bởi **cái gì xảy ra với ba cây**:

```
┌─────────────────────┐    ┌──────────────────┐    ┌─────────────────────┐
│  Working Directory  │    │  Index (Staging) │    │  Commit History     │
│  (file trên đĩa)    │    │  (.git/index)    │    │  (refs/heads/, HEAD)│
└─────────────────────┘    └──────────────────┘    └─────────────────────┘
         Cây 1                    Cây 2                     Cây 3
```

**Bảng tổng hợp các mode** — đây là **bảng quan trọng nhất** của toàn bài:

| Mode                 | HEAD (Cây 3) | Index (Cây 2)       | Working Tree (Cây 1)      |
| -------------------- | ------------ | ------------------- | ------------------------- |
| `--soft`             | ✅ Di chuyển  | ❌ Không đổi         | ❌ Không đổi               |
| `--mixed` (mặc định) | ✅ Di chuyển  | ✅ Reset theo commit | ❌ Không đổi               |
| `--hard`             | ✅ Di chuyển  | ✅ Reset             | ✅ Reset                   |
| `--merge`            | ✅ Di chuyển  | ✅ Reset             | ⚠️ Chỉ file không conflict |
| `--keep`             | ✅ Di chuyển  | ✅ Reset             | ⚠️ Chỉ nếu an toàn         |

**Quy tắc ghi nhớ**: 
- `--soft` = chỉ cây 3 (lịch sử).
- `--mixed` = cây 3 + 2 (lịch sử + index).
- `--hard` = cây 3 + 2 + 1 (tất cả).

## 2. Cú pháp và các dạng của `git reset`

### 2.1 Hai dạng chính

Git `reset` có **hai chế độ hoàn toàn khác nhau** — đây là nguồn gốc nhiều nhầm lẫn:

#### Dạng 1: Reset theo commit (di chuyển HEAD)

```bash
git reset [<mode>] <commit>
```

- `HEAD`, `refs/heads/<branch>` di chuyển về `<commit>`.
- Index và Working Tree tùy mode.
- **Ảnh hưởng toàn bộ repo**, không chỉ file cụ thể.

#### Dạng 2: Reset theo path (bỏ stage file)

```bash
git reset [<commit>] -- <path>...
git reset <path>...
```

- **KHÔNG** di chuyển HEAD.
- Chỉ cập nhật **Index** cho các path được chỉ định.
- **Tương đương** `git restore --staged <path>` (lệnh hiện đại).

**Lý thuyết**: Hai dạng chia sẻ tên nhưng **ngữ nghĩa khác hẳn**. Dạng 1 thao tác trên commit/branch, dạng 2 thao tác trên index. Sự nhầm lẫn này là lý do Git tách `git restore` (Git ≥2.23) ra để làm rõ.

### 2.2 Cú pháp đầy đủ

```bash
git reset [--soft | --mixed | --hard | --merge | --keep] [-q] [<commit>]
git reset [--mixed] [-q] [<commit>] [--] <pathspec>...
git reset [--mixed] [-q] [<commit>] [--] <pathspec>...
```

**Mặc định**: Nếu không chỉ định mode → `--mixed`. Nếu không chỉ định commit → `HEAD`.

## 3. `--soft` — Di chuyển con trỏ, giữ mọi thứ

### 3.1 Cơ chế

```bash
git reset --soft HEAD~1
```

**Hành động**:
- `HEAD` → commit cha (HEAD~1).
- Branch hiện tại → commit cha.
- **Index: KHÔNG đổi**.
- **Working Tree: KHÔNG đổi**.

### 3.2 Minh họa

```
Trước:
  A ← B ← C   (main, HEAD)
  
  Working tree: giống C
  Index: giống C

git reset --soft B:

Sau:
  A ← B   (main, HEAD)
      ↖
       C  (unreachable, chỉ reflog)

  Working tree: giống C    ← KHÔNG đổi
  Index: giống C           ← KHÔNG đổi
```

**Kết quả**: Commit `C` "biến mất" khỏi lịch sử branch, nhưng **nội dung của C vẫn còn nguyên trong Index** — sẵn sàng để commit lại.

### 3.3 Ứng dụng điển hình

#### Gộp nhiều commit thành một

```bash
# Có 3 commit gần nhất muốn gộp
git reset --soft HEAD~3
# → HEAD về trước 3 commit
# → Index chứa toàn bộ thay đổi của 3 commit

git commit -m "feat: gộp 3 commit"
# → 1 commit mới thay thế 3 commit cũ
```

**Lý thuyết**: `--soft` + `commit` = **gộp commit** (tương tự `squash` nhưng không cần interactive rebase). Đơn giản hơn khi gộp **các commit liền kề gần nhất**.

#### Sửa commit gần nhất (thay `--amend`)

```bash
git reset --soft HEAD~1
# Sửa file
git add .
git commit -m "feat: sửa lại message và nội dung"
```

**Khác `--amend`**: `--amend` gộp vào commit cũ (giữ metadata). `--soft HEAD~1` tạo commit **hoàn toàn mới**. Kết quả tương tự, nhưng `--soft` linh hoạt hơn (có thể tách commit nếu muốn).

#### Di chuyển commit sang branch khác

```bash
# Đang ở feature, commit cuối cùng thực ra thuộc main
git reset --soft HEAD~1        # gỡ commit khỏi feature, giữ trong Index
git stash                       # cất thay đổi
git switch main
git stash pop                   # lấy lại
git commit -m "commit thuộc main"
```

#### Hủy commit nhưng giữ thay đổi để làm lại

```bash
git reset --soft HEAD~1
# Bây giờ có thể:
# - Commit lại với message khác
# - Tách thành nhiều commit
# - Bỏ một phần (git restore --staged <file>)
```

### 3.4 Điểm mạnh và điểm yếu

**Mạnh**: **Không bao giờ mất dữ liệu** — Index và Working Tree nguyên vẹn. An toàn nhất trong các mode.

**Yếu**: Không "reset" thực sự — Index vẫn chứa thay đổi cũ. Nếu muốn **xóa hoàn toàn** commit → dùng `--hard`.

## 4. `--mixed` (mặc định) — Di chuyển con trỏ + reset Index

### 4.1 Cơ chế

```bash
git reset HEAD~1              # tương đương git reset --mixed HEAD~1
```

**Hành động**:
- `HEAD` → commit cha.
- Branch → commit cha.
- **Index: reset về commit cha** (bỏ mọi staged changes).
- **Working Tree: KHÔNG đổi**.

### 4.2 Minh họa

```
Trước:
  A ← B ← C   (main, HEAD)
  
  Working tree: giống C
  Index: giống C

git reset --mixed B:

Sau:
  A ← B   (main, HEAD)
      ↖
       C  (unreachable)

  Working tree: giống C    ← KHÔNG đổi
  Index: giống B           ← RESET về B
```

**Kết quả**: 
- Commit `C` biến mất khỏi lịch sử.
- Thay đổi của `C` **vẫn còn trong Working Tree**, nhưng **không còn staged** — chúng trở thành **unstaged changes**.
- `git status` sẽ hiện chúng trong "Changes not staged for commit".

### 4.3 Ứng dụng điển hình

#### Bỏ stage tất cả file

```bash
git add .                       # stage tất cả (nhầm)
git reset                       # bỏ stage tất cả — tương đương git reset HEAD
```

**Lý thuyết**: `git reset` (không tham số) = `git reset --mixed HEAD` = **bỏ stage mọi thứ**, giữ nguyên Working Tree. Đây là lệnh **cứu cánh** khi lỡ `git add .` nhầm.

#### Hủy commit, giữ thay đổi nhưng chưa stage

```bash
git reset HEAD~1
# → Commit bị hủy
# → Thay đổi vẫn trong Working Tree
# → Nhưng KHÔNG staged

# Giờ có thể:
git add -p                      # stage từng phần
git commit -m "commit 1"
git add .
git commit -m "commit 2"
```

**Lý thuyết**: `--mixed` linh hoạt hơn `--soft` — cho phép **chọn lọc lại** thay đổi nào stage, thay đổi nào bỏ.

#### Xem lại thay đổi của commit vừa hủy

```bash
git reset HEAD~1
git diff                        # xem tất cả thay đổi (unstaged)
git diff --staged               # (rỗng — vì chưa stage)
```

### 4.4 Vì sao `--mixed` là mặc định?

**Lý do thiết kế**: `--mixed` là **trung gian an toàn nhất**:
- Không mất dữ liệu (Working Tree giữ nguyên).
- Không "giữ rác" trong Index (Index reset sạch).

Người dùng có thể **quyết định lại** từ đầu: stage gì, commit gì. Đây là hành vi "an toàn mặc định" của Git.

## 5. `--hard` — Reset toàn diện (nguy hiểm nhất)

### 5.1 Cơ chế

```bash
git reset --hard HEAD~1
```

**Hành động**:
- `HEAD` → commit cha.
- Branch → commit cha.
- **Index: reset về commit cha**.
- **Working Tree: reset về commit cha** — **GHI ĐÈ mọi thay đổi** (kể cả chưa commit!).

### 5.2 Minh họa

```
Trước:
  A ← B ← C   (main, HEAD)
  
  Working tree: giống C + thay đổi chưa commit
  Index: giống C + staged changes

git reset --hard B:

Sau:
  A ← B   (main, HEAD)
      ↖
       C  (unreachable)

  Working tree: giống B    ← GHI ĐÈ
  Index: giống B           ← GHI ĐÈ
```

**Kết quả**: 
- Commit `C` biến mất.
- **Mọi thay đổi chưa commit trong Working Tree bị XÓA VĨNH VIỄN** (không cứu được qua reflog!).
- Mọi staged changes bị xóa.

### 5.3 Tại sao `--hard` nguy hiểm?

**Lý thuyết quan trọng**: 
- Commit "bị bỏ" → **cứu được** qua reflog (vì là Git object).
- Thay đổi **chưa commit** → **KHÔNG cứu được** (vì chưa bao giờ là Git object!).

```
Cứu được:
  ✅ Commit (đã tồn tại trong .git/objects)
  ✅ Staged changes (đã có trong .git/index — nhưng khó cứu)

KHÔNG cứu được:
  ❌ Thay đổi unstaged trong Working Tree
  ❌ File untracked (chưa từng biết tới Git)
```

**Đây là lý do `--hard` được coi là "lệnh nguy hiểm nhất"** — nó có thể xóa **công việc chưa được lưu vào Git**.

### 5.4 Các ứng dụng

#### Hủy hoàn toàn commit + thay đổi

```bash
git reset --hard HEAD~3
# → Mất 3 commit gần nhất
# → Mất mọi thay đổi chưa commit
```

**Chỉ dùng khi chắc chắn 100%** muốn bỏ hết.

#### Đồng bộ với remote

```bash
git fetch origin
git reset --hard origin/main
# → Local = remote (bỏ mọi commit/thay đổi local)
```

**Ứng dụng**: "Cho tôi về đúng trạng thái remote, bỏ hết công việc local". Dùng khi:
- Branch local bị rối.
- Muốn bắt đầu lại từ remote.
- Sau khi lỡ commit nhầm nhiều thứ.

#### Hủy merge/rebase đang dở

```bash
git reset --hard ORIG_HEAD
# → Quay về trước merge/rebase
```

**Lý thuyết**: `ORIG_HEAD` = vị trí HEAD trước thao tác nguy hiểm gần nhất. `--hard ORIG_HEAD` = "hủy thao tác vừa làm".

### 5.5 `--hard` có cứu được không?

**Commit**: Có, qua reflog:
```bash
git reset --hard HEAD~3        # mất 3 commit
git reflog                     # tìm SHA cũ
git reset --hard <sha-cũ>      # cứu
```

**Thay đổi chưa commit**: Không. Đã mất vĩnh viễn.

**File untracked**: Không (nhưng `--hard` không đụng tới untracked — chúng vẫn còn).

**Lưu ý**: `--hard` **KHÔNG xóa untracked files** — đó là việc của `git clean`. Đây là điểm hay bị hiểu nhầm.

## 6. `--merge` và `--keep` — Các mode trung gian

### 6.1 `--merge`

```bash
git reset --merge <commit>
```

**Hành động**:
- `HEAD` → commit.
- **Index: reset** về commit.
- **Working Tree: reset CÁC FILE KHÔNG CÓ thay đổi chưa commit**. Các file có thay đổi chưa commit → **giữ nguyên** (không ghi đè).

**Lý thuyết**: `--merge` được thiết kế cho **hủy merge** — reset về trước merge mà **không mất thay đổi chưa commit trong file không liên quan**.

**Ứng dụng**:
```bash
git merge feature
# ... conflict ...
git reset --merge ORIG_HEAD
# → Hủy merge, giữ thay đổi chưa commit trong file khác
```

**Khác `--hard`**: `--hard` xóa **tất cả** thay đổi chưa commit. `--merge` chỉ reset file **không có thay đổi** (file có thay đổi được giữ).

### 6.2 `--keep`

```bash
git reset --keep <commit>
```

**Hành động**:
- `HEAD` → commit.
- **Index: reset** về commit.
- **Working Tree: reset CHỈ KHI an toàn** — tức là **không ghi đè** file có thay đổi chưa commit.

**Khác `--merge`**: `--keep` **từ chối** reset nếu có file **vừa có thay đổi chưa commit VÀ khác giữa commit hiện tại và commit đích** → tránh mất dữ liệu.

**Ứng dụng**:
```bash
git reset --keep HEAD~1
# Nếu an toàn (không conflict với thay đổi chưa commit) → OK
# Nếu không → từ chối, báo lỗi
```

**Lý thuyết**: `--keep` = "reset nếu an toàn, từ chối nếu có thể mất dữ liệu". Đây là mode **an toàn nhất** khi muốn di chuyển HEAD mà giữ thay đổi chưa commit.

### 6.3 So sánh `--merge` vs `--keep`

|                                      | `--merge`                               | `--keep`               |
| ------------------------------------ | --------------------------------------- | ---------------------- |
| File có thay đổi chưa commit         | Giữ nguyên                              | Giữ nguyên             |
| File không thay đổi chưa commit      | Reset                                   | Reset                  |
| File có thay đổi VÀ khác giữa commit | **Giữ thay đổi** (có thể conflict ngầm) | **TỪ CHỐI reset**      |
| Khi nào dùng                         | Hủy merge                               | Di chuyển HEAD an toàn |

**Lý thuyết**: `--merge` **chấp nhận** có thể có file "nửa reset" (giữa commit cũ và mới). `--keep` **từ chối** nếu không thể reset sạch — an toàn hơn.

## 7. Reset theo path — Dạng thứ hai

### 7.1 Cú pháp

```bash
git reset [<commit>] -- <path>...
```

**Hành động**:
- **KHÔNG** di chuyển HEAD.
- Chỉ cập nhật **Index** cho `<path>` — lấy nội dung từ `<commit>` (mặc định HEAD).
- Working Tree không đổi.

### 7.2 Cơ chế

```bash
git reset HEAD -- file.js
# → Index của file.js = phiên bản trong HEAD
# → Working tree của file.js KHÔNG đổi
# → Tương đương: git restore --staged file.js
```

**Lý thuyết**: Đây là cách **bỏ stage** một file cụ thể. Git lấy phiên bản trong commit (mặc định `HEAD`) và ghi vào index, ghi đè phiên bản đã staged.

### 7.3 Các biến thể

```bash
# Bỏ stage file cụ thể
git reset HEAD file.js
git reset file.js                  # tương đương (mặc định HEAD)

# Bỏ stage tất cả
git reset
git reset HEAD
git reset .

# Bỏ stage về commit cụ thể (hiếm)
git reset <sha> -- file.js         # index = file.js trong <sha>

# Bỏ stage + xem diff
git reset -p                       # interactive: chọn từng phần để bỏ stage
```

### 7.4 `-p` — Interactive reset

```bash
git reset -p
```

**Hành động**: Mở chế độ interactive — hiển thị từng hunk của thay đổi staged, hỏi bạn có muốn **bỏ stage** hunk đó không.

```
diff --git a/file.js b/file.js
@@ -1,3 +1,3 @@
 function foo() {
-  return 1;
+  return 2;
 }
Unstage this hunk [y,n,q,a,d,s,e,?]?
```

**Lý thuyết**: `-p` cho phép **bỏ stage một phần** của file — cực hữu ích khi muốn tách commit logic.

### 7.5 So sánh với `git restore --staged`

```bash
git reset HEAD file.js                # cũ
git restore --staged file.js          # mới (Git ≥2.23)
```

**Tương đương hoàn toàn**. `git restore --staged` là syntax mới, rõ nghĩa hơn. Git khuyến nghị dùng `restore` cho việc unstage.

**Lý do tách**: `git reset` quá tải nghĩa (vừa di chuyển HEAD, vừa unstage). `git restore` tách phần "làm việc với file" ra — dễ hiểu hơn.

## 8. `git reset` vs các lệnh khác — Bảng so sánh

### 8.1 Với `git restore`

| Mục đích                  | `git reset`           | `git restore`                          |
| ------------------------- | --------------------- | -------------------------------------- |
| Bỏ stage file             | `git reset HEAD file` | `git restore --staged file`            |
| Hủy thay đổi working tree | (không hỗ trợ)        | `git restore file`                     |
| Cả hai                    | (không có 1 lệnh)     | `git restore --staged --worktree file` |
| Di chuyển HEAD            | ✅                     | ❌                                      |

**Lý thuyết**: `restore` chỉ làm việc với **file/index**, không đụng tới lịch sử. `reset` làm cả hai. Git khuyến nghị `restore` cho thao tác file.

### 8.2 Với `git checkout`

`git checkout` cũ (trước Git 2.23) đảm nhận **cả ba việc**:
1. Đổi branch: `git checkout branch`.
2. Restore file: `git checkout -- file`.
3. Detach HEAD: `git checkout <sha>`.

Git tách thành:
- `git switch` → đổi branch.
- `git restore` → restore file.
- `git checkout <sha>` → detach (vẫn dùng `checkout`).

**`git reset` khác `checkout`**:
- `reset` **di chuyển branch ref** (HEAD và branch hiện tại).
- `checkout` **di chuyển HEAD** (detach) hoặc **đổi branch**.

### 8.3 Với `git revert`

|                           | `git reset`                 | `git revert`          |
| ------------------------- | --------------------------- | --------------------- |
| Viết lại lịch sử          | ✅                           | ❌                     |
| Tạo commit mới            | ❌                           | ✅ (commit đảo ngược)  |
| An toàn cho shared branch | ❌                           | ✅                     |
| Phạm vi                   | Nhiều commit                | 1 commit (hoặc range) |
| Kết quả                   | Commit bị "xóa" khỏi branch | Commit mới đảo ngược  |

**Lý thuyết**: `reset` = "xóa quá khứ". `revert` = "ghi lại quá khứ như chưa từng có". `reset` dùng cho **local**, `revert` dùng cho **shared**.

### 8.4 Bảng tổng hợp

| Lệnh                 | Chức năng                    | Viết lại lịch sử | An toàn shared |
| -------------------- | ---------------------------- | ---------------- | -------------- |
| `reset --soft`       | Di chuyển HEAD, giữ Index/WT | ✅                | ❌              |
| `reset --mixed`      | + reset Index                | ✅                | ❌              |
| `reset --hard`       | + reset WT (XÓA)             | ✅                | ❌              |
| `reset HEAD -- file` | Bỏ stage file                | ❌                | ✅              |
| `restore --staged`   | Bỏ stage file                | ❌                | ✅              |
| `restore`            | Hủy thay đổi WT              | ❌                | ✅              |
| `revert`             | Tạo commit đảo ngược         | ❌                | ✅              |
| `checkout`           | Đổi branch / detach          | ❌                | ✅              |

## 9. Phục hồi sau `reset` — Reflog

### 9.1 Tại sao cứu được?

`git reset` **không xóa** commit — chỉ di chuyển con trỏ. Commit cũ vẫn trong:
- `.git/objects/` (Git object store).
- **Reflog** (`.git/logs/HEAD`, `.git/logs/refs/heads/`).

**Reflog** giữ **mọi di chuyển của HEAD** trong ~90 ngày (mặc định `gc.reflogExpire`).

### 9.2 Quy trình cứu

```bash
# 1. Lỡ tay
git reset --hard HEAD~5        # mất 5 commit

# 2. Xem reflog
git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~5
# f7g8h9i HEAD@{1}: commit: feat: 5    ← commit cuối trước reset
# e5f6g7h HEAD@{2}: commit: feat: 4
# ...

# 3. Cứu
git reset --hard HEAD@{1}      # quay về vị trí trước reset
# hoặc
git reset --hard f7g8h9i
```

### 9.3 `ORIG_HEAD` — Hủy nhanh

```bash
git reset --hard ORIG_HEAD
```

**Lý thuyết**: `ORIG_HEAD` = HEAD trước thao tác nguy hiểm gần nhất (reset, merge, rebase). Nhanh hơn reflog khi mới reset.

### 9.4 Giới hạn — Cái gì KHÔNG cứu được

| Loại                             | Cứu được?               |
| -------------------------------- | ----------------------- |
| Commit bị reset                  | ✅ (reflog)              |
| Staged changes bị `--hard`       | ⚠️ Khó (index bị ghi đè) |
| **Unstaged changes bị `--hard`** | ❌ **MẤT VĨNH VIỄN**     |
| File untracked                   | ✅ (`--hard` không đụng) |

**Điểm mấu chốt**: `--hard` **không xóa** untracked files — đó là việc của `git clean`. Nhưng nó **xóa** unstaged changes — không cứu được.

## 10. Các tình huống thực tế

### 10.1 Lỡ `git add .` nhầm nhiều file

```bash
git add .                       # stage tất cả (nhầm)
git reset                       # bỏ stage tất cả, giữ WT
# → Tương đương git reset --mixed HEAD
```

**Lưu ý**: `git reset` (không tham số) **không** xóa thay đổi — chỉ bỏ stage.

### 10.2 Hủy commit gần nhất, giữ thay đổi

```bash
# Cách 1: --soft (giữ stage)
git reset --soft HEAD~1
# → Commit bị hủy, thay đổi VẪN staged

# Cách 2: --mixed (bỏ stage)
git reset HEAD~1
# → Commit bị hủy, thay đổi UNSTAGED

# Cách 3: --amend (sửa commit)
git commit --amend
```

**Chọn cái nào?**
- Muốn commit lại ngay → `--soft`.
- Muốn chọn lọc lại → `--mixed`.
- Muốn sửa message/nội dung commit → `--amend`.

### 10.3 Hủy hoàn toàn commit + thay đổi

```bash
git reset --hard HEAD~3
# → Mất 3 commit + mọi thay đổi chưa commit
```

**Cẩn thận**: Chỉ dùng khi chắc chắn. Cứu commit qua reflog, nhưng thay đổi chưa commit mất vĩnh viễn.

### 10.4 Đồng bộ với remote

```bash
git fetch origin
git reset --hard origin/main
# → Local = remote, bỏ mọi commit local
```

**Ứng dụng**: Branch local bị rối, muốn bắt đầu lại từ remote.

### 10.5 Hủy merge đang dở

```bash
git merge feature
# CONFLICT...
git reset --merge ORIG_HEAD
# → Hủy merge, giữ thay đổi chưa commit trong file khác
```

**Hoặc**:
```bash
git merge --abort              # cách chuẩn
```

### 10.6 Bỏ stage một file cụ thể

```bash
git reset HEAD file.js
# hoặc
git restore --staged file.js   # khuyến nghị
```

### 10.7 Gộp commit bằng `--soft`

```bash
# Có 5 commit lộn xộn, muốn gộp thành 1
git reset --soft HEAD~5
git commit -m "feat: một commit sạch"
```

**Lý thuyết**: Đơn giản hơn interactive rebase khi gộp **các commit liền kề gần nhất**. Với commit không liền kề → phải dùng rebase.

### 10.8 Di chuyển branch về commit cũ (giữ thay đổi)

```bash
git reset --keep HEAD~3
# → Di chuyển HEAD về HEAD~3
# → Giữ thay đổi chưa commit NẾU an toàn
# → Từ chối nếu có thể mất dữ liệu
```

### 10.9 Reset về commit cụ thể

```bash
git reset --hard a1b2c3d
# → Về đúng commit a1b2c3d, xóa mọi thứ sau
```

### 10.10 Tạo branch mới từ commit cũ

```bash
# Thay vì reset (nguy hiểm), tạo branch
git switch -c rescue-branch a1b2c3d
# → Branch mới từ commit cũ, main không đổi
```

**Lý thuyết**: Đây là cách **an toàn** để "quay về quá khứ" mà không mất hiện tại — tạo branch mới thay vì reset.

## 11. Lý thuyết nâng cao

### 11.1 `reset` không xóa objects — GC

```bash
git reset --hard HEAD~5        # commit vẫn trong objects
git gc                          # dọn objects unreachable (sau ~30 ngày)
git gc --prune=now             # dọn ngay (nguy hiểm — không cứu được)
```

**Lý thuyết**: 
- `reset` chỉ di chuyển ref.
- Commit cũ trở thành **unreachable**.
- Git **không xóa ngay** — chờ `gc` (mặc định 30 ngày với reflog).
- `git gc --prune=now` xóa ngay → **mất vĩnh viễn**.

**Tại sao không xóa ngay?** Vì reflog cần commit cũ để cứu. Đây là thiết kế "an toàn mặc định" của Git.

### 11.2 `reset` và submodule

```bash
git reset --hard HEAD~1
# → Submodule pointer cũng reset theo commit
# → Nhưng submodule working tree KHÔNG tự cập nhật
```

**Lý thuyết**: Sau reset, submodule con trỏ về commit cũ, nhưng thư mục submodule vẫn ở commit mới. Cần:
```bash
git submodule update --init --recursive
```

### 11.3 `reset` trong detached HEAD

```bash
git checkout a1b2c3d           # detach HEAD
git reset --hard HEAD~1
# → HEAD (detached) di chuyển, không branch nào đổi
```

**Lý thuyết**: Trong detached HEAD, `reset` chỉ di chuyển `HEAD` — không có branch ref để cập nhật. Commit bị bỏ → unreachable, cứu qua reflog.

### 11.4 `reset` vs `revert` cho shared branch

**Quy tắc vàng**: 
- **Shared branch** (main, develop): dùng `revert`.
- **Local branch** (feature cá nhân): dùng `reset`.

**Lý do**: `reset` viết lại lịch sử → người khác bị rối. `revert` giữ lịch sử → an toàn.

### 11.5 `git reset` không thể hoàn tác thay đổi unstaged

**Điểm lý thuyết quan trọng nhất**: 

```
Cứu được:
  ✅ Commit (Git object)
  ✅ Staged changes (trong index — nhưng khó)
  ✅ File untracked (không bị đụng)

KHÔNG cứu được:
  ❌ Unstaged changes trong working tree
```

**Tại sao?** Vì unstaged changes **chưa bao giờ được Git lưu**. `reset --hard` ghi đè chúng từ commit — không có bản sao nào khác.

**Nguyên tắc**: Trước khi `--hard`, **luôn kiểm tra** `git status` và **luôn commit hoặc stash** nếu có thay đổi quan trọng.

### 11.6 `reset` không đụng untracked files

```bash
git reset --hard HEAD
# → Reset tracked files
# → Untracked files VẪN CÒN
```

**Lý thuyết**: `reset --hard` chỉ reset **tracked files**. Untracked files (file Git chưa biết) không bị đụng. Để xóa untracked:

```bash
git clean -fd                  # xóa untracked files + directories
git clean -n                   # dry-run — xem trước
```

**Cẩn thận**: `git clean -fd` **không cứu được** — untracked files chưa bao giờ trong Git. Luôn `-n` trước.

## 12. Tổng kết lý thuyết

### Bảng tổng hợp mode

| Mode        | HEAD | Index    | Working Tree | Cứu được?              | Dùng khi                      |
| ----------- | ---- | -------- | ------------ | ---------------------- | ----------------------------- |
| `--soft`    | ✅    | ❌        | ❌            | ✅                      | Gộp commit, sửa commit        |
| `--mixed`   | ✅    | ✅        | ❌            | ✅                      | Bỏ stage, chọn lọc lại        |
| `--hard`    | ✅    | ✅        | ✅            | ⚠️ Commit ✅, Unstaged ❌ | Đồng bộ remote, hủy hoàn toàn |
| `--merge`   | ✅    | ✅        | ⚠️ An toàn    | ✅                      | Hủy merge, giữ thay đổi       |
| `--keep`    | ✅    | ✅        | ⚠️ An toàn    | ✅                      | Di chuyển HEAD an toàn        |
| `-- <path>` | ❌    | ✅ (path) | ❌            | ✅                      | Bỏ stage file                 |

### Nguyên tắc vàng

1. **`reset` không xóa commit** — chỉ di chuyển con trỏ. Commit cũ cứu được qua reflog.
2. **`--hard` xóa unstaged changes** — không cứu được. Luôn commit/stash trước.
3. **`--soft` an toàn nhất** — không mất gì, chỉ di chuyển HEAD.
4. **`--mixed` là mặc định** — bỏ stage, giữ working tree.
5. **`--hard` chỉ cho local** — không dùng trên shared branch.
6. **`reset <path>` = `restore --staged`** — bỏ stage file, không di chuyển HEAD.
7. **Reflog là phao cứu sinh** — commit "mất" vẫn cứu được trong ~90 ngày.
8. **`reset` không đụng untracked** — dùng `git clean` để xóa.
9. **Shared branch → `revert`**, local branch → `reset`.
10. **`--keep` an toàn hơn `--merge`** — từ chối nếu có thể mất dữ liệu.

### Điểm mấu chốt cần nhớ

**`git reset` là lệnh "di chuyển con trỏ" kết hợp "đồng bộ ba cây"**. Mỗi mode là một mức độ đồng bộ khác nhau:
- `--soft`: chỉ di chuyển con trỏ (lịch sử).
- `--mixed`: + đồng bộ Index.
- `--hard`: + đồng bộ Working Tree (ghi đè).

**Hiểu mô hình ba cây = hiểu `reset`**. Mỗi mode trả lời câu hỏi: "cây nào bị reset?". Và câu hỏi quan trọng nhất trước khi `--hard`: **"Tôi có thay đổi chưa commit nào không?"** — vì đó là thứ duy nhất **không cứu được**.
