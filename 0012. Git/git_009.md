# Merge Conflicts — Giải thích lý thuyết chi tiết

---

## 1. Bản chất: Tại sao conflict tồn tại?

### 1.1 Định nghĩa cốt lõi

**Merge conflict** xảy ra khi Git **không thể tự động quyết định** nội dung cuối cùng của một vùng trong file, vì hai (hoặc nhiều) nhánh lịch sử đã thay đổi cùng vùng đó theo cách khác nhau.

> **Điểm mấu chốt**: Conflict **không phải lỗi** — nó là **cơ chế an toàn có chủ đích**. Git chủ động **dừng lại** và **giao quyền quyết định cho con người** khi nó không chắc chắn. Đây là hành vi đúng đắn: thà dừng lại còn hơn tự động chọn sai và làm hỏng code.

### 1.2 Conflict không phải là vấn đề cú pháp

Đây là điểm lý thuyết quan trọng nhất, hay bị hiểu sai:

- Git **không** hiểu ngữ nghĩa code (không biết `if/else`, không biết function, không biết class).
- Git chỉ so sánh **văn bản theo dòng** (line-based).
- Khi hai bên sửa **cùng dòng** (hoặc dòng gần nhau) theo cách khác nhau → Git **không thể biết** nên chọn bên nào.
- Vấn đề là **ngữ nghĩa** (ý nghĩa của code), không phải **cú pháp** (cấu trúc text).

**Ví dụ kinh điển**:

```javascript
// Bên A sửa:
const TIMEOUT = 5000;

// Bên B sửa:
const TIMEOUT = 3000;
```

Cả hai đều **hợp lệ về cú pháp**. Git không thể biết 5000 hay 3000 là đúng. Chỉ con người — người hiểu context dự án — mới quyết định được. Đây là lý do conflict tồn tại.

### 1.3 Khi nào KHÔNG có conflict?

Git tự động merge được khi:

| Tình huống                                                    | Git xử lý                 |
| ------------------------------------------------------------- | ------------------------- |
| Hai bên sửa **cùng file nhưng dòng khác nhau** (cách xa nhau) | ✅ Auto-merge              |
| Hai bên sửa **file khác nhau**                                | ✅ Auto-merge              |
| Một bên sửa, bên kia không đổi                                | ✅ Lấy bên sửa             |
| Một bên thêm file mới, bên kia không chạm                     | ✅ Lấy file mới            |
| Cả hai thêm **cùng nội dung** vào cùng vị trí                 | ✅ Auto-merge (giống nhau) |
| Cả hai xóa **cùng file**                                      | ✅ Auto-merge (đã xóa)     |

**Nguyên tắc**: Git auto-merge khi các thay đổi **không chồng lấn về mặt văn bản** (textual overlap). Chỉ khi chồng lấn mới conflict.

## 2. Lý thuyết three-way merge — Nền tảng của conflict

### 2.1 Tại sao gọi "three-way"?

Merge không phải so sánh **hai** phiên bản — mà so sánh **ba**:

```
        BASE (common ancestor)
         /              \
        /                \
   OURS                  THEIRS
   (nhánh hiện tại)      (nhánh được merge)
        \                /
         \              /
          → MERGED ←
```

- **BASE**: commit tổ tiên chung gần nhất (`git merge-base`). Đây là "trạng thái gốc" trước khi hai bên phân kỳ.
- **OURS**: phiên bản ở nhánh hiện tại (branch bạn đang đứng — thường là `main` khi merge feature).
- **THEIRS**: phiên bản ở nhánh được merge vào (thường là `feature`).

### 2.2 Thuật toán three-way merge — Cách hoạt động

Với **mỗi vùng** (đoạn dòng) trong file, Git so sánh:

| BASE       | OURS  | THEIRS | Kết quả                                 |
| ---------- | ----- | ------ | --------------------------------------- |
| X          | X     | X      | Giữ X (không đổi)                       |
| X          | Y     | X      | Lấy Y (chỉ ours đổi)                    |
| X          | X     | Z      | Lấy Z (chỉ theirs đổi)                  |
| X          | Y     | Y      | Lấy Y (cả hai đổi **giống nhau**)       |
| X          | Y     | Z      | **CONFLICT** (cả hai đổi **khác nhau**) |
| X          | (xóa) | X      | Xóa (chỉ ours xóa)                      |
| X          | Y     | (xóa)  | **CONFLICT** (sửa vs xóa)               |
| (không có) | Y     | Z      | **CONFLICT** (cả hai thêm khác nhau)    |

**Điểm mấu chốt**: Git cần **BASE** để biết "ai đã thay đổi gì". Nếu chỉ có OURS và THEIRS, không thể phân biệt "cả hai thêm cùng nội dung" (hợp lệ) với "cả hai thêm khác nhau" (conflict).

### 2.3 Ví dụ minh họa three-way

```
BASE (commit C):
line 1: function calculate() {
line 2:   return a + b;
line 3: }

OURS (main):
line 1: function calculate() {
line 2:   return a + b;         ← không đổi
line 3: }                       ← không đổi
line 4: // TODO: optimize       ← thêm mới

THEIRS (feature):
line 1: function calculate() {
line 2:   return a + b;         ← không đổi
line 3: }                       ← không đổi
line 4: // TODO: add tests      ← thêm mới ở cùng vị trí
```

→ **CONFLICT**: cả hai thêm dòng mới ở **cùng vị trí** (sau dòng 3) nhưng **nội dung khác nhau**.

Nếu OURS thêm dòng 4, THEIRS thêm dòng 5 (cách nhau) → Git auto-merge (không conflict).

## 3. Conflict markers — Ngôn ngữ của conflict

### 3.1 Định dạng chuẩn (merge)

Khi conflict, Git chèn marker vào file:

```
<<<<<<< HEAD
nội dung của OURS (branch hiện tại)
=======
nội dung của THEIRS (branch đang merge)
>>>>>>> feature/login
```

**Cấu trúc**:

| Marker                  | Ý nghĩa                                                               |
| ----------------------- | --------------------------------------------------------------------- |
| `<<<<<<< HEAD`          | Bắt đầu vùng "ours" — `HEAD` = commit hiện tại (branch bạn đang đứng) |
| `=======`               | Ngăn cách giữa ours và theirs                                         |
| `>>>>>>> feature/login` | Kết thúc vùng "theirs" — tên branch/ref đang merge                    |

**Lý thuyết**: `HEAD` trong marker **không phải** là tên file — nó là **ref name** (thường là branch hiện tại). Tên ở dưới (`feature/login`) là ref của nhánh được merge.

### 3.2 Định dạng với `merge.conflictStyle=diff3`

Cấu hình `diff3` thêm **BASE** vào marker:

```bash
git config --global merge.conflictStyle diff3
```

Kết quả:

```
<<<<<<< HEAD
nội dung OURS
||||||| merged common ancestors
nội dung BASE (gốc)
=======
nội dung THEIRS
>>>>>>> feature
```

**Lợi ích**: Bạn thấy **BASE** — biết được "trước khi phân kỳ, code trông thế nào". Giúp quyết định sáng suốt hơn nhiều so với chỉ thấy OURS/THEIRS.

**`zdiff3`** (Git ≥2.35): biến thể của diff3, **cắt bớt** phần base trùng lặp với ours/theirs — gọn hơn diff3 nhưng vẫn giữ thông tin base. Được khuyến nghị hiện đại.

```bash
git config --global merge.conflictStyle zdiff3
```

### 3.3 Các loại conflict khác (không phải content)

Ngoài conflict nội dung, Git còn có:

#### 3.3.1 Add/Add conflict

Cả hai bên **tạo file cùng tên** với nội dung khác nhau:

```
<<<<<<< HEAD
nội dung file từ ours
=======
nội dung file từ theirs
>>>>>>> feature
```

#### 3.3.2 Modify/Delete conflict

Một bên sửa file, bên kia xóa file:

```
CONFLICT (modify/delete): config.js deleted in feature and modified in HEAD.
Version HEAD of config.js left in tree.
```

Git giữ file (ours) trong working tree nhưng đánh dấu conflict. Bạn quyết định: giữ file (sửa nội dung) hay xóa file.

#### 3.3.3 Rename/Rename conflict

Cả hai bên **đổi tên file gốc** thành các tên khác nhau:

```
CONFLICT (rename/rename): file.js renamed to a.js in HEAD and to b.js in feature.
```

Git tạo **cả hai file** (`a.js` và `b.js`) trong working tree → bạn quyết định giữ tên nào, xóa file kia.

#### 3.3.4 Rename/Modify conflict

Một bên đổi tên, bên kia sửa nội dung (file gốc):

```
CONFLICT (rename/modify): file.js renamed to a.js in HEAD but modified in feature.
```

#### 3.3.5 Binary conflict

File binary (image, PDF, compiled) không thể merge theo dòng. Git đưa ra:

```
CONFLICT (content): Merge conflict in logo.png
```

Bạn phải chọn một trong hai phiên bản (không thể "gộp").

#### 3.3.6 Directory/File conflict

Một bên có **thư mục** tên `foo/`, bên kia có **file** tên `foo`. Không thể cùng tồn tại → conflict.

## 4. Các ngữ cảnh sinh conflict

Conflict có thể xảy ra ở nhiều lệnh — mỗi lệnh có ngữ nghĩa `ours`/`theirs` khác nhau.

### 4.1 `git merge` — Ngữ cảnh chuẩn

```bash
git switch main
git merge feature
```

- `ours` = **main** (branch hiện tại).
- `theirs` = **feature** (branch được merge).

Conflict marker:
```
<<<<<<< HEAD               ← main
=======
>>>>>>> feature            ← feature
```

### 4.2 `git rebase` — Ngữ cảnh ĐẢO NGƯỢC

```bash
git switch feature
git rebase main
```

**Đây là cạm bẫy lớn nhất**. Trong rebase:
- `ours` = **main** (base mới — commit đang áp lên).
- `theirs` = **commit feature đang được áp lại**.

Conflict marker:
```
<<<<<<< HEAD               ← main (base mới!)
=======
>>>>>>> abc1234 (feat: ...) ← commit feature đang áp
```

**Tại sao đảo ngược?** Vì rebase "replay" commit của bạn lên base mới. Trong quá trình replay, Git coi base mới là "nền hiện tại" (ours), còn commit bạn đang áp là "thay đổi được áp vào" (theirs).

**Hệ quả thực tế**:
- `git checkout --ours <file>` trong rebase = **chọn base mới (main)** — thường **ngược** với ý muốn.
- `git checkout --theirs <file>` trong rebase = **chọn commit của bạn**.

### 4.3 `git cherry-pick` — Giống rebase

```bash
git cherry-pick <sha>
```

- `ours` = **HEAD hiện tại** (branch đang đứng).
- `theirs` = **commit được cherry-pick**.

Giống rebase về ngữ nghĩa ours/theirs.

### 4.4 `git stash pop` — Ngữ cảnh khác

```bash
git stash pop
```

- `ours` = **working tree hiện tại** (sau khi pull).
- `theirs` = **thay đổi đã stash**.

Đây cũng là nguồn nhầm lẫn phổ biến.

### 4.5 Bảng tổng hợp `ours`/`theirs`

| Lệnh                               | `ours`                | `theirs`             |
| ---------------------------------- | --------------------- | -------------------- |
| `git merge feature` (đang ở main)  | main                  | feature              |
| `git rebase main` (đang ở feature) | **main**              | **commit feature**   |
| `git cherry-pick X` (đang ở main)  | main                  | commit X             |
| `git stash pop`                    | working tree hiện tại | stash                |
| `git revert X`                     | HEAD hiện tại         | commit X (đảo ngược) |

**Quy tắc ghi nhớ**: Trong merge, `ours` = "cái tôi đang đứng". Trong rebase/cherry-pick, `ours` = "cái tôi đang áp lên" (thường là base, không phải branch của bạn).

## 5. Trạng thái conflict — Điều gì xảy ra bên trong?

### 5.1 Trạng thái index khi conflict

Index có **3 entry** cho file conflict (thay vì 1):

```bash
git ls-files -u
# 100644 abc123 1  config.js     ← stage 1: BASE
# 100644 def456 2  config.js     ← stage 2: OURS
# 100644 ghi789 3  config.js     ← stage 3: THEIRS
```

**Lý thuyết**: Git lưu **cả ba phiên bản** trong index với **stage number** khác nhau:
- **Stage 1**: BASE (common ancestor).
- **Stage 2**: OURS.
- **Stage 3**: THEIRS.

Đây là lý do `git checkout --ours` và `--theirs` hoạt động — chúng đọc từ stage 2/3 của index. Và đây là lý do khi conflict, file trong working tree **không khớp** với bất kỳ stage nào — nó là **bản tổng hợp có marker**.

### 5.2 Trạng thái repo khi conflict

```bash
git status
# You have unmerged paths.
#   (fix conflicts and run "git commit")
#   (use "git merge --abort" to abort the merge)
#
# Unmerged paths:
#   (use "git add <file>..." to mark resolution)
#     both modified:   config.js
#
# no changes added to commit (use "git add" and/or "git commit -a")
```

**Điểm lý thuyết**: Repo đang ở **trạng thái merge dở**. Git lưu `.git/MERGE_HEAD` (SHA của commit theirs) và `.git/MERGE_MSG` (message gợi ý). Trạng thái này **phải được kết thúc** bằng:
- `git add` (đánh dấu resolved) + `git commit` (hoàn tất merge).
- Hoặc `git merge --abort` (hủy, quay về trước merge).
- Hoặc `git reset --hard` (xóa sạch, quay về trước merge).

Bạn **không thể** `git switch` sang branch khác khi đang merge dở (trừ khi `--merge` hoặc `--discard-changes`).

### 5.3 File trạng thái đặc biệt

| File                    | Ý nghĩa                           | Lệnh tạo             |
| ----------------------- | --------------------------------- | -------------------- |
| `.git/MERGE_HEAD`       | SHA của commit đang merge         | `git merge`          |
| `.git/MERGE_MSG`        | Message gợi ý cho merge commit    | `git merge`          |
| `.git/MERGE_MODE`       | `no-ff`, `ff-only`...             | `git merge`          |
| `.git/REBASE_HEAD`      | SHA commit đang rebase            | `git rebase`         |
| `.git/rebase-merge/`    | Thư mục trạng thái rebase         | `git rebase -i`      |
| `.git/rebase-apply/`    | Thư mục trạng thái rebase (apply) | `git rebase --apply` |
| `.git/CHERRY_PICK_HEAD` | SHA commit đang cherry-pick       | `git cherry-pick`    |

Kiểm tra trạng thái:
```bash
git status
# hoặc
ls .git/MERGE_HEAD 2>/dev/null && echo "Đang merge"
```

## 6. Giải quyết conflict — Quy trình chuẩn

### 6.1 Quy trình 5 bước

```bash
# Bước 1: Nhận diện conflict
git status
git diff --name-only --diff-filter=U   # chỉ file conflict

# Bước 2: Xem chi tiết conflict
git diff                              # diff tổng hợp
git diff -- <file>                    # diff file cụ thể
git log --merge --oneline             # commit liên quan

# Bước 3: Sửa từng file
vim config.js
# Chọn/ghép nội dung, XÓA hết marker <<<<<<< ======= >>>>>>>

# Bước 4: Đánh dấu resolved
git add config.js                     # đánh dấu đã giải quyết
# hoặc
git add .                             # tất cả

# Bước 5: Hoàn tất
git commit                            # merge commit
# hoặc
git merge --continue                  # tương đương
```

### 6.2 Quy tắc khi sửa file conflict

**Bắt buộc**:
1. **Xóa toàn bộ marker** `<<<<<<<`, `=======`, `>>>>>>>` (và `|||||||` nếu diff3).
2. File cuối cùng phải **hợp lệ về cú pháp** (Git không kiểm tra, nhưng code sẽ hỏng nếu không).
3. **Test** trước khi commit — conflict resolution có thể đưa bug vào.

**Không nên**:
- Chỉ chọn "ours" hoặc "theirs" một cách máy móc mà không hiểu — có thể mất thay đổi quan trọng.
- Bỏ sót marker → file có `<<<<<<<` trong production → thảm họa.

**Mẹo**: Tìm marker còn sót:
```bash
grep -rn "<<<<<<<\|=======\|>>>>>>>" .
```

### 6.3 Các công cụ chọn nhanh

```bash
# Chọn toàn bộ OURS cho 1 file
git checkout --ours <file>
git checkout --ours .

# Chọn toàn bộ THEIRS cho 1 file
git checkout --theirs <file>
git checkout --theirs .

# Lấy file từ BASE (hiếm dùng)
git checkout --merge <file>        # tạo lại marker
git checkout -m <file>             # tương tự
```

**Lưu ý**: `git checkout --ours/--theirs` **không đánh dấu resolved** — bạn vẫn phải `git add` sau đó.

**Cẩn thận**:
- Trong **merge**: `--ours` = branch hiện tại, `--theirs` = branch merge.
- Trong **rebase**: `--ours` = base mới, `--theirs` = commit đang áp.
- Kiểm tra kỹ bằng `git status` hoặc `git diff -- <file>` trước khi chọn máy móc.

### 6.4 Mergetool — Công cụ đồ họa

```bash
git mergetool
```

Git mở tool đồ họa (mặc định `vimdiff`, có thể cấu hình `meld`, `kdiff3`, `Beyond Compare`...):

```bash
git config --global merge.tool meld
git config --global mergetool.keepBackup false   # không giữ .orig file
```

**Giao diện 3-way merge** điển hình:
```
┌─────────────┬─────────────┬─────────────┐
│   LOCAL     │    BASE     │   REMOTE    │
│   (ours)    │ (ancestor)  │  (theirs)   │
├─────────────┴─────────────┴─────────────┤
│           MERGED (output)               │
└─────────────────────────────────────────┘
```

**Lý thuyết**: Mergetool hiển thị **3 phiên bản** (từ 3 stage trong index) + **output** (working tree). Bạn click chọn từng vùng từ LOCAL/BASE/REMOTE, tool tự tổng hợp vào MERGED.

Sau khi đóng tool: `git add <file>` tự động (hoặc bạn phải làm tay tùy tool).

### 6.5 `git diff` với conflict

```bash
git diff                              # diff tổng hợp (working tree vs cả 3 stage)
git diff --ours                       # so sánh working tree với stage 2
git diff --theirs                     # so sánh working tree với stage 3
git diff --base                       # so sánh working tree với stage 1
```

**Ứng dụng**: `git diff --ours` cho biết "bạn đã sửa gì so với branch hiện tại". `--theirs` cho biết "bạn đã sửa gì so với branch merge".

## 7. Hủy bỏ conflict — Quay lại trạng thái an toàn

### 7.1 Hủy merge

```bash
git merge --abort
```

**Cơ chế**: Khôi phục `refs/heads/main` về trạng thái trước merge (đọc từ reflog hoặc `ORIG_HEAD`), xóa `.git/MERGE_HEAD`, reset index, khôi phục working tree. **Hoàn toàn hủy merge** — như chưa từng merge.

**Lưu ý**: `--abort` có thể **fail** nếu có thay đổi chưa commit trong working tree **trước khi** merge. Khi đó phải `git stash` hoặc commit trước.

### 7.2 Hủy rebase

```bash
git rebase --abort
```

**Cơ chế**: Khôi phục branch về `ORIG_HEAD` (trước rebase), xóa trạng thái rebase trong `.git/rebase-merge/`. **Hoàn toàn hủy** — commit local vẫn nguyên SHA gốc.

**Đây là "cứu cánh" khi rebase gặp quá nhiều conflict** — abort và chuyển sang merge (an toàn hơn).

### 7.3 Hủy cherry-pick

```bash
git cherry-pick --abort
```

**Cơ chế**: Khôi phục về trước cherry-pick (`ORIG_HEAD`), xóa `.git/CHERRY_PICK_HEAD`. Giống merge abort.

### 7.4 Hủy stash pop

```bash
git reset --hard ORIG_HEAD
# hoặc nếu chưa commit:
git reset --hard
```

**Lưu ý**: `git stash pop` conflict **không** để lại trạng thái đặc biệt — nó chỉ để working tree có marker và index có 3 stage. `git reset --hard` xóa sạch. Nhưng **cẩn thận**: `--hard` xóa **cả thay đổi chưa commit khác**.

### 7.5 So sánh

| Lệnh hủy                  | Khôi phục gì                | Xóa gì                   |
| ------------------------- | --------------------------- | ------------------------ |
| `git merge --abort`       | Branch về trước merge       | `.git/MERGE_*`           |
| `git rebase --abort`      | Branch về trước rebase      | `.git/rebase-*`          |
| `git cherry-pick --abort` | Branch về trước cherry-pick | `.git/CHERRY_PICK_HEAD`  |
| `git reset --hard`        | Bất kỳ về commit chỉ định   | Mọi thay đổi chưa commit |

## 8. Các chiến lược giải quyết nâng cao

### 8.1 `-X ours` / `-X theirs` — Auto-resolve conflict

```bash
git merge -X ours feature           # conflict → chọn ours
git merge -X theirs feature         # conflict → chọn theirs
git rebase -X ours main             # (đảo ngược ngữ nghĩa)
```

**Lý thuyết**: `-X` (strategy option) **không** bỏ qua toàn bộ theirs như `-s ours`. Nó:
- Merge bình thường cho các vùng **không conflict**.
- **Chỉ khi conflict** → auto chọn ours/theirs.

**Cẩn thận**:
- Có thể **mất thay đổi quan trọng** mà không biết (không có marker).
- Chỉ dùng khi bạn **chắc chắn** bên kia không có gì cần giữ, hoặc đã review kỹ.
- **Không dùng** cho merge branch chính.

### 8.2 `git rerere` — Reuse Recorded Resolution

**Lý thuyết**: `rerere` (REuse REcorded REsolution) ghi nhớ **cách bạn giải quyết conflict** và **tự động áp dụng lại** khi gặp conflict **tương tự** (cùng pattern).

```bash
git config --global rerere.enabled true
```

**Ứng dụng**:
- **Rebase branch dài**: cùng conflict có thể gặp lại nhiều lần khi rebase qua nhiều commit.
- **Merge branch nhiều lần**: fix conflict một lần, lần sau tự động.
- **Cherry-pick nhiều commit**: conflict lặp lại.

**Cơ chế**: `.git/rr-cache/` lưu hash của (base, ours, theirs) → resolution. Khi gặp lại cùng bộ ba → áp resolution đã lưu.

**Lưu ý**: `rerere` **không tự động commit** — nó chỉ đánh dấu resolved (file trong working tree). Bạn vẫn phải review rồi `git add`.

### 8.3 Merge strategies thay thế

Ngoài `recursive` (mặc định) và `ort` (mới), có:

```bash
git merge -s ours feature           # tree = ours, bỏ hoàn toàn theirs (chỉ đánh dấu merge)
git merge -s subtree feature        # cho subtree merge
git merge -s resolve feature        # đơn giản, ít conflict phức tạp
```

**`-s ours`**: Khác `-X ours` — bỏ **toàn bộ** nội dung theirs. Dùng để "đánh dấu đã merge" một branch mà không muốn lấy code (ví dụ: bỏ qua branch không cần).

### 8.4 `-X patience` và `-X histogram`

Thuật toán diff ảnh hưởng đến vùng conflict:

```bash
git merge -X patience feature       # patience diff: chính xác hơn cho code
git merge -X histogram feature      # histogram diff: nhanh hơn, ít "false conflict"
```

**Lý thuyết**: `patience` và `histogram` là thuật toán diff thay thế `myers` (mặc định). Chúng giảm **false conflict** — conflict do diff thuật toán chứ không phải thực sự mâu thuẫn. Đặc biệt hữu ích khi file có nhiều dòng trùng lặp (như code lặp, test case giống nhau).

### 8.5 `git merge-file` — Merge thủ công 3 file

```bash
git merge-file <current> <base> <other>
```

**Ứng dụng**: Merge 3 file bất kỳ (không cần Git repo) — hữu ích cho script, hoặc khi cần merge ngoài Git.

## 9. Phòng tránh conflict — Best practices

### 9.1 Nguyên tắc "commit nhỏ, merge thường xuyên"

**Lý thuyết**: Conflict tỉ lệ thuận với:
- **Thời gian branch sống** (càng lâu → càng nhiều thay đổi trên main).
- **Số dòng thay đổi** (càng nhiều → càng dễ chồng lấn).
- **Số file chạm** (càng nhiều → càng dễ conflict).

**Giải pháp**:
- **Feature branch ngắn** (< vài ngày).
- **Merge/rebase từ main thường xuyên** (hàng ngày).
- **Commit nhỏ, atomic** — dễ review, dễ revert, ít conflict.

### 9.2 Chia nhỏ file — Tránh "file God"

File lớn (>1000 dòng) dễ conflict vì nhiều người sửa. Giải pháp:
- Tách file theo module, class, function.
- Mỗi file chỉ một trách nhiệm.
- **Lý thuyết**: File nhỏ → vùng thay đổi nhỏ → ít chồng lấn → ít conflict.

### 9.3 Tránh format toàn file (mass reformat)

**Cạm bẫy**: Nếu bạn reformat toàn file (thay đổi whitespace, indent), Git thấy **mọi dòng đều thay đổi** → conflict với **mọi thay đổi khác** trên file.

**Giải pháp**:
- **Commit reformat riêng** — không trộn với feature.
- **Thông báo team** trước khi reformat lớn.
- **Cấu hình formatter** (`.editorconfig`, `prettier`, `gofmt`) để mọi người dùng chung.

### 9.4 `.gitattributes` — Giảm conflict do line ending

```gitattributes
* text=auto eol=lf
*.png binary
*.pdf binary
```

**Lý thuyết**: Trên Windows, Git có thể chuyển LF → CRLF khi checkout. Nếu không cấu hình, file bị coi là "thay đổi mọi dòng" → conflict giả. `.gitattributes` chuẩn hóa line ending → tránh conflict giả.

### 9.5 `CODEOWNERS` — Chia vùng trách nhiệm

```
# .github/CODEOWNERS
/src/auth/       @team-auth
/src/payments/   @team-payments
/docs/           @team-docs
```

**Lý thuyết**: `CODEOWNERS` tự động assign reviewer theo vùng file → giảm khả năng hai team cùng sửa một file mà không biết.

### 9.6 Giao tiếp

**Yếu tố con người** quan trọng hơn kỹ thuật:
- Thông báo khi sửa file "hot" (nhiều người chạm).
- Review chéo sớm.
- Chia task rõ ràng — tránh hai người cùng làm một feature.

## 10. Tình huống đặc biệt

### 10.1 Conflict khi merge commit (criss-cross merge)

Khi hai branch merge qua lại nhiều lần:

```
      A ← B ← C ← M1 ← D ← M3
       \       \       /
        X ← Y ← M2 ← Z
```

**Criss-cross**: `M1` và `M2` đều là merge của `B`/`Y`, tạo DAG phức tạp. Khi merge `D` và `Z`, Git phải chọn **base** — có thể có **nhiều common ancestor**.

**Thuật toán `recursive`** xử lý bằng cách **merge các common ancestor trước** (tạo "virtual base"). Đây là lý do `recursive` phổ biến và `ort` (Git ≥2.34) là phiên bản nhanh hơn, chính xác hơn của nó.

### 10.2 Binary conflict — Không thể merge

File binary (image, PDF, Office) **không thể merge theo dòng**. Git chỉ có thể:
- Chọn ours.
- Chọn theirs.
- Hoặc dùng tool ngoài.

```bash
git checkout --ours logo.png
git checkout --theirs logo.png
# hoặc mở cả hai phiên bản trong image editor, tự ghép
```

**Best practice**: Binary file nên được **quản lý riêng** (Git LFS) hoặc **tránh sửa đồng thời**.

### 10.3 Conflict với submodule

Submodule là con trỏ tới commit — conflict xảy ra khi hai bên trỏ tới **commit khác nhau** của submodule:

```
CONFLICT (submodule): Merge conflict in lib/some-lib
```

Giải quyết: chọn commit submodule nào (thường là commit mới nhất, sau khi cả hai bên đã update submodule).

### 10.4 Conflict trong file generated

File generated (lock file, build output) — conflict thường vô nghĩa. Giải pháp:
- **Không commit** file generated (`package-lock.json` — có thể commit nhưng conflict thì regenerate).
- Hoặc **regenerate** sau merge: `npm install` sinh lại lock.
- `.gitattributes` với `merge=ours` cho file generated.

```gitattributes
package-lock.json merge=ours
```

### 10.5 `git rerere` với rebase dài

Khi rebase branch 50 commit, cùng conflict có thể gặp lại. Bật `rerere`:

```bash
git config --global rerere.enabled true
```

Sau lần đầu giải quyết, các lần sau Git tự áp resolution. **Tiết kiệm cực nhiều thời gian**.

## 11. Tổng kết lý thuyết

| Khái niệm            | Định nghĩa cốt lõi                          | Lưu ý                                 |
| -------------------- | ------------------------------------------- | ------------------------------------- |
| **Merge conflict**   | Git không tự quyết định được nội dung cuối  | Là **cơ chế an toàn**, không phải lỗi |
| **Three-way merge**  | So sánh BASE, OURS, THEIRS                  | BASE là common ancestor               |
| **Conflict marker**  | `<<<<<<< ======= >>>>>>>`                   | Phải xóa hết trước khi commit         |
| **diff3/zdiff3**     | Thêm BASE vào marker                        | Giúp quyết định sáng suốt hơn         |
| **Index 3 stage**    | Stage 1=base, 2=ours, 3=theirs              | Cơ sở cho `--ours`/`--theirs`         |
| **`ours`/`theirs`**  | **Đảo ngược** trong rebase/cherry-pick      | Cạm bẫy lớn nhất                      |
| **`--abort`**        | Hủy merge/rebase/cherry-pick                | Cứu cánh khi rối                      |
| **`-X ours/theirs`** | Auto-resolve conflict                       | Cẩn thận mất thay đổi                 |
| **`rerere`**         | Ghi nhớ resolution, tự áp lại               | Cực hữu ích cho rebase dài            |
| **Phòng tránh**      | Branch ngắn, commit nhỏ, merge thường xuyên | Yếu tố con người quan trọng           |

**Nguyên tắc vàng**:

1. **Conflict là bình thường** — không phải lỗi, không phải thất bại. Nó là cơ chế bảo vệ.
2. **Hiểu BASE trước khi quyết định** — dùng `diff3` hoặc `git diff --base` để thấy gốc.
3. **`ours`/`theirs` đảo ngược trong rebase** — luôn kiểm tra ngữ cảnh trước khi dùng `--ours`/`--theirs`.
4. **Xóa hết marker** — grep `<<<<<<<` trước khi commit.
5. **Test sau khi resolve** — conflict resolution có thể đưa bug vào.
6. **`--abort` khi rối** — không cố giải quyết khi không hiểu; abort rồi fetch + xem lại.
7. **Bật `rerere` cho rebase dài** — tiết kiệm thời gian.
8. **Phòng tránh hơn giải quyết** — branch ngắn, commit nhỏ, merge thường xuyên, giao tiếp tốt.
